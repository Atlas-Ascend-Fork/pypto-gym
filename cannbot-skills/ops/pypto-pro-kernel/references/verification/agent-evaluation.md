# Evaluate skill effectiveness

Use matched tasks to determine whether a knowledge/tool change helps the agent. Keep checker regression, native correctness and agent behavior as separate results. [Tool invocation](../tooling/checks.md#tool-and-agent-evaluation) owns the commands; task definitions and observation validation live in `scripts/_checks/evaluation.py`.

## Freeze the comparison

Keep the input task, model identifier, reasoning setting, tool/device/time budgets, available framework source and installation fixed. Use fresh conversations with equivalent tool permissions. Give the baseline its frozen skill and examples; give the candidate the changed bundle. Copy companion examples into each isolated workspace so a broad search cannot reveal the candidate's new recipe to the baseline. An evaluation agent receives the task and raw source, not the expected diagnosis or repair. Exclude a trial whose context was contaminated; do not treat it as a valid baseline.

For knowledge-access trials, distinguish access, content and implementation changes. Compare original-file search/read against added query access using the same visible corpus, model and budget. Measure implementation changes against a fixed corpus and source/metadata changes against a fixed implementation; a combined improvement cannot establish either contribution alone. Generated distractors test scale and incomplete coverage, not new factual knowledge. Validate source-owner IDs and the public-export dependency closure before running questions: a defective snapshot or oracle is instrumentation failure, not a model or retrieval failure. Keep benchmark fixtures, grading code, planning records and other trial outputs outside subject workspaces. Canonicalize filesystem aliases when checking citations; a valid path/line/SHA proves a location, not the truth of the cited statement.

When a task asks about program verification or dependencies, its ordinary reference/test modules, `conftest.py` fixtures and `pytest.ini` are permitted source material. Evaluation prompts must distinguish these files from hidden graders, harness configuration and other trials; a blanket ban on “test configuration” can conflict with the task. If that ambiguity affects an observation, preserve it and exclude the affected comparison rather than crediting or penalizing the model for one interpretation.

Use development trials to calibrate tasks, budgets and rubrics. Freeze independent holdout tasks and graders before their outputs exist; once a formal failure informs a change, retain it as a regression and use fresh holdouts for the next effectiveness claim. A finished answer can exceed its declared action/time budget; preserve that failure and exclude it from eligible cost comparisons. Source-only adaptation, native parsing and independently executed numerical results are separate outcomes. MCP SDK parity does not replace an actual agent-host trial, and an unavailable host or controller leaves that part unverified.

State required interfaces, completion conditions and budget restrictions in the visible task. Distinguish a prescribed first call from later permitted retries; do not make an unstated query route or capability check a hidden completion requirement. Preflight task and rubric consistency before dispatch. If wording admits conflicting interpretations, retain the original answers and rubric observations, exclude the affected comparison from effectiveness claims, and use fresh tasks with explicit constraints. A supplied initial failure is experimental input; count subsequent spontaneous mistakes separately.

Geometry-constrained trials must check evaluated native launch values, not require one AST spelling. Legal controls include named constants, constant arithmetic, metadata parameters and cached native launchers. Bind any internal observation hook to the installed source identity and a capability probe; an unavailable hook leaves geometry unverified. Validate request parameters before device operations, and keep pinned status reads independent of device occupancy or execution locks. Recover an unknown outcome through its existing request identity before considering a new invocation; the [board execution rules](board-runs.md) own that boundary.

Check immutable input manifests before and after each trial, including empty package files. Any unexplained change excludes that trial from effectiveness and cost comparisons even when the nonempty sources still match and its answer is correct. Preserve the raw result and integrity difference; absence of a recorded agent edit does not identify the deleting actor or establish unchanged inputs throughout execution.

The source suite has development and held-out partitions covering aliased API names, different physical rows, legal aligned conversions, compact/odd NZ handovers and unresolved producers. These test the checker, not the model. `check.py evaluate --prepare /path/to/new/scratch-directory` copies the blind repair fixture from `scripts/_checks/tests/data/ub_l1_repair.py` and returns its task prompt and identity: preserve the native public callable and its supported specializations while making the VF increment and Cube contraction correct. Keep the fixture separate from the runnable example library. Its source hash identifies the input task; hashes of the model's resulting source identify each outcome.

Use independently executed native parsing and the numerical evaluator to grade a repair, including every supported ROWS/DIRECT combination, both AIVs, changed-input repeated calls and output guards. The independent evaluator must load source with ordinary Python annotation/future semantics rather than reusing the loader being tested; include legal annotation controls so a tool-created rejection is not taught as an API restriction. Source-check exit zero and an agent's self-report do not establish correctness. Unsafe or structurally unverified candidates stop before device execution; their numerical result remains unknown. Additional optimization tasks need the original precision contract and matched complete-call timing, not this repair task's checker score.

## Attribute a regression before changing knowledge

Separate implementation cost from the reason an agent selected it. Different model-written programs can change ownership, arithmetic, buffering and synchronization together. First use a fixed correct source and the [source-bound mechanism controls](../diagnostics/performance.md#test-a-mechanism-with-source-bound-evidence) to establish which legal transformation changes complete-call cost. A source-level switch can also change compiler lowering; inspect the realized difference before naming an individual instruction as the cause. A two-factor control family can compare each edge separately and expose interactions; do not add the measured speedups as independent savings.

Track the exact corpus body, query/rank, returned excerpt and truncation, delivery before the decision, and the observable choice or code change. Bind those records to source hashes. Corpus presence, a query hit, a later citation and an agent's self-report do not establish that the relevant conditions were delivered before the choice. Request a short choice, applicability and next check when needed; internal reasoning is not required. Missing original code or delivery records leaves the historical question unverified. A reconstruction has a new identity and can test a mechanism without replaying the missing trial.

For an access hypothesis, compare ordinary access, a routing-only change with the same prose, and directed exposure to that same body. Keep the task, source, model, budgets and execution feedback fixed; declare the directed reading as an intervention and count its visible actions and tokens. A rescue after directed exposure alone can reflect attention or application rather than a failed lookup. An access diagnosis also needs the original delivery gap and evidence that the routing intervention repairs it. Verify that the changed entry point was exercised before attributing a cost difference to that route. A model can infer a valid comparison from source or equivalent guidance without opening the target section; absence of that section alone does not establish absence of useful knowledge.

For misleading content, identify the specific changed passage and verify that it was delivered before the affected decision. Compare the unchanged bundle with selective withdrawal or a scoped replacement of that passage, then confirm on fresh holdouts. Control the changed excerpt size and surrounding context where practical, and report remaining volume or ordering differences. Identical old/new prose excludes a new wording claim for that passage; other content can still change discovery or priority. Failure after directed reading does not establish that the text is wrong. A common executor that returns the changed advice to both arms supplies shared help; keep its feedback fixed and include that boundary in the claim.

| Evidence | Maintenance decision |
| --- | --- |
| Installed source and a discriminating probe contradict a factual claim, or the owner omits a necessary applicability condition | Correct the existing owner and its version/consumer boundary; keep legal controls |
| Correct prose exists, but queries or bounded replies fail to deliver it, and the routing control repairs that gap | Change owner metadata, ranking, resolution or reply delivery; keep factual prose fixed |
| Correct conditions were delivered, but a source-bound misuse or omitted comparison persists | Improve the relevant diagnostic or conditional experiment suggestion; a cost hypothesis remains advisory |
| A specific changed passage induces an out-of-scope decision, and selective withdrawal/scoping repairs it on matched and held-out cases | Correct that passage's applicability, competing control and stopping condition |
| A valid decision produces a different executable, unsupported measurement or unresolved request | Repair execution/feedback identity and classification before grading knowledge |
| Effects are neutral, inconsistent, or indistinguishable from compiler/noise/context changes | Retain an unresolved result; do not manufacture a new fact or universal rule |

A controlled decision trial may reuse sealed native observations when all arms receive the same source/workload/toolchain-bound data and that reuse is declared. Reading a confirmation receipt establishes its identity; it is not an independent capture or new device execution. Grade selection and applicability separately from generating and independently running a new implementation. Count feedback requests separately from actual device starts.

Calibrate a fixed safe control family and the feedback path before model observations where possible. Preserve raw wall, queue/review waits and model-visible polling separately under the frozen accounting rules; infrastructure delay is not a knowledge diagnosis and cannot be deducted after a budget failure. Admit a new example only when the existing native programs cannot teach a verified composition. Its scope and controls must transfer to another consumer or workload regime, including a case where the proposed optimization is inapplicable or loses; task names and sampled-shape cutoffs are not the mechanism.

## Observe costs without inventing them

Each external observation contains `task_id`, `task_sha256`, `model`, `reasoning`, `budget`, `toolchain`, `repeat`, `variant` (`baseline` or `candidate`), `skill_sha256` and `source_sha256`. Budget and toolchain can be structured objects. Bind the model's output and grader artifacts outside Git. The optional observed metrics are `correct` (boolean), `repeated_errors`, `tool_calls`, `context_tokens`, `device_requests`, `wall_seconds` and `latency_us`. Use null when the host does not expose a measurement. Output bytes are not tokenizer counts; requested budgets are not measured usage.

`evaluate --observations` pairs only identical task/model/reasoning/budget/toolchain/repeat identities, rejects duplicate variants and invalid metrics, and preserves unmatched observations. It summarizes supplied evidence; it does not authenticate a self-reported pass or infer missing measurements. A matched pair carries a separate `cost_comparison`: eligibility requires both observations to declare `correct`, `budget_met` and `valid_protocol` true, with `telemetry_status: complete`; a false direction judgment excludes it. Missing acceptance evidence or incomplete telemetry keeps the cost comparison unverified. `available_metrics` lists only measurements present on both sides, so eligible input accounting does not invent total tool calls or peak context. These flags summarize caller-supplied evidence, not an independent audit of it. Repeated trials and additional held-out workloads are needed before making a general effectiveness claim. Report a single matched repair as a pilot, including failures and unavailable telemetry.

## Host event accounting

`check.py evaluate --events /scratch/events.jsonl` reads observed Codex JSONL events without importing a candidate or calling a model. Start/completion records for the same visible action identity count once; file edits count alongside commands and MCP calls. Pending actions remain attempts. Session polling is not fully exposed by this log, so total `tool_calls` stays null; `visible_actions` is the reported action count. A failed or truncated turn keeps total token use unknown instead of reporting a cheap completed run. Recognized pre-tool feature warnings count as host notices without requiring hook counters; hook-trust notices retain the separate attempt-coverage requirement below. Other error items and unknown kinds keep tool counts unverified. The input event file is hashed; this parser does not authenticate the host log or grade the task.

Use `input_tokens`, `cached_input_tokens` and `uncached_input_tokens` for cumulative host input accounting, including input resent across requests. `context_tokens` remains null when peak or unique context is unavailable; a character count or logged output byte count does not fill it. Missing fields remain null. Compare `budget_met`, task correctness and `direction_correct` before comparing costs; lower usage from a failed, interrupted or incorrect trial is not a context-efficiency gain. Log source/native gates, actual native starts and numerical checks separately. Define repeated failure by the same diagnostic boundary across verification attempts; failed lookup commands alone do not establish repeated kernel failures.

For optimization decisions, grade the selected mechanism, applicability, preserved contract, rejection control and next discriminating evidence. Include controls where a lexical pattern is already specialized or workload distribution is balanced. A correct plan is decision evidence; an implementation gain still requires numerical acceptance and complete-call timing. Keep development corrections separate from fresh holdouts and repeat with equivalent task/model/toolchain/budget identities before claiming a general effect.

For host context controls, freeze the underlying permissions, task, action/device/time budgets on both arms. If read-output caps are the treatment, record that difference explicitly rather than claiming identical tool environments or a pure knowledge ablation. Record the audited hook definition and actual rewritten command/result; an installed but skipped hook is not enforcement evidence. Report recognized-reader coverage separately from arbitrary-program access. Count byte-bounded replies, refusals, continuations and status queries alongside actual token telemetry; additional small replies can still increase cumulative input. Codex can omit pre-tool refusals from ordinary JSONL: bind `--host-counters` to the same event session before declaring attempt accounting complete. Keep per-status internal receipt reads separate from model-visible actions and unavailable total polling calls. A negative/changed receipt must not turn into a cheap successful trial.

## Admit a change

Inspect incorrect hard rejections and missed hazardous forms before increasing coverage. A query must provide enough context to perform the operation, including applicable physical representation and synchronization, without promoting an empirical optimization into a universal requirement. Compare numerical success under the fixed budget, repeated failures and the context/tool/device cost. Keep a narrow fix when it helps held-out cases; add new facts, rules or diagnostics at their existing owner rather than expanding the entry for every trial.
