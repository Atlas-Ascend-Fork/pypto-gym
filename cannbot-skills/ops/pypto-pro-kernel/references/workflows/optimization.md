# Optimization: measure → choose an experiment → compare

Use this for a kernel that is numerically correct on the workloads being compared. For a new kernel, start with [representative computation-path comparisons](authoring.md#compare-computation-paths-before-expanding-coverage); full-matrix correctness is a final acceptance requirement, not a prerequisite for those comparisons. A baseline-measurement request can finish with a verified metric. An optimization request also needs measured candidate comparisons. Keep the [authoring acceptance matrix](authoring.md#preflight-decisions) active throughout, and profile representative workloads unless full performance coverage is explicitly requested.

For a configuration-selection task, keep the supplied implementation family fixed and use [configuration comparisons](#choose-configuration-comparisons) to select its parameters and metadata dispatch. This task's acceptance concerns the selected configurations and their workload coverage.

When the user asks to avoid missing known methods, use [coverage mode](optimization-coverage.md) with an explicitly supplied card library (`--cards-root`; see [tooling/optimization.md](../tooling/optimization.md)). Coverage closure is a process result; paired native-task timing still decides whether the kernel is faster.

## First comparison for an explicit target

For supplied correct code with current source-bound evidence and an explicit performance target, first check whether a small control already exposed by the implementation is legal and predicted to meet that target. When ownership, capacity and the execution limit are established, compare that control directly using the original checker and complete-call metric. Preserve arithmetic and other controls for this first comparison; unrelated algebraic or scratch-buffer rewrites add validation cost and obscure attribution. Reuse applicable evidence and consult further references only for unresolved facts.

Once the requested correctness and performance target passes, deliver the best verified source and state untested directions. A new implementation is still required when the user explicitly asks for one. If the control misses the target, its legality or benefit is unresolved, or the optimization is open-ended, continue with the implementation loop below; consider structural opportunities without waiting for a full parameter sweep. A quick comparison does not establish global optimality.

## Carry contracts, reconsider implementation costs

A passing example establishes a correctness control, not tuned task parameters. Keep its verified computation while inspecting inherited preparation, buffer reuse, payload transport, batching and synchronization. A compact teaching example may choose a smaller live state at a throughput cost.

Use the applicable mechanism owner for the comparison: [row-work planning](../patterns/vf-row-reduce.md#plan-the-row-work-before-choosing-a-template), [bulk padding](../api/datamove.md#3-fillpad-requires-three-pieces-in-three-places-omitting-one-leaves-valid-data-surrounded-by-garbage), [buffer lifetimes](../api/memory-allocation.md#independent-buffers-and-slot-depth) or [exact key recovery](../patterns/ordered-selection.md#native-sort-records-and-index-payloads). Preserve a verified fast route while testing alternatives.

## Review residency, representation and publication

Start an implementation-optimization task by generating structural alternatives from the computation and complete dataflow, and revisit them after a meaningful accepted change. Do not wait until a tiling sweep fails or a pipe looks idle. A saturated pipe describes the current representation's work; another organization may require less of that work. The user's fixed-family configuration-only, measurement-only or diagnosis-only scope still takes precedence.

### Generate a concrete alternative from the computation

Use this as the implementation-optimization loop; the sections below supply decision details at each step.

1. **Derive work and ownership.** Write the actual expression, output domains, reduction extents/tails and recurrence dependencies; [trace addends, masks, normalization and rounding](#derive-opportunities-from-actual-expressions) before asserting an invariant. Map independent outputs to the actual launch workers and the busiest worker's iterations, including unused parallelism. Count repeated preparation, materialization, padded computation and partial publication. Current tensor shapes and kernel/helper boundaries need not be mathematical dependencies.
2. **Propose a concrete organization.** Distinguish the [inherited family's controls](#distinguish-family-selection-from-an-implementation-change) from new arithmetic, reuse, residency, output ownership or producer/consumer boundaries. Separate load panels, accumulator lifetime, publication groups and the work grid. Use a relevant [mechanism example](#turn-a-mechanism-example-into-a-task-specific-candidate) or [cost-specific route](#choose-the-implementation-experiment) when it resolves an implementation question.
3. **Rank and qualify candidates.** Rank legal controls from the current family alongside structural alternatives by predicted complete-call benefit and validation cost. Compare exposed parallelism and work elimination/reuse with local fusion: removed products/bytes/launches, added packing/merges/rereads, qualifying workloads and numerical/resource risks. State the changed loop/buffer/writer, physical slots and last reader. Collect or reuse [baseline diagnostics](#diagnose-before-changing-the-implementation) to make the prediction falsifiable. Easy integration alone is not a cost ranking; an unverified native mechanism is a focused capability question.
4. **Implement and compare.** Keep the strongest correct baseline. Reject cheap source, capacity or arithmetic contradictions first, then test the leading feasible candidate using the [screening and sampling policy](#screen-candidates-before-confirmation). Establish the original numerical contract and matched complete-call timing; an idea list, profile or parameter sweep alone does not test an implementation. Candidate classification does not force structural rewrites to precede launch or tiling comparisons. For example, independent rows serialized on one worker warrant a legal parallel-launch control before lower-impact arithmetic rewrites; include startup and transfer costs when choosing workers.
5. **Retain or restore, then continue.** Keep a supported gain or measured regime-specific tradeoff; restore the best source after a loss or unresolved comparison. Update the cost map when the mapping changes or evidence contradicts it, and pursue the next actionable hypothesis without seeking approval for each reversible experiment. Final acceptance uses the original evaluator and required coverage. Apply the [exit criteria](#exit-criteria) and [limit provenance](#budget-and-candidate-identity); a local sample/trial count does not end the task.

The source detector has narrow coverage; a missing `suggest` match or busy pipe does not close the structural review. A losing grouping rejects its tested geometry and lifetime costs, not all residency or ownership alternatives. Reconsider earlier candidates when their dominant extra cost changes.

### Distinguish family selection from an implementation change

A factory that already accepts `group_width`, threads, tile sizes or slots defines an existing parameter family. Selecting another value, adding a Host selector or generating a different existing specialization is configuration selection. This remains true when different values change the number of record owners or work waves. For example, selecting width 1 instead of 32 in an unchanged grouped sampler can be useful, but does not implement a new shared descriptor producer. An added selector changes the source AST without establishing a new computation organization.

An implementation change introduces work/dependencies beyond those existing controls: an algebraically reduced path, a device plan consumed by a different phase, retained state across former publications or a new partition/merge schedule. Selecting between algorithms already present is useful algorithm selection; report that separately from implementing a new one. Classification does not rank speedups or set experiment order. Preserve configuration-only scope when requested; for broader implementation optimization, a configuration result alone does not rule out credible implementation opportunities. A configuration may satisfy the requested performance target when no separate implementation change was required; report untested structural directions without claiming they are excluded. Give concrete capacity, dependency, numerical or complete-cost reasons for exclusions, rather than forcing an unprofitable rewrite.

### Derive opportunities from actual expressions

For `G=A^T*B`, write `G[i,j]=sum_r A[r,i]*B[r,j]`. An actual reduction extent of one gives an outer product before additional transformations; a configured chunk size or sampled matrix appearance does not. Check every addend and intervening operation: a dense residual added to G can destroy rank one, and elementwise transforms or prescribed finite-precision rounding need separate qualification. If the downstream computation repeatedly multiplies G or its Gram matrix, read the [invariant derivation](../api/numerics.md#prove-an-invariant-before-removing-work) before treating all those dense products as necessary work. Keep general-count and ineligible paths correct.

Likewise, when `f(record)` is used by many payload lanes, count how often the current source actually produces f: a hoisted channel loop may duplicate it per lane group rather than per channel. Compare [shared production or a device plan](../patterns/stable-placement.md#separate-reusable-metadata-from-payload-execution), including metadata reads/writes, synchronization, capacity and any extra launch. Changing only the existing group-width control remains a useful configuration comparison alongside that distinct implementation candidate.

Compare work at the complete-call level before choosing among such opportunities. A qualified rank-one polynomial can replace repeated dense matrix products with scalar iteration and reconstruction; fusing a later row update removes intermediate traffic and launches while retaining those products. Their coverage, stability, ownership and actual hardware paths differ. Count both sides and choose a discriminating experiment; operation counts do not prove latency ordering. If a cheap mathematical screen fails, state the failed condition and continue with the remaining candidates. A zero gradient only simplifies its own subgraph: later weight normalization, state commit and outputs may still be required.

Build a compact cost/ownership graph of the complete call: each tensor's GM/UB/L1/L0/register representation, physical pitch, producer, all readers, overwrite boundary and final publication. Compare useful arithmetic with executed padded/carrier products, and final tensor bytes with all intermediate/repeated transfers. Use the selected [capacity accounting](../api/memory-limits.md); capacity includes every simultaneously live plane, operand, scratch and slot. This review generates implementation candidates even when one pipe is continuously active under the current design.

The [expanded structural review](structural-review.md#structural-questions-and-native-anchors) supplies cost questions and native anchors when the current mapping needs deeper investigation. Routine candidate generation uses the loop above; it does not require closing every structural dimension.

When combining successful changes, compare `baseline → A → A+B` with common controls. Report incremental and cumulative times without adding percentages or isolated-stage gains.

## Measure first

Use [native-task timing](../verification/native-timing.md) for the execution-host helper path, callback contract, task counts, metric definitions and AB/BA calls. Freeze the comparison inputs, shapes, worker counts, metric, baseline and requested completion criteria before searching. Keep the best verified baseline available.

Inspect `per_task` and map execution positions to actual launches. Choose work that matters to the complete call, including initialization, movement, conversions and merges; a locally faster phase can lose once its new stages are included.

For a requested aggregate benchmark score, inspect its actual formula and estimate each workload's contribution from plausible latency reductions. Combine that sensitivity with measured headroom and implementation cost; the worst speedup ratio need not offer the largest score gain. Keep this prioritization subordinate to the user's chosen objective and the unchanged numerical contract.

If the goal is to exceed the supplied baseline, a gain over a slower prototype does not meet it. Validate the final library implementation through the original evaluator and cache protocol, including the selected dispatch on the complete case set. Report an aggregate score and mean speedup separately when both are requested; a nonlinear score is not interchangeable with an arithmetic mean. A mechanism example or isolated stage improvement is supporting evidence, not a replacement for that acceptance.

When a change adds native calls or wrapper work, report the task count and compare both [device-task and complete-call metrics](../verification/native-timing.md#choose-and-name-the-metric) before accepting it. A faster variant relative to its own new prototype does not supersede a stronger earlier implementation; unresolved numerical failures disqualify it regardless of timing.

## Diagnose before changing the implementation

Before selecting the first implementation experiment, collect [task-level pipe counters](../verification/native-timing.md#collect-pipe-counters-for-diagnosis) for the correct baseline. Use source, generated CCE (`kernel.cpp`) and, when needed, transformed IR to inspect work counts, buffer lifetimes and dependencies. Compare per-worker work with actual per-core counters when averages can hide a long tail. Record one observed cost, its source/core/pipe, the proposed change and the expected effect; [performance diagnosis](../diagnostics/performance.md) owns interpretation. Missing collector support is an explicit limitation, not a reason to abandon a valid native candidate or spend the whole budget on setup. Revisit diagnostics after a mapping change or unexplained regression; do not collect every expensive trace for every tuning point.

Use the [Active card index](../knowledge-cards/index.md) to find a mechanism that fits the observed cost. Read the whole card, check its target/API gate against the current authoring policy, and use its rejection case when designing the comparison. For CLI lookup and relation types see [optimization tools](../tooling/optimization.md).

Development and optimization use code inspection and focused native experiments. Select each experiment for a named uncertainty and keep individual diagnostic commands bounded; a command timeout or a capture-sized batch is not a task deadline.

### Turn profiling into the next implementation decision

Profiling supplies the prediction and next observation in the [implementation loop](#generate-a-concrete-alternative-from-the-computation):

1. **Locate the consequential cost.** Map the complete call to launches and work owners; distinguish startup, transfer, compute and tail regimes before extrapolating. Rank its contribution to the requested latency or score, not just its local speedup.
2. **Choose the cheapest discriminating observation.** Task timing and pipe counters are the starting point. Escalate to per-core distribution, one memory/counter group, or a bounded timeline only for the question each can answer; use the [profile-selection table](../diagnostics/performance.md#choose-the-next-profile-by-the-unresolved-question). Existing valid evidence can be reused. Missing tooling limits attribution; it does not require an endless setup effort before a legal matched implementation comparison.
3. **Make a falsifiable prediction.** State the source work to change, expected critical-path effect, added costs and a competing explanation. Use the [structural review](#review-residency-representation-and-publication) for repeated work/publication and the [conditional work model](../diagnostics/performance.md#model-the-current-mapping-without-declaring-a-hardware-limit) to rank candidates. A high busy ratio alone selects neither buffering nor a hardware ceiling. Explain reversals against the model; a changed counter or faster component alone does not justify promotion.

For a deliberately incorrect ablation, preserve legal addresses, initialized readers and completion boundaries. Label it diagnostic-only and implement the equivalent correct candidate before promotion. Keep the current hypothesis, evidence and next comparison in existing task state, without per-capture ledgers. A diagnosis-only request may finish with the supported hypothesis and proposed discriminating experiment.

## Budget and candidate identity

A task-wide stopping limit must come from the user, system or execution platform/controller, with a stated scope and an observed ceiling or remaining allowance. If none was supplied, record the task limit as unspecified and continue toward the requested result or evidence-supported convergence. Do not invent a time, token, device-request or trial ceiling, or infer exhaustion from a long conversation, slow compilation, several failed candidates or a sense that enough work has been done. To stop for a limit, name its source and the actual exhausted allowance.

Keep task-wide limits separate from memory capacity, per-command timeouts, diagnostic sample sizes and local experiment-state batch caps. Those constrain how work is executed; they do not by themselves end the task. A timeout requires inspecting and cleaning up the affected invocation, then continuing other feasible work or diagnosing a genuine blocker. A locally chosen batch size is not an externally authorized stopping criterion. Never reset, rename or start new batches to bypass a real cumulative quota.

When the host exposes `experiment_plan`, use it on the correct baseline before editing with the actual supplied limits. Distinguish any planning estimate or local batch size from a hard task ceiling. Reserve resources for repair and confirmation under real phase quotas. The runtime supplies actual elapsed/remaining values; outside that host obtain equivalent facts from its execution controller, keeping unknown usage unknown. Use `task_start` for native execution with `budget_phase=screen`, `fix` or `confirm`; `local` is CPU-only. One managed command is not one kernel launch or necessarily one test case.

Plan the discriminating implementation comparison before spending requests on final coverage. Read the remaining quota for its actual phase: unused protected repair/confirmation requests need not be available for a new candidate. If that admission rule stops exploration, report the budget constraint and the untested direction separately from any hardware hypothesis; do not relabel a new experiment as repair to bypass the reserve.

Bind the entry, wrappers and imported helpers to each attempt, including dynamic imports and non-Python dependencies; installed libraries belong to toolchain identity. Exact byte hashes bind results. Semantic comparison identifies rollback and ignores comments/unimported backups; AST or directory-hash changes do not classify an implementation change. Use the [source-bound work comparison](../tooling/checks.md#source-bound-contract-and-work-inspection) to resolve cheap contradictions before device requests. An executable dependency change invalidates its old numerical pass; an unrelated backup does not require a full rerun. Retaining the baseline is valid when candidates lose; report tested exclusions and open directions rather than keeping a regression to satisfy a change check.

## Choose configuration comparisons

Start with the supported parameter family, the current callable and its measured configuration. State whether the user's performance objective is a fixed benchmark set or transfer across the supported metadata domain; functional support for a domain alone does not specify its performance objective. For a transfer objective, treat supplied shapes as calibration anchors and reserve additional performance workloads before tuning. Separate capacity/alignment/ownership guards from performance estimates: guards determine legal candidates, while work counts prioritize comparisons among them. Inspect the [realized configuration](#compare-the-realized-configurations), including any capacity fallback that changes another parameter. A resource maximum, register width or full-worker launch is an initial control; its legality alone supplies no performance ranking.

1. **Make a small joint shortlist.** Include the current geometry, a coarser transfer/reuse unit and a finer ownership unit where legal. For each shortlisted geometry, compare its current launch with useful alternatives around changes in the busiest worker's iteration count, including the nonempty-owner count when it fits the platform. Count transfers, repeated bytes, useful/padded work and peak live storage along that worker's path. A configuration with fewer work items than cores remains a candidate: fewer calls or greater reuse can pay for lower concurrency. Test reduced concurrency at fixed geometry too. If changing tile size and workers together wins, compare the crossed configurations needed to distinguish their effects; a diagonal sweep leaves that interaction unresolved.
2. **Cross the metadata axes that can reverse a ranking.** Cover small and large independent-work counts, short and long reductions, retained-axis aspect ratios, alignment/tails and reuse regimes relevant to this implementation. A supplied benchmark list may vary several axes together. Combine a retained extent from one anchor with a reduction extent or aspect ratio from another, so a small number of crossed cases separates their effects. Where both independent work and reduction length vary, cover few/many outputs against short/long reductions instead of measuring only two diagonal combinations. Screen promising configurations on those contrasting regimes before dropping one for losing on a single shape. The [data-dependent workload contract](#data-dependent-work) applies when equal shapes can perform different work.

   Check what the measurement entry actually times. A numerical harness may validate several shapes while its benchmark selects only one. Add a matched capture for a declared tail or small-work regime before freezing a selector; correctness coverage does not supply its latency. Use the original criteria and the same complete-call metric, and keep unmeasured regimes explicit when the execution scope prevents that capture.
3. **Size comparisons using observed execution cost.** Account for compilation and collector export as well as kernel time, leaving room for checks outside the tuning anchors and required final validation. For a same-task-count family, [screen a shortlist in two captures](../verification/native-timing.md#screen-configurations-in-two-captures) with `compare_configurations`, preserving an adjacent baseline for every candidate. Split the matrix into commands fitting the execution timeout. Retain completed comparisons with exact parameter/source identity in ignored scratch; after interruption, inspect them and resume missing comparisons. Choose the shortlist and samples before collection under the [sampling policy](#screen-candidates-before-confirmation), preserving paired order and numerical checks. CPU enumeration does not replace latency comparisons.
4. **Time the public selector on additional metadata.** Derive a simple predicate from the measured tradeoff, then freeze it before testing unseen interior shapes, crossed-axis cases and both sides of its proposed boundaries. Resolve the actual selected configuration and time it against the preserved baseline and a plausible measured challenger. Each performance predicate needs a reason in the realized work: a resource/layout boundary, a change in reuse or worker assignment, or a measured crossover. An equality to a sampled reduction extent, a rounded bound around sampled rows, or a gap between sampled intervals needs this same justification. Compare a crossed case before treating such a sampling boundary as a reason to restore an untuned configuration. For a full-domain selection task, budget remaining after anchor confirmation should first address these unresolved regions. Production Host selection still uses permitted metadata, without reading tensor contents or performing an undeclared online search.
5. **Close the tested region explicitly.** Recheck [neighbors and coupled parameters](#check-the-neighbors-of-a-winning-configuration) after accepting a geometry or worker change. Report the prescribed aggregate and per-regime regressions separately, preserving uncertainty for close or order-dependent results. State which shapes and configuration directions remain unmeasured. A small representative set supports a scoped selector, not a universal threshold or global optimum.

Keep the supported domain, dispatch policy and measured coverage separate. Kernel constraints define which configurations are legal. The selector can generalize a measured reuse/ownership mechanism to other legal metadata; label that extrapolation as an inference and use its boundaries to choose validation cases. Timing coverage belongs in the evidence report. A fallback should follow a failed comparison, a credible cost-regime change or insufficient applicability of the candidate, rather than automatically excluding every shape outside the sample set. Review unexplained holes between regions using the same configuration. Preserve a justified baseline when the tradeoff remains unresolved, without claiming that either choice is optimal there.

Keep the acceptance questions separate:

| Check | Evidence it provides |
| --- | --- |
| Enumerate shape metadata and inspect resource guards | The selector returns configurations in the supported family |
| Explain dispatch predicates using realized work and measured crossovers | The selection policy has an explicit basis for extrapolation; its unmeasured performance remains an inference |
| Compare outputs, changed inputs and guards with the original reference | The selected implementation preserves the numerical and storage contract on those cases |
| Pair the selected configuration with controls on crossed and boundary workloads | The dispatch decision has performance evidence beyond its tuning anchors |

The computation pattern owns how each parameter changes physical work: [row batching](../patterns/vf-row-reduce.md#batch-independent-rows-even-when-each-row-fits), [outer-axis transfer blocks](../patterns/vf-outer-reduce.md#choose-transfer-and-register-blocks-separately), [GEMM output grids](../api/gemm.md#count-the-complete-output-grid-before-assigning-workers), and [slot depth](../api/memory-allocation.md#independent-buffers-and-slot-depth). Reuse this comparison procedure across those families; a measured cutoff belongs to its implementation, workload and toolchain scope.

## Preserve a fast baseline during refactoring

Freeze the working callable, its generated code and the requested measurement protocol. Change interface adaptation, function/stage extraction, synchronization ownership, stage schedule, physical layout and computation mapping separately when they can be isolated. A from-scratch implementation may be the deliverable while the old implementation remains an experimental control.

For `auto_mutex`/pipeline migration, first inspect what is already enabled. Match physical aliases to mutex IDs; an enabled decorator alone is insufficient. Remove a hand-written event only after identifying the generated dependency that replaces it. Check `get_buf/rls_buf`, actual cross-core producer/consumer pipes and slot reuse, including first/last and empty iterations. `preload=0` can isolate generated cross-core synchronization from changed overlap; it does not represent a final pipelined performance result.

If extraction or rewriting loses performance, inspect newly runtime VF flags and [hardware-loop lowering](../api/vf.md#keep-runtime-dispatch-out-of-vf-loops) before blaming the pipeline. A neutral loop/unrolling experiment does not exclude a separate branch cost. Re-test previously losing algorithms after removing that cost; an old ranking can reflect a compiler-shape penalty rather than the algorithm's work or reuse.

The optional [current experiment state](../tooling/optimization.md) retains one frozen best, current hypothesis and missing evidence across trials; its configured promotion gates do not replace the task's execution controller or sampling protocol.

## Compare the realized configurations

Before interpreting a parameter sweep, [verify the compiled variant](../verification/native-timing.md#verify-the-compiled-variant) and inspect the selected specialization: physical/valid tile sizes, slot depths, work-item counts, reduction panels, workers and generated compute calls. A capacity fallback can silently shrink another tile when a split size grows. Fewer inner splits per item may then be canceled by more items; changing only one source constant has not isolated one hardware cost.

Recompute work counts from executable expressions and the current input metadata. Inline comments, variant names and old summaries can disagree with the actual constants or loop bounds. For a wave-balance hypothesis, show the before/after tile count, worker count, `ceil(tiles / workers)` and the busiest worker's tile extents; a short host calculation is sufficient for known scalars. If that calculation contradicts the hypothesis, correct the prediction before spending a device request. A measured improvement remains evidence for the candidate, but cannot validate a work-count premise that was already false. Update affected geometry and slot comments with the retained implementation before freezing its final validation snapshot.

Resolve the Host dispatch predicate and selected specialization for every measured workload before calling its path unchanged. Check untested workloads against the same predicates: passing one shape does not validate all shapes using that branch, and an unmeasured shape may select a changed branch even when its broad label is “decode” or “prefill”. Use that map to choose confirmation and boundary cases; report the remaining coverage explicitly.

Count work over the complete workload and the busiest worker, including padded/boundary computation, handovers and repeated transfers. Where legal, hold the logical geometry fixed and adjust the relevant staging slots within their capacity and lifetime contract to isolate the compute-step comparison. Otherwise describe the result as a coupled configuration change. A full current allocation is a constraint on that layout, not proof that another tiling or state lifetime is infeasible.

## Data-dependent work

Equal shapes do not imply equal work for runtime masks, sparse routes, bounded gathers or interpolation. Uniform inputs over the legal domain may mostly skip costly loads. Separate execution density from locality using a small matrix: mostly active, mostly skipped, a boundary mixture, and repeated versus dispersed valid addresses where relevant.

Give performance inputs their own workload specification. Correctness fixtures may deliberately repeat a few addresses or use constant scores; reusing that generator can benchmark a tiny cached working set inside a large allocation. For indexed payloads, report the accessed-row count and approximate payload working-set bytes, and include a dispersed case spanning the legal table as well as high reuse. Keep segment-length distribution, score/value distribution and address locality as separate controls: changing a segment-distribution label must not silently change the scores or index stream too.

Keep each pair's exact inputs and worker count fixed. Tests may compute a valid fraction or workload count to explain results; production Host still handles metadata only. Correctness covers all contractual branches at the original tolerance.

For a changed SIMT decomposition, use the [launch contract](../patterns/simt-first.md#launch-variants) and [payload mapping comparison](../patterns/simt-payload.md#compare-flat-and-grouped-mappings) on these workload regimes. Retain a simple path or explain measured regressions when one configuration is not uniformly better.

## Change discipline

A coherent candidate includes necessary layout, indexing, ownership, workspace and launch edits. Hold common controls fixed, including worker count when legal, to attribute an implementation gain; describe unavoidable changes as coupled. Retune the accepted mapping separately and preserve both comparisons. Numerical regressions cannot be retained, and performance tradeoffs need measurements for the affected regimes.

Scope a negative result to its tested implementation, geometry, inputs and toolchain; a slow per-row branch does not rule out block specialization or vector predicates. Continue through the [implementation loop](#generate-a-concrete-alternative-from-the-computation) when actionable hypotheses remain. Put reusable conclusions in their pattern/API owner and example-specific evidence with the example; transient results belong in replies or ignored scratch, without unsolicited per-step ledgers or reports.

## Screen candidates before confirmation

This section owns sampling and resampling policy; [native timing](../verification/native-timing.md#compare-paired-implementations) owns helper mechanics. Follow the task's prescribed protocol first. For a free-form screen, declare representative workloads, warmup, pair/order counts, cache/capture protocol and decision criteria before collection. Helper defaults and example promotion thresholds are configurable, not additional task requirements. A sample count bounds that comparison, not autonomous optimization.

Reuse valid evidence bound to the same executed source/dependencies, specialization/launch configuration, toolchain, physical hardware, inputs, metric and protocol when it already meets the required coverage. Screening and final confirmation have different purposes, but changing the phase label alone does not require another capture. A changed final entry/dispatch, executable dependency or protocol needs evidence for that changed scope; final acceptance still uses the original evaluator and required numerical/performance coverage.

Ordinary jitter, a near tie, a small threshold miss or a desired winner does not justify extra rounds. Investigate a concrete collection fault before retrying. Additional sampling for unresolved uncertainty requires an allowance in the task's protocol and a decision-relevant question with a fixed plan declared before collection; uncertainty alone does not override a fixed-round rule. Preserve all valid observations under the prescribed aggregation, identify invalid captures with their reason, and report different protocols separately. Do not select favorable rounds. If permitted evidence remains inconclusive, retain the best verified source and label the comparison unresolved; continue other actionable hypotheses.

Keep one parameterized driver with validated baseline/candidate callables. For transport, launch or batching changes preserving arithmetic and indexing, a differential screen may use bitwise equality where bits must be preserved, plus controls for changed boundaries, ownership and slot reuse. It does not replace the independent reference: arithmetic-order/dtype changes need the original checker and semantic controls, and the selected candidate needs the full supplied acceptance matrix. Disable profiling when only numerical coverage is required; do not rebuild references or collect counters at every configuration without a new question. Follow the [stateful-callback contract](../verification/native-timing.md#in-place-and-stateful-callbacks) for mutation. Keep native and synchronized wall metrics distinct; unpaired session medians do not resolve their tradeoff.

## Check the neighbors of a winning configuration

Treat an initial heuristic value or bounded sweep as an open search region. Compare the current winner with legal neighbors at fixed inputs, worker count and metric, using the [sampling policy](#screen-candidates-before-confirmation). When an edge candidate wins, test the next legal neighbor in that direction; the new winner needs its own neighborhood check. Close each explored direction with a measured losing neighbor or actual resource/capability bound, or report it open if a verified hard limit or genuine blocker prevents the comparison. State the tested range and untested directions; a local winner is not a global optimum.

For coupled parameters, change one coordinate around the winner, then recheck the other after an accepted change. In particular, holding transfer width fixed isolates a slot-depth comparison; afterward, recheck width under the new total capacity. Changes in ownership or buffering can invalidate an earlier configuration choice. Reserve time for this search and final validation rather than stopping at the first successful implementation experiment.

## Exit criteria

Carry the unrounded inputs and formula with any derived stopping or headroom figure, and recompute it when reporting. `target / bound` is different from `(target - current) / (bound - current)`; state which question the ratio answers. Reconstruct aggregate results from raw per-case values, not rounded printed means or an earlier summary sentence. A model-derived bound still needs the independent evidence required by [performance diagnosis](../diagnostics/performance.md#distinguish-bandwidth-quantities).

For measurement only, report the validated metric. A stated correctness and performance target defines completion once the original checker and matched metric confirm it; deliver the best verified source and identify untested directions without claiming global optimality. For open-ended optimization, check the final configuration against the [neighborhood stop conditions](#check-the-neighbors-of-a-winning-configuration) and revisit pending implementation comparisons justified by the diagnosed cost. A completed numerical matrix or worker sweep does not close an unchecked direction. Continue feasible experiments while actionable hypotheses remain. If an explicit user stop, verified hard execution limit or genuine blocker interrupts the search, identify that condition and report the unresolved scope; do not convert an interruption into completion. A necessary change in tiling, ownership or compute paradigm returns to [authoring](authoring.md) within the same task.

Report source/toolchain identity, shapes, workers, data regimes, metric, paired results against the best verified baseline, and the stopping evidence or unresolved directions. A failed configuration sweep or an estimated byte count does not establish a DSL or hardware ceiling. Report an aggregate score only from the complete prescribed aggregation; a subset-based estimate cannot establish that the target was met or missed. If a requested score is unmeasured or unmet, identify the tested configuration family and open structural comparisons; retain an unverified bottleneck as a hypothesis. Keep numerical acceptance, measured improvements and remaining headroom distinct. Tool/link checks do not establish hardware speed or agent effectiveness.
