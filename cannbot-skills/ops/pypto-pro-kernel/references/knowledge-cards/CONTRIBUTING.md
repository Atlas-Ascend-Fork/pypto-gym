# 性能知识卡片贡献指南

新增卡片及实质性修订按本指南编写并完成验证；仅改措辞、排版或链接时，核对受影响内容并记录修订范围。已收录卡片的复审按[审核指南](REVIEW.md)执行，保留稳定 ID 和检索路径。

本指南供贡献者与 Agent 编写卡片、准备验证材料。独立审核按[审核指南](REVIEW.md)执行，并采用相同的格式与验证标准。

- [贡献准备](#contribute-a-card)：输入、查重、语言和贡献步骤。
- [格式与收录](#card-format-and-admission)：字段、编号及[可复制的英文模板](CARD_TEMPLATE.md#card-template)。
- [验证与材料](#validation-and-evidence)：完整样例、性能门槛和检查器接口。
- [独立审核](REVIEW.md#review-a-card)：逐行检查、设备复测和仅凭卡片的独立实现验证。
- [五项评分标准](REVIEW.md#score-the-five-criteria)：贡献者自评与独立审核共用。

<a id="contribute-a-card"></a>
## 贡献准备

卡片应满足不重复、格式规范、可泛化、简洁易懂、可验证五项要求，具体按[共用评分标准](REVIEW.md#score-the-five-criteria)核查。

### 输入与证据边界

提供优化前后源码、输入范围、数值契约、设备与工具链标识、数值结果、原始计时及机制证据。区分已观测事实、源码或文档保证与待验证推断，分别标明依据。缺少材料时列明所缺内容及验证方法；不得补造实现、测量结果或来源。

### 贡献步骤

1. 完成查重，确定新增或扩充的卡片及其稳定 ID。
2. 编写卡片与完整验证样例，优先使用可核实的来源算子；独立构造的样例应说明其代表性。
3. 固定测试条件和测量计划，完成目标设备上的正确性、性能及机制验证。
4. 对中文来源核对中英文版本，保存固定版本、原始记录及逐项自评。
5. 完成材料一致性检查，提交独立审核。


### 查重与内容组织

检索全部类别与状态、待审候选及同批材料。检索维度包括机制、瓶颈、数据搬运、依赖关系和前后代码变换。记录知识库版本、检索词、相近卡片 ID 及比较结论。相同机制在不同算子、形状或 API 表达中的应用，应扩充已有卡片；新增 ID 应对应独立机制。

每张卡片应说明一项可复用的改动、适用条件、语义约束、开销变化和至少一个排除条件。具体算子名称、测试规格及耗时归入有明确条件的验证实例。使用通行术语，必要的新术语应在首次出现时定义。[卡片模板](CARD_TEMPLATE.md#card-template)

<a id="prepare-the-language-versions"></a>
### 语言要求

中文来源应先形成完整中文原稿，再生成英文卡片。中文原稿随验证材料持久归档，两版使用同一 ID，并分别记录版本与 SHA-256。英文原创无需补写中文原稿。双向核对适用条件、代码变换、API、数值、单位、限定条件和局限，确保所有技术主张一一对应。语义核对记录应包含对应位置和核查结论。[双语审核](REVIEW.md#compare-the-chinese-original-with-the-english-card)

<a id="card-format-and-admission"></a>
## 格式与收录

卡片使用 UTF-8 编码的 Markdown，文件开头用 YAML 填写元数据。[索引](index.md)声明 `okf_version: "0.2"`，其中的有效卡片表决定哪些卡可以被查询。贡献指南、教学示例和模板都在表外。[OKF v0.2 格式规范](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md)

| 字段 | 填写要求 |
| --- | --- |
| `type`、`title`、`description`、`tags` | 卡片的 `type` 固定为 `PyPTO Performance Optimization Card`。标题点明一种可复用的优化机制，描述概括其作用，标签标注所属领域或类别。 |
| `status` | `stable` 对应有效卡片（Active），`draft` 对应草稿（Draft），`deprecated` 对应已退役（Retired）。有效状态表示可以在满足条件的负载上考虑该机制。退役时保留编号并写明原因。 |
| `item_id` | 更新已有卡时保留原编号和路径。新增机制前，先检查索引的全部状态，再在对应类别中分配下一个未使用的两位序号。路径格式为 `<category>/<item_id>-<short-name>.md`。 |
| `bound_hint`、`applicability`、`target_api_gate` | 分别写出瓶颈资源或依赖关系、可观察的适用条件，以及已经核实的设备和 API 限制。 |
| `sources` | 可选。写明实际查阅的资料。需要把结论归到特定来源时，为来源分配标识，并在正文用相同的 Markdown 脚注标签引用。区分框架保证的行为和特定设备上的观测结果。 |
| `knowledge_links` | 可选。每条关系都要写清与目标契约或文档重合的部分，以及该关系不能推出的结论。[关联规则](KERNEL_INTEGRATION.md) |

新增卡片或实质性修订的正文、元数据、图表说明和代码注释均用英文。每张卡解释一种可推广到其他算子的机制，并给出至少一个反例或不适用条件。`## Before` 和 `## After` 各自只放一个 Python 代码块，从对应已实测实现中摘取体现改动的代码，使审核者能逐行核对。完整程序、运行命令和设备证据保存在配套样例中。[卡片模板](CARD_TEMPLATE.md#card-template) · [片段与完整实现的对应规则](#build-the-companion-example)

已有卡的检索标识保持稳定。新增卡片，或实质修改优化机制、示例代码、收益结论时，须完成投稿和独立审核。仅改措辞或链接时，说明修订范围。收录材料应包含可运行对照和目标设备上的验证证据。符合要求后，一并更新英文卡片和中文索引行。索引中的中文标题、适用条件和设备限制要与卡片语义一致，编号、状态值和路径保持原样。[验证规范](#validation-and-evidence) · [审核流程](REVIEW.md#review-a-card)

<a id="validation-and-evidence"></a>
## 验证与材料

<a id="build-the-companion-example"></a>
### 完整验证样例

优先采用能够固定版本并核对实现的来源算子，分别提供优化前和优化后的完整代码。独立构造的验证算子应说明其与卡片所述计算场景、依赖关系和优化机制的对应关系。

| 材料 | 内容要求 |
| --- | --- |
| 优化前实现 | 完整的基线算子、公开入口及依赖 |
| 优化后实现 | 保持相同公开契约，明确体现所述优化 |
| 独立参考与测试 | 预先确定的精度规则、共享输入和完整必测用例 |
| 计时驱动 | 预热、完整调用边界、两种执行顺序和原始记录 |
| 复现说明 | 环境要求、构建和执行步骤、输入生成及结果计算方法 |
| 原始证据 | 设备、工具链、源码、命令、退出状态、数值及计时产物 |

目录和入口名称可沿用项目规范。Before/After 应对应完整受测实现，并标明文件、符号、位置和版本。展示时可移除公共缩进；抽象、改名和省略应明确标注，供审核者对照源码核查。

对照实现应保持工作量、数值契约、布局、初始化和计时范围一致。其他优化应通过消融对照区分。采用生成代码、计数器、时间线或匹配实验，验证所述机制及其对开销的影响。

<a id="freeze-the-cases-and-collect-the-evidence"></a>
### 设备验证与性能标准

工作负载指输入形状、数据类型、布局、参数或数据分布等测试条件的组合。每张卡片至少选择两组在优化机制上具有实质差异的收益用例，并另列正确性边界用例和排除条件。收益用例须同时通过正确性与性能门槛；仅用于正确性或预期拒绝的用例不要求提速。测量前固定各用例的角色和理由，不得在看到结果后改为非收益用例。测量前固定输入、随机种子、数值门槛、指标、单位、调用范围、预热、重复次数和缓存策略。

将计划保存为 JSON。`metrics` 列出每个收益用例须验证的指标。`cases` 按用例 ID 记录角色（`benefit`、`correctness` 或 `exclusion`）、输入定义和纳入理由。将测试驱动、用例数据及实现依赖等影响执行的本地文件引用放入计划的 `dependencies`，每项记录相对路径和 SHA-256。原始执行记录应能定位计时前固定的计划版本。

1. 在声明的目标设备上编译并执行两个实现。所有必测数值用例均应满足相同的独立参考和精度要求，失败数与跳过数均为零。保留误差、容差、输入标识及原始输出。
2. 固定 A 为优化前、B 为优化后。对每个声称获益的用例，在同一设备会话中按 A→B 和 B→A 各采集至少 10 对完整调用，预热另计。两种顺序用于检查顺序效应；保留全部有效配对以及无效采集的原因。
3. 对每个收益用例的每种顺序分别判定：至少 90% 的配对满足 `after_us < before_us`，且 `median(after_us / before_us) ≤ 0.97`。持平不计为获胜。报告两版本时延中位数、配对比值中位数、获胜比例、离散程度及原始数据。上述数值为本库的验收门槛。
4. 启动或封装工作发生变化时，同时验证端到端完整调用耗时；各必测指标均应满足门槛。项目规定更严格要求时，应同时满足。
5. 保存设备与会话标识、软件版本、受测源码与驱动标识、实际命令、退出状态及机制证据。采集数据、受测实现和性能结论应可相互追溯。

[设备执行规范](../verification/board-runs.md) · [原生计时规范](../verification/native-timing.md#compare-paired-implementations)

### 原始计时数据

每份计时文件对应计划中的一个收益用例和一个指标，包含 `case_id`、`metric` 和 `orders`。支持 `native_task_sum_us` 和 `synchronized_wall_us`，单位均为微秒。AB 数组按 `[before_us, after_us]` 记录，BA 数组按 `[after_us, before_us]` 记录。

配对计时接口 `compare_native`、`compare_wall` 通过 `include_pairs=True` 输出 `orders`，每项包含 `order` 和 `raw_pairs_us`。独立采集器也可采用 `{"AB": ab_pairs, "BA": ba_pairs}` 映射。验证驱动在保存时写入 `case_id` 及下文规定的摘要字段。[计时工具](../../scripts/profile_kernel.py)

原生计时要求每次调用在同一条流上产生固定的任务序列。调用 `compare_native` 时指定 `evidence_dir` 为一个尚未创建的目录，保留优化前单次调用、优化后单次调用和 AB、BA 的四份原始 CSV。计时文件的 `native_captures` 按 `before`、`after`、`AB`、`BA` 引用这四份文件，每项包含路径和 SHA-256。检查器按单次调用的任务数量和名称序列核对分组，并从 CSV 重算配对耗时。准备输入与状态时应计入每侧一次额外的独立采集。动态任务序列或无法核对任务归属的采集不能作为该指标的证据。

<a id="author-preflight"></a>
### 材料一致性检查

材料检查器（[接口实现](../../scripts/check_card_submission.py)）采用 `check_card_submission.py <card> <example_root> <evidence>` 参数形式。

| 参数 | 含义 |
| --- | --- |
| `card` | 固定版本的待检查卡片 |
| `example_root` | 验证材料的共同根目录 |
| `evidence` | 包含文件引用及原始计时引用的 JSON 清单 |

清单使用相对于材料根目录的路径和实际文件字节的 SHA-256 摘要。`sources.before` 和 `sources.after` 引用受测实现，`oracle` 引用独立参考，`plan` 引用固定计划，`correctness` 引用正确性报告，`timings` 引用计划要求的全部计时文件。`artifacts` 引用原始日志及其他证据，适用时包含中文原稿。

```json
{
  "schema_version": 2,
  "sources": {
    "before": {"path": "baseline/operator.py", "sha256": "<SHA-256>"},
    "after": {"path": "optimized/operator.py", "sha256": "<SHA-256>"}
  },
  "oracle": {"path": "reference.py", "sha256": "<SHA-256>"},
  "plan": {"path": "plan.json", "sha256": "<SHA-256>"},
  "correctness": {"path": "correctness.json", "sha256": "<SHA-256>"},
  "timings": [
    {"path": "timing-1.json", "sha256": "<SHA-256>"},
    {"path": "timing-2.json", "sha256": "<SHA-256>"}
  ],
  "artifacts": [{"path": "run.log", "sha256": "<SHA-256>"}]
}
```

验证驱动在构建和执行时对实际加载的两个实现记录 `source_sha256`（包含 `before`、`after`），并记录实际读取的 `plan_sha256`，将这些摘要同时写入正确性报告及每份计时文件。涉及多文件实现时，同时核对计划所列依赖。归档的构建和执行记录应保留实际载入的构建产物标识。更改实现、依赖或计划后，须重新验证受影响的结果，不能在归档时用新摘要替换旧结果的绑定。

正确性报告还应包含实际使用的独立参考的 `oracle_sha256`，并在 `cases` 中按用例 ID 记录所有收益和正确性用例的 `before`、`after` 结果，两者均为 `passed`。预期拒绝的域外输入单独记录。

检查器核对文件与结果的摘要、声明的用例与指标覆盖、原生任务分组及配对统计，并提供片段定位。独立审核确认计划是否足以覆盖适用范围、片段与实际执行路径、设备来源、机制归因和双语语义。

### 自评与交付

按五项标准逐项记录结论、证据位置和得分。完整交付包括卡片、适用时的双语对照、验证实现、复现说明、原始产物、材料检查结果和自评报告。材料应满足版本固定、结果可复算、结论可追溯的要求。[独立审核](REVIEW.md#review-a-card)


<a id="evidence-organization-example"></a>
### 证据组织示例

以[循环不变量复用](vec/vec-06-broadcast-once-vl-merge.md)为例，先证明各次迭代的输入值、地址、范围和掩码保持不变，并核对别名及写入。基线在循环内读取，候选将适用读取外提，其余计算与数值契约一致。

选择不同复用次数或工作集规模的收益用例，另列尾部及地址、掩码变化等边界或排除条件。对比生成代码、读取次数以及寄存器或缓冲占用，验证减少读取与延长数据生存期的成本变化。结论绑定源码、设备、工具链和原始数值、计时及机制证据，仅覆盖已验证条件。

## 材料组织建议

采用 PR 提交时，建议分别组织英文卡片和验证材料；中文来源的原稿随验证材料保存。提交形式不属于内容质量评审条件。
