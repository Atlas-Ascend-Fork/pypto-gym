# 技术卡片 vec-20：外部只读表按并发读者复制副本

- **适用 bound**：访存 / MTE2（读取侧；并发访存命令落在同一片地址区域造成的串行，不是容量或带宽）
- **一句话**：一份小的只读表被大量读者每拍并发读取时，复制成若干份并按 id 错开，
  让并发读取真正并行；**错开量必须与单次搬运的地址足迹同量级**，按更细的粒度错开无效。

## 何时用（诊断特征）

- 存在**外部构造的只读表**：由 host 侧生成、kernel 全程不写，例如掩码模板、查找表、系数表、
  索引表。
- 该表在**每拍或每次迭代都被读取**，且读取在主循环的路径上。
- **并发读者数量多**（数十个量级），且各读者一次搬运覆盖的地址区域**彼此重叠**。这里的判据是
  地址区域的重叠，不是表的总大小，也不是读者起始地址是否精确相同——见“原理”。
- profiler 显示该流水（AIV 侧为 MTE2）耗时明显偏高，而该表的**单次搬运量很小**：耗时与数据量
  不成比例，是最直接的运行时判据，说明瓶颈不是带宽。
- 最可靠的确认方式是**改副本数做剂量响应**：只改副本数、其它一律不动。表是只读的、各副本内容
  相同，输出必须逐位一致。若耗时随副本数单调下降并饱和，即确认；若完全不动，则问题在别处。

已核验的算例（Ascend 950，block-sparse FA）：一张几十 KB 的 uint8 掩码模板，全部 AIV subblock
每拍各从中读一个固定大小的窗口。共享单份时该流水是全 kernel 的瓶颈，改为按读者复制后瓶颈转移到
其它流水，端到端收益可观；两种配置输出逐位一致。

## 何时不适用

- **读者数量少**。代价随每副本读者数迅速衰减，降到十几个以下时本算例已观测不到，只有几个核
  并发读时本方法无事可做。
- 表**很大**：成本分三层，须分开评估。显存占用与 host 侧构造成本按副本数**线性增长**；读取次数
  与单次 tile 不变时，每次读取的**逻辑请求字节数不变**（这一条是静态结论，仅在读取次数与 tile
  均不变时成立）；而**实际 GM 流量**随副本数如何变化不能由上述两条推出——各副本不再共享同一片
  地址，缓存行复用随之改变——该项一律须绑定测量证据。表大到实测流量成为新瓶颈时本方法反向有害，
  表小是前提，不是可放松的条件。
- 读取**不在热路径**：整个 kernel 只读一次、或在声明区读取，复制不解决任何问题。
- 表**会被写**：一旦 kernel 写入，多副本立即引入一致性问题，本方法只适用于纯只读数据。
- 各读者的搬运区域**本来就互不重叠**（例如表被切成若干段、每个读者只读自己那段且段间距离大于
  搬运足迹）：已经天然错开，无串行可消除。
- 显存紧张：先做剂量响应取够用的副本数，不必一律按读者数复制。

诊断上容易误判的相邻情形：读取耗时高也可能来自**搬运形状差**（跨步短突发）或**与消费者没有
重叠**。区分办法见“性能与验证指标”。

## 原理

**性能根因**：读取该表的那条流水之所以慢，不是搬运量大，而是数十个读者每拍发出的访存命令落在
同一片地址上、只能依次完成；把读者按地址分开，这些命令就恢复并行。

访存以固定大小的块为单位完成，一次请求作用于整块而不能再细分（Ascend 950 上 cache line 512 B，
分为 4 个 sector，每个 128 B，sector 是最小访存单位——读半个 sector 也要搬满一个 sector）。
多个核的访存命令落在同一块上时，这些命令无法并行、只能依次完成。

但**判断两个读者会不会互相阻塞的尺度不是最小访存单位，而是单次搬运的地址足迹**。这一点实测
证伪过按 sector 量级思考的直觉：本算例里模板的行距恰好是一个 sector，一次搬运因此横跨上百个
连续 sector。把所有读者的起始行取成完全相同（足迹完全重叠），与把起始行散开到仍有约一半足迹
重叠的程度相比，**耗时没有可测差异**——在足迹内部错开若干 KB 等于没错开。两个读者起始位置相差
W 行时仍有“足迹行数 − W”行重叠，只有把读者分到互不重叠的整片区域，串行才会消失。

因此本方法的机制是**按足迹量级把读者分到互不相干的地址区域**：复制成多份、读者按 id 索引自己的
副本，副本间距天然等于表的整体大小，必然大于足迹。代价是显存占用乘以副本数——用显存换并发访存的
并行度，只有表足够小时才划算。

代价随**每副本读者数**下降，且是超线性的：读者数减半，代价的下降幅度远超一半；降到十几个以下后
端到端时间不再变化（该流水的计数器仍继续下降，但此时它已不在关键路径上）。这给出了副本数的选取
依据——**按实测取到曲线转平处即可，不必真的每读者一份**，转平的位置随算子而异，必须自己扫一遍。

一个容易走反的直觉是“共享一份能常驻片上缓存，所以共享更快”。这在**读者不并发**时成立，但数十个
读者并发读同一片区域时，串行的代价盖过驻留收益。分界取决于表大小与并发度，必须实测。

## 怎么改（before / after）

以下为**嵌入片段**，取自一个已上板验证的 kernel：一张 uint8 掩码模板被全部 AIV subblock 在每拍
各读一次。表的行数按副本数扩展，kernel 侧从张量形状反推副本数，因此同一份 kernel 既能吃单副本也能
吃多副本，由 host 决定。表的 dtype、行列含义与 Tile 尺寸须按当前算子核验。

```python
import pypto_pro.language as pl
import torch

TABLE_ROWS = 256          # 单副本行数；表的语义由算子自身定义
TABLE_COLS = 128
SUBBLOCKS_PER_CORE = 2    # 每个 cube 核对应的 AIV subblock 数，按平台核验
TABLE_COPIES = None       # None 表示每 subblock 一份；按剂量曲线可取更小值以省显存


def make_table(device, n_copies=1):
    """host 侧构造表；n_copies 份内容相同的副本在行方向堆叠。"""
    t = build_single_copy()                     # [TABLE_ROWS, TABLE_COLS] uint8
    return t.repeat(n_copies, 1).to(device)


# before：单份表，所有 subblock 每拍读同一批地址
# with pl.section_vector():
#     ...
#     for beat in pl.range(0, n_beats):
#         pl.load(tile_slot, table, [row_off, col_off])

# after：多份副本，读地址按 id 错开整张表的大小
with pl.section_vector():
    sub_id = pl.get_subblock_idx()
    # 副本数从张量高度反推，host 传单副本表时 copy_base 恒为 0，退回 before 的行为。
    n_copies = table.shape[0] // TABLE_ROWS
    copy_base = (core_id * pl.get_subblock_num() + sub_id) % n_copies * TABLE_ROWS
    ...
    for beat in pl.range(0, n_beats):
        pl.load(tile_slot, table, [copy_base + row_off, col_off])
```

`copy_base` 在 section 的声明区算一次，不在每拍的路径上；主循环里只多一次标量加法。
`% n_copies` 使副本数与读者数不必相等——这正是按剂量曲线取中间值的落点：host 侧按
`TABLE_COPIES` 传若干份，若干读者共享一份，仍是合法配置。

## 性能与验证指标

比较 `Task Duration(us)`、读取该表那条流水的忙时（AIV 侧 `aiv_mte2_time`）与单次搬运的数据量；
读取次数与单次 tile 均不变，因此**逻辑请求字节数**前后相同，收益只来自并发命令不再串行。注意这是
静态口径：**实际 GM 流量不由此推定**，要声称 HBM/L2 侧流量不变须另有测量证据，不得以逻辑字节数
相同代替。**已在交付算子上双向实测**（共享单份 ↔ 按读者复制，以及副本数的剂量响应），具体数值
与测试条件不在本卡归档，采用时按自身算子实测；建议以隔离对照臂（仅改副本数、其余不变）归因收益，
不与其它优化合并报告。

验证方法：以单副本版本的输出做 bitwise 比对——表是只读的、各副本内容相同，改动只涉及读地址，
输出必须逐位一致，这是本方法最强的正确性判据；不通过即说明副本索引算错，性能数据不必再看。
覆盖副本数退化为 1、副本数小于读者数（`%` 回绕共享）与等于读者数三种配置。

归因时注意三点：

- **耗时与单次搬运量不成比例**才指向争用；成比例则是带宽或搬运形状问题，本方法无效。剂量曲线
  （只扫副本数）是唯一能把争用单独隔离出来的手段，因为它不改变读取次数与单次 tile，逻辑请求
  字节数恒定。
- **单核不作为判据**：单核跑不存在并发争用，单核探针既无法观测也无法否证本方法——本卡对应的改动
  早期曾被一次单核测量误判为无效。
- **per-pipe 计数器会整轮漂移**：同一配置重复测量时 `aiv_mte2` 可差出一成以上，个别轮次甚至出现
  pipe 忙时大于 `Task Duration`。结论一律以端到端时间为准，pipe 列只作方向性参考。频率不锁定时
  端到端也有数十个百分点的波动，小于该波动的差异无法归因，须锁频后再比对。锁频也**不替代配对
  采样**：两臂交替多次采样、按配对统计判定，不得以任一单次样本（含最快一次）作为验收结论。

## 技术限制与风险

- **显存开销**为 `表大小 × 副本数`，线性增长；host 侧构造成本同比增长。复制是否抬高实际 GM 流量
  须实测，表大到实测流量成为新瓶颈时本方法反向有害。
- 只适用于**纯只读**数据；表若在 kernel 内被写，多副本破坏一致性。
- 副本数写死会与运行时核数脱节。从张量形状反推（如上）可让 kernel 不感知副本数，但 host 侧必须
  保证副本数合理，或用 `%` 回绕兜底。
- 各副本内容相同，host 侧构造成本也乘以副本数；表很小时可忽略，但仍属 launch 前开销。
- 本方法消除的是**并发命令落在同一片地址区域造成的串行**，不改善搬运形状。若耗时主要来自跨步
  短突发，或来自读取与消费者之间缺少重叠，复制副本无效。
- **错开量必须达到单次搬运的地址足迹**。按表整体大小复制天然满足；若为省显存而改用更细的错开
  方式（例如只错开几个 sector），本卡的实测结果是**无效**，不要假定任意错开都管用。
- 与 `mem-03` 的边界：本卡处理的是**多个读者同时落在同一片地址上互相阻塞**，表很小、反复被读；
  `mem-03` 处理的是**一次性大块流式读挤占 L2**。两者诊断特征相反（前者搬运量小而耗时高，后者
  搬运量大），手段也相反（复制 vs 绕过），不要互相冒充收益。

## 参考资料

- PyPTO 仓库：`pl.load` 的多维 offset 为绝对元素坐标，见 `docs/zh/api/pro_api/SIMD-API/memory_data_movement/load.md`。
- 读者 id 的取值前提：`pl.get_subblock_num()` 的返回值取决于 kernel 是否同时含 cube 与 vector section（纯 vector kernel 下恒为 1、`get_subblock_idx()` 恒为 0），见本技能 `references/api/support.md` 第 5 节；按 id 分副本的映射依赖这一事实。
- 相邻现象：多个 block 向邻近 GM 地址**写**标量的丢写观测见 `references/api/support.md` 第 7 节。那是写侧正确性问题且机制未定论，与本卡的读侧串行是两件事，不可互推。
