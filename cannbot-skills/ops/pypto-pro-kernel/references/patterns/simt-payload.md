# SIMT payloads: transport units and record ownership

Use for routing, indirect reads, sampling and packing where several contiguous elements share coordinates, weights, indices or a destination. First run the [element-per-thread direct-GM baseline](simt-first.md), then compare mappings. Even a simple copy can dominate time; use [native-task decomposition](../verification/native-timing.md) to locate the worthwhile change.

## Derive ownership

For `T` threads per block, choose a logical group width `G` with `T % G == 0`. `G` need not equal a hardware warp width. Groups own records and lanes own contiguous elements:

```text
lane = thread_id % G
groups_per_block = T // G
record_start = block_id * groups_per_block + thread_id // G
record_step = grid_blocks * groups_per_block
record = record_start, record_start + record_step, ...
element = lane, lane + G, ...
```

These quotient/remainder mappings give each valid `(record, element)` one writer. Read metadata only for valid records; bound the element loop by the true width. Cover record counts beyond one grid and tail widths. Assign separate unique writers to compact per-record outputs such as indices or counts.

Define the independent unit before flattening: it may be a scalar, a tuple of adjacent elements with coupled outputs, or a transport word. One unit per thread preserves work shared within that unit. In the grouped mapping, `G=1` instead makes each thread traverse an entire record serially; it is not the flat control. Name comparisons by their actual ownership and loops.

Hoist only element-independent reads, address calculations and computation outside each thread's element loop. Each lane can compute metadata once and reuse it; lane 0's local scalar is not automatically visible to other lanes. No shared UB or barrier is needed without cross-thread communication. A whole record per thread is also a candidate, but addresses across threads may become widely strided: logical reuse does not guarantee coalescing.

## Analyze one memory instruction across lanes

List the addresses issued by adjacent lanes at the same load/store instruction. A serial contiguous loop within one thread can still issue strided addresses across a warp. Conversely, grid-stride iterations can be far apart for an individual thread while adjacent lanes coalesce each iteration. Analyze input and output separately: a transpose can make one contiguous and the other strided. Prioritize actual traffic and frequency when both cannot be contiguous together; a byte ratio for one isolated scalar load does not establish whole-kernel bandwidth efficiency.

UB staging can move an irregular GM permutation into on-chip reads, at the cost of a tile, barriers and additional accesses. Once GM requests are contiguous, inspect UB bank/subbank conflicts separately. The [Ascend 950 example](https://gitcode.com/cann/cannbot-knowledge/blob/01b5bf44246aa6f2ac04e4ee6dfe107bf30c2095/knowledge/ops/ascendc/guides/operator_practice/simt_operator_optimization/memory_access/avoid_ub_bank_conflict_simt.md) compares FP32 32x32 and 32x34 tiles; this is a scoped pitch experiment, not a universal `+1` or `+2` padding law. Derive the target mapping for the actual element/access width and validate with counters or matched full calls. See [SIMT memory observations](../diagnostics/performance.md#simt-memory-paths-and-cache-evidence) for evidence limits.

The native [tiled transpose](../../examples/algorithms/simt_tiled_transpose/) supplies this shared-UB composition with independent bit-pattern checks and configurable pitch. Pro's Tile declaration alignment still applies: a 32x34 FP32 ND Tile has a nonaligned row stride and is rejected in the current source. This example allocates an aligned `[1, 32*pitch]` physical Tile and explicitly addresses `row*pitch+col`, keeping allocation span and logical pitch separate. It uses a block-uniform outer tile loop and unconditional barriers inside each SIMT invocation; it does not place a barrier inside a thread-dependent traversal. Its contiguous input contract differs from [explicit physical-stride addressing](../../examples/algorithms/strided_transpose/).

## Keep a reused table only within a proved lifetime

Compare default GM reads with per-worker UB residency when many consumers reuse a compact table. Each worker pays its own staging cost and holds its own copy; fewer logical GM reads do not establish fewer HBM transactions because the direct control can hit Data Cache. Count table padding and all overlapping live buffers against the [mixed-kernel budget](../api/memory-limits.md), including SIMT's dynamic reservation. Retain a direct-GM path when the whole table does not fit; do not allocate a nominally small logical view over a larger physical span. Small consumer counts and already hot addresses are rejection controls for staging.

There are two native producers. SIMT threads can cooperatively initialize a shared Tile and reach an unconditional `pl.simt.syncthreads()` before consuming it; every thread must reach the barrier, including threads with no output. Alternatively, an outer `pl.load` can fill the Tile through MTE2 before a SIMT consumer, using explicit paired `pl.system.sync_src` / `sync_dst` with `set_pipe=MTE2, wait_pipe=V`. The [SIMT math kernel](../../examples/basic_api/simt/simt_math/kernel.py) supplies that handover. A thread barrier does not order an outstanding MTE transfer. For manually allocated bare Tiles and explicit events, select `@pl.jit(auto_mutex=False)`; use the documented Tile-group mechanism for automatic ownership instead of assuming a plain Tile receives automatic ordering.

Cache a compiled factory by metadata, not table values or a tensor address. Refill the resident Tile from the current runtime table on every invocation. Verify changed values at the same GM pointer, poisoned output, tails, dispersed/high-reuse keys and the large-table fallback. Repeated profiler calls on the same buffers describe that reuse regime; without controlled cache state or transaction counters they do not establish cold-HBM performance. [Cache-policy availability and evidence](../diagnostics/performance.md#simt-memory-paths-and-cache-evidence) remain separate from explicit UB residency.

## Separate an irregular selector from a contiguous payload

An irregular row selector does not make every element of that row an irregular transfer. For whole-row copies, compare the scalar SIMT control with a device-side scalar read of `indices[row]` followed by native `pl.load` / `pl.store` of the selected row. On source `c46548eac0ce40350a5d19293368552c2fae3dc5`, the Python scalar-subscript parser lowers integer Tensor indexing to `getval`; C++ `MakeGetValCodegenCCE` permits that Tensor read outside a VF and emits a GM scalar dereference. Outside SIMT, INT32 getval widens to INT64. This is outer `@pl.jit` device code, not Python Host readback and not an arbitrary scalar operation inside a Vector VF. Recheck the installed source and a focused probe after upgrades.

The native [indexed-row copy](../../examples/basic_api/datamove/indexed_rows/) shows a worker-stride row loop, aligned physical `[1,padded_columns]` Tile, actual `[1,columns]` validshape, and a depth-one Tile group under `auto_mutex=True`. The group orders MTE2→MTE3 and reuse across rows; these dependencies remain necessary with a single slot. It keeps the original FP32 bits, including signed zero and subnormal values. For a later SIMT arithmetic consumer, establish its MTE/V handover separately; a pure copy needs no SIMT launch.

Long contiguous records can amortize scalar selection and MTE setup; short records can favor SIMT or grouped ownership. Compare both at fixed workers, preserving valid indices, input/output disjointness, odd widths and fresh inputs. A whole-row Tile that no longer fits requires a separately verified chunked implementation. Per-element gathers with unrelated column indices, numerical transforms and overlapping copies are different contracts; this recipe does not cover them.

Compare bytes per selected row together with rows assigned to each worker. The depth-one MTE implementation issues a device scalar selection and dependent transfers in its worker-stride row loop; SIMT can distribute elements from many rows across its threads. A single narrow row and many narrow rows can therefore rank differently, even at fixed workers. A small total row count is not by itself a reason to reject MTE, and a large total output is not by itself a reason to select it. Include a few-row wide-payload control and a many-row narrow-payload control alongside the main workload, then recheck the intended worker count.

Keep the direct-SIMT control when selecting an MTE path. Establish any metadata dispatch boundary using neighboring row counts and widths, odd-width tails, changed inputs and both call orders; a crossover observed at one worker count or reuse regime does not define a portable cutoff. For very short calls, report absolute native-task microseconds as well as ratios so the size of a regression remains visible. If the available measurements do not support a stable boundary, retain explicit alternatives and leave performance undecided rather than installing a default threshold.

## Use wider words for pure transport

When a phase only copies contiguous bytes, its numerical element type need not be its transfer unit. A native `pl.make_tensor(..., dtype=...)` view can group adjacent short elements into one integer word for SIMT load/store. This changes address/count units, not values; `simt.cast` is a numerical conversion and is not a substitute. Keep arithmetic consumers in their original dtype.

Before testing a wider carrier, prove base alignment, row/panel byte pitch, whole-word extent and unique output ownership. Express the view's shape, stride and loop bounds in carrier elements, preserving the original byte span and record selector. Do not round a partial word up into padding or another record; use a narrower path or separately owned tail when the contract permits it. A contiguous tensor can have a misaligned storage offset, so contiguity alone does not prove alignment. Input/output overlap needs its own ordering proof.

The [indexed word-view probe](../../examples/basic_api/datamove/strided_view/kernel.py) uses ordinary native kernels and tests FP16/BF16 storage through 32/64-bit integer views. Its tests compare original 16-bit patterns, including NaN payloads, signed zero, repeated indices, aligned offset bases and guards; they do not reproduce the carrier's grouping as the reference. Official `make_tensor` docs, Python/C++ declarations and these probes agree on behavior `75a6c2600` / CANN 9.2.0. Fewer address calculations and scalar memory operations can matter even when bytes moved are unchanged; this is not a universal speed guarantee.

## Compare flat and grouped mappings

Retain both a flat unit mapping and a cooperative record mapping, even when starting from grouped code. Grouping can reduce metadata work from roughly `width` to `G` operations per record, but its contiguous access span, active records and tail-lane waste also change. The flat control may repeat more metadata yet win through coalescing or more independent memory operations. Narrow payloads and `G > width` can waste lanes; small `G` can increase scattered accesses.

Make `T/G` explicit factory/cache parameters whose offsets and strides match the [actual launch](simt-first.md#launch-variants). At fixed workers, compare at least two legal `T` values for the flat control and a small grouped set spanning at least two `T` and two `G` values. Sweeping only `G` at the original `T` does not validate the grouped launch choice. Keep the same consumers and include the complete producer/consumer call when ranking the two mappings.

When changing carrier width, first hold launch geometry fixed to isolate that change, then retune both mappings in the new units. Losing at an old scalar path's thread count does not reject the flat carrier path. If its cost is still falling at a tested edge, follow that trend within budget before comparing the families' best configurations. The optimization workflow owns [screening](../workflows/optimization.md#screen-candidates-before-confirmation) and [neighborhood stopping conditions](../workflows/optimization.md#check-the-neighbors-of-a-winning-configuration).

## Workload and validation

Use the [data-dependent workload rules](../workflows/optimization.md#data-dependent-work): indexed reads need dispersed and high-reuse addresses; conditional payloads also need active, skipped and mixed records when those branches are contractual. Production Host handles metadata only; tests may report valid fractions, but Host must not inspect runtime tensors to select a configuration.

Validate tail widths, small and multi-grid record counts, worker counts, poisoned repeats and guards on the selected configuration. For pure transport, compare original payload bit patterns independently of the carrier grouping. Apply the workflow's [final confirmation](../workflows/optimization.md#exit-criteria); a locally faster group width or one cached workload does not establish a general mapping win.

Initialization is work too. Reducing pre-zeroing requires proving valid output ranges, fill ranges and order so every element has a writer; old caller values cannot supply correctness. For ordered categories, derive [stable positions](stable-placement.md) first and choose payload mapping separately. One block owning a category is not the same as a group cooperating on one record.

When a record produces both scatter and a payload-reduced small output, use [multiple-output ownership](multi-output-reductions.md) to separate final writers from reduction participants. Uniquely writing a statistic does not require that thread to read every channel serially; atomic outputs do not prevent per-record metadata reuse. Compare initialization fusion and partial/merge choices using their work domains and complete-call cost.

[Bilinear sampling](../../examples/algorithms/bilinear_sampling/) demonstrates shared coordinates and boundary decisions with cooperative channels. [RoPE and KV scatter](../../examples/algorithms/rope_kv_scatter/) demonstrates adjacent-element units and separate output-validity domains. Their headers and independent references define tested shapes, locality regimes and configuration limits; their defaults are not universal launch rules.

## Indexed operands feeding Cube

The [materialized indexed contraction](../../examples/algorithms/indexed_batched_gemm/kernel.py) gathers a GM panel and then runs Cube on the same Stream. Its gather and product can use independent grids. The [on-chip alternative](../../examples/algorithms/indexed_batched_gemm_onchip/kernel.py) couples a SIMT producer to each Cube work item. Establish whether the panel is internal scratch before removing its write; an observable panel remains part of the contract.

Count selection and format work at the new ownership frequency. In the on-chip example, a work item owns one `(batch, M tile, N tile)`, so gathering and ND-to-NZ preparation repeat for every M tile. The materialized control gathers once and uses regular MTE loads of that panel for its product tiles. Removing an intermediate allocation or a launch does not establish lower complete-call latency or lower HBM traffic. Compare few and many M tiles, reused and dispersed selectors, and startup/tail cases; retain the verified split path where it wins.

Match the actual AIC/AIV budget, not just the numeric Host block argument. In the verified A5 composition, each mixed block uses one AIC and two AIVs; the two AIVs fill disjoint halves of one panel. The control can give its independent gather twice the product's block count to match that physical budget. Keep dtype, inputs, addresses and total contraction work equivalent, and count the exported native tasks for each complete call.

Budget all live panel slots and the A operand in Mat, plus conversion buffers and the SIMT reservation in Vec. Establish the serial handover first; a deeper ring changes memory use, slot lifetime and possibly transpose legality. The [group-transpose contract](../api/gemm.md#transpose-aliases-on-multi-slot-operands) owns that boundary. Read the native example when composing these stages; it supplies explicit addresses, bounded conversion tiles, both subblocks and matched worker ownership without another compiler layer. Complete-call profiler evidence decides whether an overlap experiment is useful.
