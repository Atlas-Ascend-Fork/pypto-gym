## 运行环境

复现运行的标准环境配置：

```bash
source ${ASCEND_HOME_PATH:-/usr/local/Ascend/cann}/set_env.sh
export TILE_FWK_DEVICE_ID=<空闲设备号>   # 单卡运行，指定设备
```

- **设备占用重试**：运行报 `F71008 MAP_REG_ADDR_FAILED`（"maybe others are using current device"）时，说明设备被其他任务占用，与复现问题本身无关。换一个设备号重试，或稍后重跑，直至取得无干扰的干净结果。受干扰的运行日志保留，但在日志中标注"设备占用干扰，已重试"。
- **环境信息留档**：首次运行前采集一次环境快照（CANN 版本、pypto 版本与 commit、Python 版本、torch / torch_npu 版本、硬件型号），保存为 `env_info.log`。采集命令如下，任一命令失败则对应字段记为 `Unknown`，不影响复现：

  ```bash
  {
    npu=$(lspci -n -D 2>/dev/null | grep -oE '19e5:d80[23]' | head -1 | sed 's/19e5:d802/Ascend 910B/; s/19e5:d803/Ascend 910C/' || true)
    cann=$(echo "${ASCEND_HOME_PATH:-}" | grep -oP 'cann-\K[\d.]+' || true)
    py=$(command -v python || command -v python3 || true)
    echo "服务器/NPU 型号: ${npu:-Unknown}"
    echo "CANN 版本: ${cann:-Unknown}"
    echo "PyPTO 版本/Commit: $(git rev-parse --short HEAD 2>/dev/null || echo Unknown) $(git log -1 --format='%ci' 2>/dev/null)"
    echo "Python 版本: $("$py" --version 2>&1 || echo Unknown)"
    echo "torch 版本: $("$py" -c 'import torch; print(torch.__version__)' 2>/dev/null || echo Unknown)"
    echo "torch_npu 版本: $("$py" -c 'import torch_npu; print(torch_npu.__version__)' 2>/dev/null || echo Unknown)"
    echo "操作系统: $(grep '^PRETTY_NAME=' /etc/os-release 2>/dev/null | cut -d= -f2- | tr -d '\"' || echo Unknown)"
  } > env_info.log
  ```

- **不改动原始目录**：复现所需的资产（历史探针脚本、数据文件）拷贝到 issue 目录下使用，禁止在原运行目录内修改或新增文件。

## 复现脚本要求

- **最小化**：脚本只保留触发问题所必需的部分，去除与问题无关的算子逻辑。能在 host 侧复现的（编译报错、lint 拦截、脚本行为）不要求设备运行。
- **可重复执行**：脚本无交互输入，一次执行产出明确的成功/失败信号。
- **对照组**：条件允许时同时提供"触发问题的写法"与"正常写法"两组，证明问题由目标因素而非环境引起。
- **文档对照型问题**：文档缺失、文档与实现不一致类问题，复现脚本可以是 grep / find / 运行产物比对等静态核查命令序列，同样要求可重复执行、输出可存档。
- **报错行为类实跑优先**：声称"触发某错误码/某报错消息"的问题（E1-E4 及一切报错行为声称）不属于文档对照型，必须编写实跑脚本并在当前环境实际触发至少一次。静态代码证据只能支持"机制存在"，不能替代实跑触发；实跑触发不出目标报错时，按实际结果降级为 ⚠️（写明实际触发的错误码与消息）或 ❌。
- **无脚本不写入**：提单文本中每个报错点/子现象都必须有对应的可执行复现脚本或静态核查命令序列随包存档。确实无法构造脚本的报错点，不得作为已确认现象写入 issue，只能显式标注"session 观察，未独立复现"并从现象计数中剔除。

## 运行与日志收集

- 每次运行将完整 stdout 与 stderr 落盘为独立日志文件，命名格式 `run_<场景>.log`，禁止只记录结论不留日志。
- 多次尝试（设备重试、参数变体）在同一日志内按 attempt 分段标注。
- 日志中使用的命令（含完整参数与工作目录）记录在复现文档的"复现步骤"一节，保证他人可按步骤重跑。

## 复现状态分档

| 状态 | 含义 | 要求 |
|------|------|------|
| ✅ 复现 | 问题现象在复现环境完整重现，关键报错或行为与历史记录逐字或等价一致 | 给出日志原文对照，标注与历史记录的一致点与差异点 |
| ⚠️ 部分确认 | 问题的部分子现象复现，其余子现象未复现或无法验证 | 逐个子现象分别标注 ✅ / ⚠️ / ❌，未复现部分必须给出差异归因线索 |
| ❌ 未复现 | 问题现象在复现环境不出现 | 必须记录环境差异（pypto 构建版本、CANN 版本、硬件型号）作为归因线索，并给出下一步建议（如用同期构建做 A/B 回归） |

未复现与部分确认的归因线索至少包含：复现环境与原 run 环境的 pypto 构建版本差异、硬件型号差异、问题本身是 host 侧还是设备侧行为（host 侧行为与硬件无关，未复现更可能指向版本差异）。

**分档粒度是报错点/子现象，不是 issue**：含多个子现象的问题必须逐子现象分档并记入台账表（模板见 `templates/repro-readme-template.md` 的"子现象台账"），issue 级状态由台账汇总得出。仅有静态代码证据支持的报错点，判定栏标"静态确认，未实跑触发"，不计入 ✅ 数量。

**实跑保鲜**：报错行为类问题的实跑取证必须在与提单相同的环境快照下完成。复现环境与 session 发生时的环境（CANN/pypto 版本）不一致时，禁止引用 session 时期的报错观察值作为现象描述——必须以当前环境实跑结果为准重新定性，包括把声称的错误码改写为实际触发的错误码。

## 报错信息类问题的日志判定（AI 语义判定，禁止关键字判定）

**适用范围**：E1-E4（报错缺失 / 模糊 / 误导 / 无建议）以及任何核心问题是"日志或报错是否提供了足够信息"的候选问题，例如错误码可读性、日志打印质量、异常消息是否含定位要素。

- **禁止用关键字匹配判定日志质量**。"是否提供了报错信息和解决方案"是语义判断，不是字符串匹配：消息里出现 `File` 字样不代表给出了有用的源码位置；出现 `use` / `please` 不代表给出了可执行的修复建议；反之，一条没有任何"建议关键词"的消息可能已经把根因和修法说清楚了。用 grep 关键字命中率做质量定性大概率误判，判出的 ✅/❌ 不可信。
- **判定方法**：写完复现脚本并取得日志后，由 AI 完整阅读日志原文，逐条对照下述 rubric 做语义判定。每个检查项必须给出"日志原文引证 + 一句话理由"，不允许只给结论。

| 检查项 | 判定问题（rubric） | 判定要点 |
|--------|---------------------|----------|
| (a) 根因可读描述 | 不了解编译器内部的开发者，能否只凭这条消息知道"发生了什么、为什么错"？ | 含具体数值 / 对象名但不解释含义记 ⚠️ 部分；只有码值或内部枚举记 ❌ |
| (b) 源码位置 | 消息能否定位到**用户自己代码**的文件与行号？ | 只给编译器内部函数名、内部 tensor id、PASS 名记 ❌；给 Python caller frame 记 ✅ |
| (c) 修复建议 | 消息是否给出可执行的下一步（改用哪个 API、调哪个参数、看哪篇文档）？ | 暗示方向但无可执行动作记 ⚠️；完全无指引记 ❌ |

- 判定结果按三档记录：✅ 具备 / ⚠️ 部分具备（写明缺什么）/ ❌ 不具备，与复现状态分档口径一致。
- **关键字的合法用途**：仅限"证据可回查性自检"——确认文档引用的日志行真实存在（`grep -n` 命中），不参与上述质量定性。

## 上游核对

凡涉及"文档缺失""报错看不懂""示例无效"的问题，下结论前必须核对上游最新状态，避免把"上游已修复"或"上游已写文档"的问题按旧定性提单。核对覆盖两个来源：

1. **pypto 源码仓最新 commit**：核对**以远端 master 为准**，不以本机克隆为准（本机克隆可能陈旧，单看本地 `HEAD` 会误判）。标准渠道按优先级：
   - `git ls-remote <remote> master` 或 GitCode API 查询远端 HEAD；
   - 或先 `git fetch`（只读）再 `git log origin/master`。
   确认远端 HEAD 后，检查相关报错文案、检查逻辑、生成逻辑在远端 master 上的现状，定位相关提交（`git log --oneline origin/master -- <路径>`）。
2. **benchmark 运行时下载的文档快照**：benchmark 通过 `sync_devkit.py` 机制在跑测时拉取上游 master 文档快照，缓存在 `$PYPTO_DEVKIT_DIR`（未设置时为 `/root/.cache/pypto-devkit/`）。核对缓存中的 `MANIFEST.json` 确认快照版本（以其 `download@<commit>` 为准），并在快照内检索问题相关内容。

核对结论分三种结局，必须明确归类：

| 结局 | 含义 | 提单口径 |
|------|------|----------|
| ① 上游已解决 | 最新代码或文档已覆盖该问题 | 不再提单，或改提"工具链未跟上上游"的问题 |
| ② 上游至今没写 | 最新 master 上问题原样存在 | 按原定性提单，注明核对的 commit 哈希 |
| ③ 内容有了但索引失效 | 上游内容存在，但本地索引路径、链接随上游目录迁移失效（如 404） | 问题定性从"内容缺失"修正为"索引失效"，修复落在索引侧 |

核对结果连同核对日期、commit 哈希写入复现文档的"上游核对"一节。措辞要求：写明"远端 master HEAD `<commit>`（核对日期）"，禁止只写"仓 HEAD"这类渠道不明的表述。核对发现原定性被推翻时，必须显式记录定性修正过程（原定性 → 新定性 → 依据），不允许静默改结论。

## 根因定位与证据标准

- **根因定位到具体位置**：每个问题的根因必须定位到具体文件与行号，格式 `path:line`（如 `framework/src/machine/runtime/runner/device_error_tracking.cpp:177-182`）。只写模块名不写行号的定位不合格。
- **证据使用原文**：报错、拦截文案、文档条款均逐字引用，标注来源（日志文件名或 `path:line`）。关键日志行可附加注释，但不得改写原文。
- **证据链完整**：一个确认结论至少包含"现象证据（日志原文）+ 根因证据（源码位置）"两类；文档类问题为"文档原文（`path:line`）+ 核查记录（grep / 实跑日志）"。
- **与历史断言对照**：复现结论必须与断裂点报告中的原始断言逐条对照，一致点与差异点分别说明；差异连同可能原因（构建版本、硬件）如实记录。
- **证据可回查性自检（交付前必做）**：
  1. README 中每一处 `日志文件:行号` 引用，用 `sed -n '<行号>p' <文件>` 核对内容与引用描述一致；
  2. 每一处"日志中含 X"的断言，用 `grep -n 'X' <文件>` 核对至少一次命中；
  3. 每一处证据文件引用，确认文件非空（`wc -l` 大于标题行数）；
  4. 自检结果写入汇总报告过程备注；任一不命中必须先修正再交付。

## 输出目录约定

阶段②的产物按问题组织在 `issues/issue-XX/` 目录下（XX 从 01 开始顺序编号）：

```
issues/
├── issue-01/
│   ├── README.md            # 问题定位文档（模板见 templates/repro-readme-template.md）
│   ├── env_info.log         # 环境快照
│   ├── repro_<场景>.py      # 最小复现脚本（可有多个）
│   ├── run_<场景>.log       # 运行日志（可有多个）
│   └── evidence_<场景>.log  # 静态核查证据（grep / find 记录等）
├── issue-02/
└── ...
```

汇总报告（如 `issue_conform.md`）在 `issues/` 的上一级，包含总表（编号、问题指向、仓分类、复现状态、提单建议、复现目录链接）、逐问题说明、仓分类统计与过程备注。汇总报告引用各 issue 目录的相对路径，不重复粘贴证据原文。交付前执行 `references/writing-style.md` 的"交付前检查"（禁用词扫描 + "陌生同事"可读性自检），检查结果写入过程备注。
