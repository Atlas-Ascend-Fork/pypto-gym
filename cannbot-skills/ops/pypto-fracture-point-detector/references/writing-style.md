# 文档写作规范

本规范适用于本 skill 产出的全部文档：断裂点报告、复现定位文档、issue 报告、汇总报告。skill 自身的文本同样遵守本规范，作为样板。

## 规范条款

### 1. 术语统一

关键术语在全部产出文档中口径一致：同一概念只用一个词，中文术语不随意改写，英文技术词保持原文，首次出现时给出定义。

本 skill 的固定术语表：

| 术语 | 定义 | 禁用写法 |
|------|------|----------|
| 断裂点 | session 中因框架、文档或工具链不完善导致的失败、重试或低效问题点 | 断点、卡点、坑 |
| 复现状态 | 问题在复现环境的确认程度，分 ✅ 复现、⚠️ 部分确认、❌ 未复现三档 | 复现成功、大概复现了 |
| 仓分类 | 按修复问题需要改动哪个仓库的代码划分修复方（pypto / pypto-gym / benchmark） | 归属仓、责任仓 |
| 作弊检查 | 检查 agent 是否直接抄袭现成同算子实现的检测步骤 | 抄袭检测、查重 |
| 上游核对 | 对照上游 pypto 仓最新代码与文档确认问题现状的步骤 | 查最新文档、看看上游 |

- ❌ 反例：前文写"断裂点"，后文写"这个坑"；同一文档中"复现成功""复现通过""确认复现"三种写法并存。
- ✅ 正例：全文统一使用"断裂点"；复现结论一律使用三档术语之一。

### 2. 书面技术语言

使用完整的书面句式，主谓宾齐全；技术判断给出依据，不使用口语化表达。

- ❌ 反例："这个报错看不懂，agent 试了好几次都不行，挺坑的。"
- ✅ 正例："报错信息仅包含错误码 `507018`，未携带算子名、源码位置与修复建议，agent 无法据此定位问题，连续三次尝试均失败。"

允许保留的表达方式：结论先行、短句收尾、必要的强调（加粗）。禁止的表达方式：语气词、网络用语、拟声拟态描述、无依据的情绪化评价。

### 3. 单点表述

一条信息只在一个位置完整表述，其他位置引用该位置。

- ❌ 反例：摘要里写一遍环境问题，详情里原样再写一遍，附录里再抄一遍。
- ✅ 正例：环境信息只在"环境信息"一节完整列出；其他章节写作"环境同第 2 节"或直接引用 `env_info.log`。

### 4. 标题含场景与指向

标题必须包含问题发生的场景与能力归属，使读者不读正文即可区分该问题指向什么。

- ❌ 反例："问题描述""复现结果""错误码问题"
- ✅ 正例："OL13 与编排手册的测试文件生成时序冲突""F21009 编译报错缺少算子定位与修复建议"

断裂点详情标题沿用 `{类型码}-{类型名}: {实体}` 格式，问题描述一节概括具体场景，二者结合满足本条要求。

### 5. 删除冗余成分

删除不改变语义的修饰语与重复定语，一个限定词只保留一处。

- ❌ 反例："agent 在实际的运行过程当中遇到的这个问题其实本质上是一个文档缺失的问题。"
- ✅ 正例："该问题的根因是文档缺失。"

### 6. 结构紧凑

文档层级不超过四级（`####`）；同一层级内的段落围绕同一主题；相邻段落之间有明确的逻辑关系（因果、对照、递进），不以单句段落连续堆叠。

- ❌ 反例：连续五个单句小节，每节一句话，互相之间无过渡也无归类。
- ✅ 正例：相关现象归入同一小节按条列出；结论与依据分属"结论""证据"两节，通过编号互相引用。

### 7. 读者导向（提单文档可读性）

issue 文档与复现定位文档的读者是**不了解 session 上下文的仓维护者**。写作时按"把文档交给一个只懂业务、不了解本次分析过程的同事，他能否一次读懂"自检。除前 6 条外还须遵守：

- **结论先行**：每篇文档、每个问题小节的开头用一句话交代"什么场景下、做什么操作、出了什么现象、造成什么影响"，然后再展开细节。读者读第一句就应知道这篇在说什么。
- **内部标识必须翻译**：错误码、枚举名、编译器内部函数名、内部 tensor id 等首次出现时，必须紧跟一句对普通开发者可懂的解释，之后才可直接使用。禁止把裸标识丢给读者自行猜义。
  - ❌ 反例："触发 `F4FFFF (PASS_INNER_ERROR)`，ExpandFunction 失败。"
  - ✅ 正例："触发错误码 F4FFFF（编译器内部 pass 执行失败的通用兜底码，不指向具体原因）；本次失败点在 ExpandFunction 这个编译 pass 处理 permute 算子时。"
- **证据导读**：日志与代码片段只摘录关键行，逐行或逐段配一句"这一行说明 …"的导读；禁止整段无注释堆砌原文。读者应能不读全文、只看导读就理解证据链。
- **复现步骤可照做**：按编号列出，命令可整段复制执行，每步附一句"这一步在做什么"。步骤中引用的脚本必须写清文件位置。
- **具体化**：用数字、路径、行号代替"很多、经常、大概"类模糊词（如"6/11 算子踩过"而非"很多算子踩过"）。
- **为判断给理由**：所有 ✅ / ⚠️ / ❌ 类定性结论，紧跟一句话说明凭什么这样判，让读者能复核而不必重读日志。

## 适用范围说明

- 证据引用（日志原文、session 原文）不受第 2、5 条约束：证据必须逐字引用，不得改写。
- 报告模板中的占位符与字段名不受本规范约束，但填充内容必须遵守。

## 交付前检查

交付前对全部产物执行禁用词扫描，命中处逐条改写；证据原文引用豁免（见"适用范围说明"）。

```bash
grep -rn -E '坑|卡点|卡死|迷茫|搞定|折腾' issues/ *.md
grep -rn -P '断点(?!裂)' issues/ *.md   # 排除术语"断裂点"本身
```

词表以第 1 条术语表"禁用写法"列为准维护。检查结果写入汇总报告过程备注；任一命中未处理不得交付。

### "陌生同事"自检（可读性，交付前必做）

禁用词扫描只能管住措辞，管不住"读不读得懂"。交付前还须对每篇 issue 文档与复现定位文档执行第 7 条的自检——把文档假想为交给一个只懂业务、完全不了解本次分析过程的同事，逐项回答以下问题，任一答案为"否"则先改写再交付：

| # | 自检问题 | 对应条款 |
|---|----------|----------|
| 1 | 只读每篇文档和每个问题小节的第一句话，能否说出"什么场景、什么操作、什么现象、什么影响"？ | 结论先行 |
| 2 | 文中每个错误码 / 枚举名 / 内部函数名 / 内部 id 的首次出现处，是否都紧跟了一句人话解释？ | 内部标识必须翻译 |
| 3 | 不读日志原文、只看每段证据的导读句，能否理解整条证据链？ | 证据导读 |
| 4 | 把"复现步骤"整段复制出来，能否不问任何人直接照做跑通？ | 复现步骤可照做 |
| 5 | 全文是否还有"很多、经常、大概"这类可用数字 / 路径 / 行号替代的模糊词？ | 具体化 |
| 6 | 每一处 ✅ / ⚠️ / ❌ 定性结论旁，是否都有一句判定理由可供复核？ | 为判断给理由 |

自检方式：逐篇通读产物并逐项核对，6 项结果（通过 / 改写处摘要）写入汇总报告过程备注，与禁用词扫描结果并列。
