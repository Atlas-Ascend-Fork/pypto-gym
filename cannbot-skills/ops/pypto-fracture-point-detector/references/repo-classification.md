# 仓分类规则

仓分类回答一个问题：修复该问题需要改动哪个仓库的代码。分类结果决定 issue 提交对象与修复责任方，是复现阶段对每个问题的必做判定。

## 三个修复方

| 修复方 | 范围 | 典型修复内容 |
|--------|------|--------------|
| **pypto** | 框架本体：编译器、运行时、自带工具、官方文档 | 报错文案改进、错误码回填、API 行为修正、官方文档补写、自带分析脚本（如 `pypto/tools/` 下的工具）修复 |
| **pypto-gym** | agent 工具链：lint 门禁、命令守卫、技能文档、错误码索引、分析脚本 | lint 规则判定逻辑、守卫拦截逻辑、SKILL.md 与 references 文档、错误码索引条目、gym 侧脚本 |
| **benchmark** | 测试运行器：判定逻辑、prompt、流程配置 | 达标判定口径、任务说明文案、运行流程配置 |

## 判定方法

按以下顺序判定：

1. **定位修复点**：根据复现阶段的根因定位（`path:line`），确定修复需要修改的文件属于哪个仓库。注意 pypto 自带工具位于 pypto 仓（如 `pypto/tools/profiling/draw_swim_lane.py`），不要因它在 agent 流程中被使用而误判为 pypto-gym。
2. **主附带拆分**：问题的完整修复涉及多个仓库时，按"缺了哪一处修复问题就不算解决"确定主责仓，其余记为附带。格式：`X 为主（Y 附带）`。
3. **上游核对修正**：上游核对（见 `references/reproduction.md`）可能改变分类。例如原判定"pypto 文档缺失"，核对后发现上游已写文档、是本地索引未跟上，则主责从 pypto 修正为 pypto-gym。

## 与断裂点根因归属的关系

阶段①的根因归属（PyPTO框架 / PyPTO文档 / PyPTO样例 / Agent框架 / 模型能力）回答"问题是谁造成的"，仓分类回答"修复要改谁的代码"。二者维度不同，不做机械映射：

- "PyPTO框架""PyPTO文档""PyPTO样例"通常对应 pypto 仓，但文档已在上游修复时主责转为 pypto-gym；
- "Agent框架"通常对应 pypto-gym 或 benchmark，需按修复点进一步区分；
- "模型能力"不进入仓分类，也不进入复现阶段。

## 汇总统计要求

汇总报告必须包含仓分类统计：

- 总表为每个问题列出仓分类（含主附带）与具体修复位置；
- 统计表按修复方汇总主责数量与附带数量；
- 统计之后给出一句话结论，说明本批问题的修复重心在哪个仓。
