# Issue 报告生成规则

阶段③把复现确认的问题转化为可直接提交 GitCode 的 issue 文档。本文件规定断裂点类型到 issue 类型的映射、标题格式与字段填充规则。issue 的完整模板见 `templates/issue-report-template.md`，其字段结构遵循 GitCode `cann/pypto` 仓 ISSUE 处理规约的 5 类标准字段集（见下节），本 skill 只产出其中的 Bug Report / Documentation / Requirement 三类。

## 标题格式

所有 issue 标题遵循 GitCode `cann/pypto` 仓 ISSUE 处理规约：

```
[英文类型|中文类型]: 具体描述
```

仅允许 5 种前缀：

| 前缀 | issue 类型 |
|------|-----------|
| `[Bug-Report\|缺陷反馈]` | Bug Report |
| `[Requirement\|需求建议]` | Requirement（功能与改进需求） |
| `[Documentation\|文档反馈]` | Documentation |
| `[Question\|问题咨询]` | Question |
| `[Task\|任务跟踪]` | Task |

"具体描述"必须遵守 `references/writing-style.md` 第 4 条：包含场景与指向，能区分具体问题。示例：`[Bug-Report|缺陷反馈]: F21009 编译报错缺少算子定位与修复建议`。

## 标准字段集

GitCode `cann/pypto` 仓的 5 类 issue 及其必填字段（阶段③只用前三类）：

| issue 类型 | 触发场景 | 必填字段 | 选填字段 |
|------------|----------|----------|----------|
| Bug Report | 报错、异常、失败、精度问题 | 问题描述、环境信息、重现步骤、预期结果、日志/截图 | 备注 |
| Documentation | 文档缺失、文档错误、文档改进 | 文档链接、问题文档片段 | 存在的问题、修正建议 |
| Requirement（Feature Request） | 希望支持、新增功能、优化、扩展 | 背景信息、信息来源 | 价值/作用、设计方案 |
| Question | 如何使用、为什么、不理解 | 问题描述 | 已尝试的方法 |
| Task | 需要开发、计划、任务 | 任务描述、任务目标 | — |

字段名在 issue 文档中保持中英双语（如 `### Describe the current behavior / 问题描述`），填充内容使用中文。

## 断裂点类型 → issue 类型映射

| 断裂点类型 | issue 类型 | 说明 |
|------------|-----------|------|
| D1, D2, D5 | Documentation | 文档缺失、不完整、缺示例 |
| D3, D6 | Bug Report 或 Documentation | 文档与实现不一致：实现行为正确而文档写错 → Documentation；实现行为本身错误 → Bug Report |
| A1, A2, A4, A5 | Bug Report | API 缺失、行为异常、类型与边界问题 |
| A3 | Requirement | 合理参数组合不被支持，属能力扩展需求 |
| E1, E2, E3, E4 | Bug Report | 报错缺失、模糊、误导、无建议 |
| C1, C2, C4 | 按根因映射 | 行为模式类断裂点本身不是 issue 主题，其根因（某个 D/A/E 类问题）才是；映射到根因对应的类型 |
| C5, C6 | 按根因映射 | 同上；无明确根因时默认 Bug Report |

映射之后的类型再按仓分类确定提交对象：pypto 仓的问题提交 `cann/pypto`；pypto-gym 与 benchmark 的问题提交对应仓，标题格式不变。

## 字段填充规则

### Bug Report（必填：问题描述、环境信息、重现步骤、预期结果、日志）

| 字段 | 填充来源 |
|------|----------|
| 问题描述 | 断裂点报告的问题描述 + 复现阶段的定性修正（含上游核对结论），概括现象与根因 |
| 环境信息 | 复现阶段的 `env_info.log`，必填 NPU 型号、PyPTO 版本/Commit、CANN 版本、Python 版本、操作系统 |
| 重现步骤 | 复现阶段的复现脚本与命令序列，直接引用 `issues/issue-XX/` 下的脚本；步骤必须完整到他人可按步重跑 |
| 预期结果 | 断裂点报告中"期望行为"，按复现阶段核实后的口径修正 |
| 日志 / 截图 | 复现阶段的运行日志原文（关键片段），注明完整日志所在文件 |
| 备注 | 复现状态、与历史记录的差异、上游核对结论、仓分类附带项 |

### Documentation（必填：文档链接、问题文档片段）

| 字段 | 填充来源 |
|------|----------|
| 文档链接 | 问题文档的仓内路径（`path:line`）或在线文档地址 |
| 问题文档片段 | 文档原文逐字引用 |
| 存在的问题 | 缺失或错误的具体说明，含上游核对结局（① 已解决 / ② 至今没写 / ③ 索引失效） |
| 修正建议 | 复现阶段给出的修复方向 |

### Requirement（必填：背景信息、信息来源）

| 字段 | 填充来源 |
|------|----------|
| 背景信息 | 断裂点报告的问题描述 + 复现阶段的影响面数据（如多少 session 中招） |
| 信息来源 | 断裂点分析批次（session 来源、报告路径） |
| 价值/作用 | 修复后对 agent 效率或成功率的收益 |
| 设计方案 | 复现阶段给出的修复方向，可用伪代码 |

## 生成要求

- 每个确认的问题（复现状态 ✅ 或 ⚠️ 且建议提单）输出一份 issue 文档，保存为 `issues/issue-XX/issue.md`。
- ❌ 未复现的问题不生成 issue 文档，在汇总报告中说明原因与下一步建议（如 A/B 回归）。
- **报错点级门禁**：issue 文本中每个报错点/子现象必须映射到复现 README 台账中的非 ❌ 记录；❌ 子现象不得出现在现象清单中（可在备注说明"已排除及原因"）。
- **逐点 verdict 表必填**：含多个报错点/子现象的 issue，"问题描述"或"备注"中必须给出逐点 verdict 表（报错点 / 实测错误码 / 判定 ✅⚠️❌ / 证据文件），禁止只给 issue 级的一句"✅ 已复现"。
- **静态确认措辞规范**：仅有静态代码证据的报错点，在 verdict 表与正文中必须逐点标注"静态确认，未实跑触发"，不计入已复现数量；⚠️ 问题必须写明各子现象实测差异（含实际触发的错误码）与归因线索，禁止只写复现成功的部分。
- **无脚本不写入**：每个写入的报错点必须在"重现步骤"中给出对应脚本或静态核查命令；无法构造的标注"session 观察，未独立复现"并排除出现象计数。
- **提单前一致性关卡**：提交前执行三方比对（issue 文本 ↔ README 台账 ↔ 汇总/索引）+ 推翻项关键词 grep 清零自检，结果写入汇总报告过程备注（详见 SKILL.md 步骤 I2.5）。
- issue 文档的字段名保持模板中的中英双语格式（如 `### Describe the current behavior / 问题描述`），填充内容使用中文并遵守 `references/writing-style.md`。
- issue 文档只写提交所需内容；复现过程细节、证据全集保留在 `issues/issue-XX/README.md`，issue 文档中引用其相对路径。
