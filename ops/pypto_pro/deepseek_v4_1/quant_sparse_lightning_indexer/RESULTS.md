## 精度标准

**独立参考实现**：`tests/assets/quant_sparse_lightning_indexer_golden_cpu.py` 在 CPU 上独立解码 MXFP4 并按与 kernel 相同的舍入链计算——每字节低 4 位先于高 4 位、E2M1 幅值 `{0,0.5,1,1.5,2,3,4,6}` 配符号位、E8M0 指数 `字节值-127`、每 32 个连续逻辑元素共享一个 scale；QK 交接为 BF16，权重转 BF16，逐 head 融合乘加的每一步结果都舍入为 BF16。参考实现不读取设备输出，也不与 kernel 共享中间量。

**比较器**：`tests/assets/quant_sparse_lightning_indexer_precision.py`，固定阈值 `rtol = 1/128`、`atol = 2.5e-5`（`1/128` 对应 BF16 在 1 附近的相邻数间隔），由比较器模块常量固定，调用接口不接收自定义阈值。逐项检查：

1. 无效项：`indices == -1` 且（输出分数时）`values == -inf`；
2. 有效数量 == `min(topk, 允许集合大小)`；
3. 选中索引互不重复；
4. 选中索引先减去该行 `output_idx_offset`，再检查全部落在 `[0, 分数长度)` 且全部属于允许集合（候选块归属 + 可见性双重约束）；
5. 分数与参考实现在选中位置上一致（`rtol/atol`）；
6. TopK 边界：`min(选中分数) >= boundary - atol - rtol*|boundary|`，其中 `boundary` 为允许集合上第 `选中数量` 大的分数；`boundary` 为 `+inf` 时要求选中分数全为 `+inf`。

由于输出顺序不保证，比较器不逐位置对齐 CPU `topk` 的索引，而是检查输出集合、数量、对应分数和选择边界。若边界处有同分项，允许选择其中任意合法项。即使不返回分数，比较器仍会根据选中的索引查询 CPU 分数并检查 TopK 边界。`test_comparator_rejects_corruption` 对比较器自身提供负例验证。

**结果记录**：原文记录全量 **62/62 PASS（1010.6 s）**，本次未重跑该设备回归。当前 `--list` 仍列出 62 项，与该数量一致。性能脚本 `_cold_device_time` 每个场景、每种返回模式先运行 3 次预热，校验最后一次预热输出；随后采集图重放耗时，最后校验图中第一个和最后一个目标调用的输出。中间采样输出没有逐一校验，故这里不能表述为“每个性能样本都独立通过精度检查”。

## 性能结果

### 绝对性能结果

**环境与批次**：Ascend950PR_9589（32 Cube / 64 AIV，L2 = 128 MiB），CANN 9.3.0、PyPTO 0.2.1、PyTorch 2.12.0+cpu、torch_npu 2.12.0.post2、Python 3.12，device 0。下表数据采自内核源码 SHA256 `349f6aa6dddeec19d6a8ac3329b3926d44ea0e317bf6e69209f53a5738d29764`；本次核对的 kernel 文件 SHA256 `62503e2ca494678a2078e11662a67fff8ba70a1017ed0ed7763d5a15387126ca`。原文说明两者差异仅为文件头和模块 docstring；当前目录没有前一版本的原始采集附件，本次未独立重建这一历史比较。

**口径**：冷 L2 —— 一个 NPU Graph 内每次目标调用前先对 256 MiB FP32 缓冲区做 `ReduceSum` 驱逐 L2（脚本断言驱逐缓冲 > 上报 L2 容量，本机为 2.0×）；脚本将 profiler 的 native task（设备执行任务）按开始时间排序，要求同一 stream 上严格交替出现一个 `ReduceSum` 和一个目标 task，总数为 `2*repeats`；采集奇数位置目标 task 的 `Duration(us)`。其目标口径是**一次公开调用发射的全部 native task 耗时之和**；本实现每次调用恒定 1 个 task（`PYPTO_qsli_kernel`，`Type='PyPTO'`，32 MIX 块），故当前逐 task 与整次调用的设备耗时相同。若实现将来变为多个 task，现有脚本会报数量错误，需先调整采集逻辑。LI/LD 调度表在计时图之外生成一次，窗口内不含 AICPU task；host 侧校验、分配与启动开销均不计入。本表每个场景 × 每个返回模式保留原文的 **60 个样本**（3 轮 × 20 次），合并后取中位数；脚本单次 `--repeats 20` 仅采一轮 20 个样本，复现本表需要额外执行三轮并合并原始样本；表内 `范围` 为该 60 样本的 min–max。

### 理论评估对比（MFU / Bound / 利用率）

Bound 表示性能受哪个阶段或哪类资源限制；MFU（Model FLOPs Utilization）表示有效计算吞吐与所选硬件理论峰值之比；roofline 分析用计算量、数据流量及相应峰值估算耗时下界。三者含义不同，特别是 profiler 的 MAC pipe 时间占比不能直接代替 MFU。

**主要判断**：原有 profiler 快照与单记录/成对 DMA 对照共同支持：`typical` 的主要优化方向是 AIV 读取离散 PA K 记录的阶段，包括访问效率和 DMA 发射。源码也显示每 tile 每 AIV 要处理 32 条独立记录。该判断适用于记录中的场景；当前结构改动后的 pipe 快照尚未刷新，不能把旧版本占比直接当作当前性能分解。

按原输入 K/scale 的读取量计算，算术强度约为 `9.664 GFLOP / 80.22 MB = 120.5 FLOP/B`，这里还没有计入 GM 中转、键工作区、部分结果及输出流量。原文约 12% 的数字来自 `aic_mac_ratio=0.121`，应称为 MAC pipe 活跃时间占比。本文没有给出经过核实的当前 SKU、数据类型及频率下的 MXFP4 理论算力峰值，因此 **MFU 暂不计算**；保留有效吞吐与访存参照，避免把两种利用率混为一谈。

#### 分析过程

以下结合源码解释原有数据，区分可直接计算的量、历史对照记录和仍需验证的推断。

**第 1 步：核算点积工作量。** `typical` 为 72 行，每行 32 tile，共 2304 次 `matmul_mx`。每次完成 `32*512*128` 个乘加，按一次乘法和一次加法计 2 FLOP，总计约 9.664 GFLOP。除以 78.755 µs 得到 122.7 TFLOP/s，这是全芯片有效 QK 吞吐，不包含 head 归约和 TopK 的向量运算量。旧快照 `aic_mac_ratio=0.121` 表明 MAC 处于活跃状态的时间较少，但单凭该比例还不能确定峰值算力利用率。

**第 2 步：检查 AIC 累加结果是否限制流水。** 当前 `acc` 只有一个槽，MAC 与该槽的 FIXPIPE 搬出存在复用依赖。原文记录把 L0C 改为两槽后，生成代码确认第二槽地址为 `0x10000`，典型耗时由 81.35 变为 81.51 µs，没有显示收益。这支持当时 MAC/FIXPIPE 的这项依赖并非主要瓶颈；它是历史对照，不是当前代码自动验证的结论。

**第 3 步：检查 Vector 和 MTE3。** 旧快照 `aiv_vec_ratio=0.2105`，包括 head 归约、顺序恢复、键编码、radix 及位置映射；`aiv_mte3_ratio=0.2965`，包括 GM 环发布与键写回。它们都低于 AIV MTE2。原有 UB→L1 对照中，省去 GM 中转约节约 0.121 µs/tile，UB 内布局重排却约需 0.624 µs/tile，因此该替代方案没有采用。多个 pipe 占比相加大于 1，说明快照统计范围内存在时间重叠，但不能单靠比例之和确定每对 pipe 的具体重叠关系。

**第 4 步：理解标量开销。** 旧快照 AIV scalar 为 0.377，AIV MTE2 为 0.6975，比值约 0.54，略高于自查约定的 0.5。源码中的地址准备、标量读取、循环和 DMA 描述符发射都会贡献标量工作；它与搬运效率密切相关。原文记录把成对 DMA 的数据依赖分支改成无条件地址钳位后，典型耗时从 80.64 降到 79.23 µs；这支持优化发射路径，但不能据此把全部 scalar 时间都归于同一原因。

**第 5 步：核算候选数据读取量。** 每 Query 读取 2048 条记录，每条 544 B，共 `72*2048*544 = 80216064 B`，约 80.22 MB。除以 78.755 µs 得到 1.019 TB/s；相比原文 `ReduceSum` 顺序读参照的 1.46–1.57 TB/s，为约 65–70%。这里统计的是算法请求的原输入字节数，未包含 cache line 放大，也没有 HBM 计数器数据，故应称为“有效候选读取吞吐”，不能直接写成实际 HBM 带宽利用率。

**第 6 步：将访问形态与 DMA 条数分开讨论。** 旧快照 AIV MTE2 占比最大，为 0.6975，对应约 55.1 µs。其余约 30.25% 表示在该指标口径下 MTE2 不活跃；其他 pipe 可能仍在执行，不能称为“没有任何 DMA 在执行”，也不能直接等同于可消除的空闲时间。

- **DMA 条数对照**：每 tile 每 AIV 从 16 条成对 DMA 改为 32 条单记录 DMA，读取的有效字节相同，原文记录耗时 81.5→101.9 µs，约增加 25%。按每核 72 tile 折算为每新增描述符约 17.7 ns 的平均增量。该值反映发射、依赖和重叠变化后的整体结果，并非单条指令的独立延迟。
- **访问形态分析**：每行从 16384 个逻辑块中随机选 2048 个，K 的逻辑页容量为 1024 页，页表又随机映射物理页；544 B 记录起点以 32 B 为粒度变化，不保证 512 B 对齐。这样的离散小块读取与顺序 `ReduceSum` 的访问方式不同，可能影响缓存及内存访问效率。不过现有 65–70% 比值还混合了发射、计算、同步等成本，没有独立随机访问带宽实验，不能把它宣称为输入格式决定且无法改进的带宽上限。

**第 7 步：估计带宽参照耗时。** 用顺序读参照的高值估算，`t_est = 80.22 MB / 1.57 TB/s ≈ 51.1 µs`，记录中 `t_meas/t_est ≈ 1.54`。它是只计原输入有效读取、采用乐观顺序带宽的参照，不是精确的完整 kernel 下界。随机访问、DMA 发射、GM 中转、行边界和分片归并都可能影响差距；这些因素会相互重叠，不能直接把各段 pipe 时间相加。若改用更低的随机读取带宽，估计时间会增加、比值会减小，因此当前 1.54 会放大相对于该估计的差距。

**第 8 步：结合调度解释其他阶段的影响。** 典型场景按 tile 数每 worker 都是 72，但不同 worker 的整行 TopK 次数及分片归并职责可能不同。AIC 要等待 `EV_K_READY`，AIV 要等待 `EV_QK_READY`，行尾还要执行子块握手和可能的 MIX 同步。旧快照 AIC pipe 占比之和约 1.0565、`cube_utilization=96.14%`，并不足以唯一还原上述等待关系。结合 DMA 条数对照可判断 gather 值得优先优化；要量化各段等待及当前瓶颈，仍需刷新 profiler 并查看分核时间线。
