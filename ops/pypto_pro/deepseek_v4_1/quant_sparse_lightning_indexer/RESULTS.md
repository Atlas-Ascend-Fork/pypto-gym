## 精度标准

**独立参考实现**：`tests/assets/quant_sparse_lightning_indexer_golden_cpu.py` 在 CPU 上独立解码 MXFP4 并按与 kernel 相同的舍入链计算——低 nibble 优先、E2M1 幅值 `{0,0.5,1,1.5,2,3,4,6}` 配符号位、E8M0 指数 `字节值-127`、每 32 个连续逻辑元素共享一个 scale；QK 交接为 BF16，权重转 BF16，逐 head 融合乘加的每一步结果都舍入为 BF16。参考实现不读取设备输出，也不与 kernel 共享中间量。

**比较器**：`tests/assets/quant_sparse_lightning_indexer_precision.py`，固定阈值 `rtol = 1/128`、`atol = 2.5e-5`（`rtol` 取 BF16 的分辨率，不是放宽容差），**不能由测试输入覆盖**。逐项检查：

1. 无效项：`indices == -1` 且（输出分数时）`values == -inf`；
2. 有效数量 == `min(topk, 允许集合大小)`；
3. 选中索引互不重复；
4. 选中索引全部落在 `[0, 分数长度)` 且全部属于允许集合（候选块归属 + 可见性双重约束）；
5. 分数与参考实现在选中位置上一致（`rtol/atol`）；
6. TopK 边界：`min(选中分数) >= boundary - atol - rtol*|boundary|`，其中 `boundary` 为允许集合上第 `选中数量` 大的分数；`boundary` 为 `+inf` 时要求选中分数全为 `+inf`。

由于输出顺序不保证，比较器与用例名（unordered TopK validation）都是**顺序无关**的：只校验集合、数量、边界与哨兵。

**结果**：当前代码上全量 **62/62 PASS（1010.6 s）**；此外性能采集的每一次采样都会独立跑一遍上面的输出校验（预热输出 + 图重放后的首末两次输出），因此所有性能数据都对应通过精度校验的运行。

## 性能结果

### 绝对性能结果

**环境与批次**：Ascend950PR_9589（32 Cube / 64 AIV，L2 = 128 MiB），CANN 9.3.0、PyPTO 0.2.1、PyTorch 2.12.0+cpu、torch_npu 2.12.0.post2、Python 3.12，device 0。下表数据采自内核源码 SHA256 `349f6aa6dddeec19d6a8ac3329b3926d44ea0e317bf6e69209f53a5738d29764`；当前文件 SHA256 `62503e2ca494678a2078e11662a67fff8ba70a1017ed0ed7763d5a15387126ca`，与该版本**只差文件头与模块 docstring 的规范化**（注释级，无代码改动）。

**口径**：冷 L2 —— 一个 NPU Graph 内每次目标调用前先对 256 MiB FP32 缓冲区做 `ReduceSum` 驱逐 L2（脚本断言驱逐缓冲 > 上报 L2 容量，本机为 2.0×）；以 `ReduceSum` 行为分界切分每次调用，指标 = **该调用发射的全部 native task 的 `Duration(us)` 之和**；本实现每次调用恒定 1 个 task（`PYPTO_qsli_kernel`，`Type='PyPTO'`，32 MIX 块），故逐 task 与整次调用同值。LI/LD 调度表在计时图之外生成一次，窗口内不含 AICPU task；host 侧校验、分配与启动开销均不计入。每个场景 × 每个返回模式采 **60 个样本**（3 轮 × 20 次），取中位数；表内 `范围` 为该 60 样本的 min–max。

### 理论评估对比（MFU / Bound / 利用率）

这里的 **Bound 指性能瓶颈**（哪一段资源或哪一类开销决定了 kernel 耗时），不是"绑定"。只有 `typical` 场景的工作量足以做 roofline 判定；其余场景的 Bound 与之不同，见文末「各场景 Bound 归类」。

**Bound 结论（一句）**：`typical` 场景的瓶颈在 **AIV 侧 MTE2 的 paged-K gather 搬运段** —— 由「随机 544 B 记录的有效带宽上限（只到同口径顺序读参照的 65–70%）」与「每 tile 每 AIV 16 条跨步描述符的发射开销（实测 ≈17.7 ns/条）」两项叠加决定；**不是** Cube 计算、**不是** Vector 计算、**不是** MTE3，标量流水只是边际参与（`0.377/0.6975 = 0.54`，略超 G2 的 0.5 判据）而不主导。

**MFU 说明**：本算子的 MFU（对 Cube MAC 峰值）只有约 **12%**，而且这是**设计使然、不是缺陷** —— 算术强度被输入形态钉死（每搬 544 B 记录只产生 8 token × 32 head × 128 dim 的乘加），Cube 在 88% 的时间里无事可做。因此 MFU 不是本算子合适的优度指标，**有意义的是访存侧利用率**（1.019 TB/s ÷ 1.46–1.57 TB/s ≈ 65–70%）与 pipe 占用分布。

#### 分析过程

按"先排除、再定位、最后用对照实验确认"的顺序，每一步都写明依据。

**第 1 步：排除 Cube 计算（MAC）**。`aic_mac_ratio = 0.121` 是全 AIC 各 pipe 里最小的非零项，对应 2304 次 `matmul_mx`（M32×N512×K128）合计 9.8 µs；实测总吞吐 9.664 GFLOP / 78.755 µs = 122.7 TFLOP/s，但 MAC pipe 只有 12.1% 的时间在工作，说明离算力上限很远。**决定性证据**：把 `acc`（L0C）从 depth 1 改成 depth 2、让 MAC(t+1) 与 FIXPIPE(t) 重叠 —— 生成物已确认第二个槽真实存在（`kernel.cpp` 出现 `TASSIGN(_tg_acc_tiles_1_0, 0x10000)`，并产出新的 `.so`），但典型场景耗时**无可测变化**（81.35 → 81.51 µs）。⇒ MAC 与 FIXPIPE 的串行不在关键路径上，AIC 的乘加不是该场景的 pacer。

**第 2 步：排除 Vector 计算（VF）**。`aiv_vec_ratio = 0.2105`（16.6 µs），涵盖 head 归约（8 组 × 4 head 的 BF16 融合乘加链）+ 撤销成对 DMA 排序的置换 + 保序键编码 + radix TopK 的 4 趟遍历 + 位置映射，合计不到 AIV 时间的四分之一；且这些 VF 工作在寄存器内完成，与 MTE2 天然重叠（`aiv_mte2 + aiv_vec + aiv_mte3 + aiv_scalar = 1.58 > 1` 本身就证明重叠存在）。⇒ Vector 不是瓶颈。

**第 3 步：排除 MTE3（GM 环发布 + 键工作区写）**。`aiv_mte3_ratio = 0.2965`（23.4 µs）。**决定性证据**：能力探针把 GM staging 环的载荷腿整条删掉（改为 UB 内 ND→NZ 后直交 L1），实测每 tile 只值 **0.121 µs**（基线 0.82–0.85 µs/tile，约 15%），而为此必须付出的 UB 内 ND→NZ 重排是 **0.624 µs/tile** ⇒ 净亏 ≈0.5 µs/tile（按每核 72 tile 外推 = 收益 −8.7 µs 对代价 +44.9 µs）。⇒ MTE3 上有可省的绝对时间，但它不是决定耗时的限制项；而且省它的唯一路径在本平台上更贵。

**第 4 步：确认标量只是边际参与**。`aic_scalar_ratio = 0.152`、`aiv_scalar_ratio = 0.377`。G2 判据是「标量占比 ≤ 0.5 × 最大流水占比」，此处 `0.377 / 0.6975 = 0.54`，**略超**阈值 ⇒ 标量参与明显但不主导。需要注意口径：描述符发射的开销（第 6 步）本身就落在标量流水上，所以它是"搬运发射"这一项的成本体现，不该被当成独立的标量热点；这也解释了为什么把成对 DMA 的运行期分支换成标量钳位后典型场景直接变快（80.64 → 79.23 µs，每 tile 少 16 条数据依赖分支、展开体不再被切成 16 个基本块）。

**第 5 步：定位最大项 = AIV MTE2**。`aiv_mte2_ratio = 0.6975`（55.1 µs / 79.05 µs）是**全部 pipe 中最大的单项**，AIC MTE2 次之（0.4325，35.0 µs）。两者都是 K 数据搬运的不同段：前者把 544 B 记录从 GM 收进 UB，后者把 GM 环里的数据转置载入 L1。按字节核算：必须读的 K = 72 行 × 2048 块 × 544 B = **80.22 MB**，78.755 µs ⇒ **1.019 TB/s**；同口径下的顺序读参照（256 MiB `ReduceSum`）为 **1.46–1.57 TB/s** ⇒ 只到 **65–70%**。

**第 6 步：判定"AIV MTE2 占用 0.6975"是否就是全部瓶颈 —— 不是，还有 30% 空窗**。按工程约定阈值（`max(pipe_ratio) ≥ 0.8`）衡量，实测 0.6975 说明**还有约 30% 的 AIV 时间没有任何 DMA 在飞** —— 这段空窗不被 pipe 占用率计量，正是剩余可优化空间的度量。用对照实验拆开这 30%：

- **对照 A（字节不变、条数翻倍）**：关闭成对通路、强制每 tile 每 AIV 发 32 条单记录 DMA（HBM 字节数完全相同），典型场景 81.5 → **101.9 µs（+25%）**，折算每条描述符 ≈**17.7 ns** 的纯发射成本。⇒ 瓶颈里含**发射串行**成分，本场景**不是纯带宽墙**；反过来说明"减少描述符条数/去掉发射路径上的数据依赖分支"是一级优化方向，优先级高于"减少字节数"。
- **对照 B（访问形态决定带宽上限）**：候选块是 16384 块中随机选中的 2048 块，跨 1024 个物理页散布；每条记录 544 B（32 B 对齐、**非** 512 B 对齐，512 B payload + 32 B scale）。随机小记录 ⇒ DRAM 行局部性差 ⇒ 有效带宽天然低于顺序流，这就是第 5 步那个 65–70% 的来源，属于输入契约（分页 MXFP4 记录布局）决定的下限，不是实现可以消掉的浪费。

**第 7 步：roofline 收口**。带宽侧下限 `t_est = 80.22 MB ÷ 1.57 TB/s ≈ 51.1 µs`，实测 `t_meas = 78.755 µs` ⇒ **`t_meas/t_est ≈ 1.54`**，超出 G6 的 1.25 判据。差距归因三项：① 随机 544 B 记录使有效带宽只有顺序参照的 65–70%（对照 B，输入形态决定）；② 每 tile 每 AIV 16 条描述符的发射开销（对照 A，实测 17.7 ns/条）；③ 行边界的取址/预取收口与归并相位的同步。前两项有实测对照，第三项为结构分析。注意 `t_est` 用的是顺序读参照带宽，对随机访问而言偏乐观，所以 1.54 是**偏保守**的比值。

**第 8 步：AIC 侧为什么不是 pacer（补强第 1 步）**。AIC 各 pipe 占比之和 = 1.0565，而 `cube_utilization = 96.14%` ⇒ 重叠系数只有 1.10，AIC 近似串行地走完「等环就绪 → MTE2 转置载入 → MTE1 → MAC → FIXPIPE」；但它的单 tile 周期仍短于 AIV 的 gather + 发布周期，因此 AIC 是在**等 AIV**，不是被自己的乘加或搬出卡住。这与第 1 步"改 L0C 双槽无收益"互为印证。

| G2 | 无标量受限 | 标量占比 ≤ 0.5 × 最大流水占比；循环内无除法/取模 | 标量 `0.377`、最大流水 `0.6975` ⇒ 比值 `0.54`（略高于约定值）；循环内**无除法**（页大小为 2 的幂走移位+掩码，否则走预算倒数乘法+过冲修正） | 标量参与的主体是地址准备与描述符构造，与搬运发射同源；已通过成对 DMA 去分支回收过一轮（典型场景 80.64 → 79.23 µs），剩余部分与第 6 步的发射串行是同一件事 |
| G3 | 流水重叠 | 最大 pipe 占比 ≥ 0.8 | 最大 pipe 占比 `0.6975`（AIV MTE2） | 约 30% 的 AIV 时间没有 DMA 在飞。这段空窗**已被拆开定位**：描述符发射串行（对照 A，实测 17.7 ns/条）+ 随机 544 B 记录的有效带宽上限（对照 B，为顺序参照的 65–70%）。前者仍可继续优化，后者由输入契约决定 |
| G4 | 多核均衡 | `η_tail ≥ 0.9`；核间离散度 ≤ 10% | `typical` 每核精确 72 tile ⇒ `η_tail = 1.0`；约 10 tile 的小场景只有约 10 个 worker 有工作（`η_tail ≈ 0.31`） | 小场景的利用率由 LI/LD 调度表的成本模型与 tile 粒度（512 token = 64 块）共同决定，切分粒度已是契约允许的最小单位；分核时间线未采集，故核间离散度记 `unknown` |
| G5 | 流量 | 放大系数 `A ≤ 1.1` | K 每字节经 GM staging 环多一次 L2 写 + 一次读 ⇒ `A ≈ 3` | 环工作集约 4.5 MB，常驻 128 MiB L2，**不额外消耗 HBM 带宽**；HBM 侧只有 80.22 MB 的必需读。去环方案已实测为净亏（UB 内 ND→NZ 0.624 µs/tile 对收益 0.121 µs/tile，见 `DESIGN.md`），属经过论证的设计选择 |
| G6 | Roofline 终态 | `t_meas ≤ 1.25 × t_est` | `t_est ≈ 51.1 µs`、`t_meas = 78.755 µs` ⇒ 比值 `1.54` | 差距三项归因，前两项有实测对照（随机访问带宽、描述符发射），第三项为结构分析（行边界收口与归并相位）。`t_est` 用**顺序读参照带宽**作上限，对随机 544 B 访问偏乐观 ⇒ 1.54 是保守估计；用真实随机访问上限时该比值会更小 |

#### 各场景 Bound 归类

| 场景 | Bound | 依据 |
| :--- | :--- | :--- |
| `typical` | **AIV MTE2 gather**（有效带宽 + 描述符发射） | 上文第 1–8 步 |
| `pa128` / `pa64_causal` / `topk16` / `pa_short` / `tnd_causal` / `tnd_short` | **固定开销 + 标量流水**，其次才是搬运 | 这些场景只有约 10 个 tile、约 10 个 worker 有工作；`aic_mte2` 仅 0.021、`aiv_mte2` 仅 0.036，而 `aic_scalar` 0.366 / `aiv_scalar` 0.433 / `aiv_icache_miss_rate` 0.365（均为 `pa128` 快照；`topk16` 快照为 0.376 / 0.402 / 0.358） ⇒ 时间花在调度表读取、逐行取址准备、逐行输出发射与指令首次取指上，不在数据量上 |
| 4 个 `empty` 场景 | **纯固定开销** | 零 tile：搬运类 pipe 占比 ≈0（`aiv_mte2` 0.002–0.0045），32 核最小 kernel 的启动地板实测 1.525 µs，而实测 7.5 µs ⇒ 约 6 µs 是 prologue/epilogue + 逐行哨兵填充。**直接验证**：在同一采集窗口内把 MIX 网格屏障按 LD 记录条件化，空场景从 8.727/8.967 µs 降到 6.945/6.922 µs（−20% / −23%）——同窗对比才可信，跨批次只能看出量级；这说明其中确有一段是可去掉的同步固定开销，也说明该场景的 Bound 不在任何搬运 pipe 上 |

**测量口径的已知局限与后续优化方向**：

1. G2 / G3 的 pipe 占比取自结构整改**之前**的快照，整改后（成对 DMA 去分支、删除 11 对冗余手动同步、屏障条件化）**未重新采集**；由于 `max(pipe_ratio)` 当时低于 0.8，整改后的绑定因素可能已经变化，需刷新才能据此再排序优化项。
2. G4 只有调度表推导出的均衡结论，没有分核时间线实测；G6 的 `t_est` 用顺序读参照带宽代替了随机 544 B 访问的真实上限，因此 1.54 是偏保守的比值。
3. 尚未尝试的方向（按性价比排序）：删除每 tile 那条针对 `kscratch`（`mutex_ids=[0,1]`）的 WAR 侧手动同步；利用 `k_l1` 与 `ks_l1` 之间约 192 KiB 的空闲 L1，把 K/scale 的轮转深度从 2 提到 3–4 以加深 AIC 的 MTE2→MTE1 重叠（`l0b` 受 64 KB L0B 限制必须保持 2，两处索引需解耦）；缩短空场景的逐行哨兵填充路径。加深 GM 环（`STAGE_DEPTH`）目前受跨核事件 id 预算（0..15，11/12/13 归 `sync_all(MIX)`）阻塞。
