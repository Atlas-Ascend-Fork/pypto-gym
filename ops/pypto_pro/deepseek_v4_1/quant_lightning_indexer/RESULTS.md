## 精度标准

四路输出按**两种语义**分别判定，对应两套机制：

- **`indices` / `candidates`（索引类）·集合语义。** 契约允许任意输出顺序，也允许同分时返回任一
  合法索引集合，所以**不能逐元素比较**。判定项是：精确 Top-K 的阈值边界、索引合法性
  （落在可见范围内、行内不重复）、无效槽必须是 `-1`。对 `candidates` 另加两条：块内取的是
  该块可见 token 的最大分、末尾不完整的有效块必须是 `+inf`。
- **`values`（分数）与 `candidate_lengths`（候选数量）·逐元素。** 走仓库统一的方案 A
  （`tests/assets/quant_lightning_indexer_precision.py`）。分数按下面四条指标比阈值；候选数量是
  INT32，走同一脚本的整数精确匹配分支（必须逐元素相等）。

  | 指标 | 含义 | 通过条件 |
  | :--- | :--- | :--- |
  | `atol` | 平均绝对误差 | `<= atol` |
  | `rtol` | 平均相对误差 | `<= rtol` |
  | `matched_ratio` | 满足 `\|a - g\| <= atol + rtol·\|g\|` 的元素占比 | `>= 0.99` |
  | `max_abs_error` | 最大绝对误差 | `<= max(fixed_limit, 32 ULP)` |

  阈值由 dtype 查表定死，表里只有 float16 / bfloat16 / float32 / float64 四行，其中 bfloat16
  这一行最宽松，取 `rtol = atol = 2^-6 = 1.5625e-2`、`max_abs_error <= max(1.0, 32 ULP) = 1.0`。
  分数的 dtype 就是 BF16，所以实际生效的就是这一行。判定接口不接受调用方传入的容差；可以指定的
  只有一个**已登记**的 dtype 名称，用来把标准收紧（其余三行都更严），指定未登记的名称直接判失败。

**结果。**

| 检查项 | 结果 |
| :--- | :--- |
| CPU golden 自检（契约逐行核对 + 独立 FP64 / E2M1 位域 oracle 交叉校验） | **12/12 通过**；其中 10 例 oracle 开启、`max_diff = 0.000e+00`（0.00 ULP），2 个 `b12` 例 oracle 关闭（原因见下） |
| CPU golden 性质检查（① E2M1 全 256 码位解码 + E8M0 是精确的 2 的幂，② 零权重 / 带符号权重，③ 候选块三条规则） | **3/3 通过** |
| 上板用例 | **12/12 通过** |
| 逐用例分数证据（方案 A，每例跑 `return_value` 两种模式） | **12/12 `scores_schemeA_passed = true`** |
| 分数实测误差 | `atol = rtol = 0.000e+00`、`matched_ratio = 1.0000`、`max_abs_error = 0.000e+00` |

上板分数与 CPU 参考**逐元素完全一致**（误差为 0），离 BF16 的 `2^-6` 阈值还有整个量级的余量。
用例全部实际执行：没有跳过、没有吞掉异常，任何一项不满足即断言失败。

索引类的判定是否真的覆盖到了「同分」这个分支，可以逐行统计。表中「阈值同分」指该 query 行在
第 `topk` 名的分数边界上存在并列，也就是选择结果本来就有多个合法答案：

| 用例 | 校验行数 | 其中存在阈值同分的行 |
| :--- | ---: | ---: |
| `pa128_ragged` | 7 | 2 |
| `pa64_causal_candidates` | 7 | 3 |
| `tnd_causal` | 7 | 3 |
| `candidate16_ld_tail` | 7 | 3 |
| `invalid_values_PA_BBND` / `_TND` | 7 / 7 | 0 / 0 |
| `empty_query_*` / `empty_key_*` | 7 × 4 | 0 |
| `b12_s1_6_n32_s2_64k` | 72 | 68 |

CPU 参考实现另有一层独立性校验：分数用 **E2M1 位域解码 + FP64** 做第二套独立推导，与主参考
逐元素比对（上表的 0.00 ULP 就来自这里）；256 个 `E2M1` 码位、`E8M0` 的 2 的幂性质、零权重与
符号权重、候选块的三条规则，也都逐项做了性质检查（归成 3 组）。
两个长上下文的 `b12` 用例，各序列 key 长度之和分别是 786 432 与 1 572 864，超过 golden 里
`_ORACLE_KEY_LIMIT = 200 000` 这条阈值（FP64 oracle 的内存与耗时限制），因此跳过这一层交叉校验，
其正确性由集合语义与逐元素两条判定覆盖。

## 性能结果

**采集口径。** 全部使用 Ascend 官方 profiler：`msprof --output=<dir> --ascendcl=off --task-time=on
python <bench>`，取 `op_summary_*.csv` 里 `Op Name = PYPTO_quant_lightning_indexer_kernel`
那些行的 `Task Duration(us)`；`Block Num` 恒为 32、`Task Type` 恒为 `MIX_AIC`。计时流程：

1. 先跑一次被测算子，排除 JIT 编译时间；
2. 跑一次 `cann_bench_warmup`（10240×10240 fp16 MatMul），把 NPU 频率拉到稳定档位；
3. **每一次测量调用前**都执行一次 `cann_bench_cache_clean`（(96, 1024, 1024) fp16 的 ReduceMax，
   纯读 192 MiB）把 L2 清空，保证每次测量都是**冷启动**；
4. 预热 3 次不计入，测量 9 次；每次调用后 `torch.npu.synchronize()`；
5. 取这 9 个采样值的**中位数**作为该用例耗时，最小值另列；
6. 解析时用清 L2 kernel 的采样行作步分隔符重新分组，与「取最后 9 次」的选法交叉校验，
   两种选法的结果一致。

> 提交开销；那部分单独放在「绝对性能结果」里，两者不要混用。

### 绝对性能结果

核内耗时只是 kernel 自己的时间。调用方实际拿到的是公开 wrapper，它还要做形状校验、回读序列数组、
分配输出与 workspace、组装 tiling key 并派发。这一部分**不在**上面的数字里，单独列在这里，避免把
两者混为一谈。

测量办法：在同一次 wrapper 调用内部把耗时拆成三段——`torch.Tensor.cpu()` 的回读、`torch.empty` 的
分配、其余算作框架提交路径。每例预热 3 次，另做三次独立采样、每次 31 次调用，共 93 个样本，
取全部样本的**最小值**作为一次调用墙钟的估计。

| 用例 | 序列数组回读 | 输出分配 | 框架提交路径 | 一次调用墙钟（最小值） |
| :--- | :--- | :--- | :--- | --: |
| `empty_key_PA_BBND` | 0.16–0.23 ms（3 个张量） | 0.04–0.07 ms（6 个张量） | ≈1.1–1.9 ms | **1.28 ms** |
| `pa128_ragged` | 0.15–0.16 ms（3 个张量） | 0.04 ms（6 个张量） | ≈1.1 ms | **1.30 ms** |
| `b12_s1_6_n32_s2_128k` | 0.21 ms（4 个张量） | 0.05 ms（7 个张量） | ≈1.5–1.6 ms | **1.77 ms** |

两点说明：

- 回读部分是把 `cu_seqlens_q` / `seqused_q` / `seqused_k`（必要时还有 `cu_seqlens_k` /
  `cmp_residual_k`）取回 host、用来预计算分核表 `plan`（见 `DESIGN.md` 的「计算阶段划分」）。
  这几次 device→host 同步是**固定的启动延迟**，与数组长度几乎无关：随批次数涨的是张量个数，
  不是数据量。
- 剩下约 1.1–1.6 ms 落在框架的 kernel 提交路径（tiling key 组装与 JIT 派发）上，与算子实现无关。
  它比核内耗时大一个数量级以上，也是「同一个用例 rv0 与 rv1 的核内耗时几乎相同、但调用方感受
  不到差别」的原因：两侧的核内差异被这 1 ms 完全淹没。这一段的绝对值随框架版本与主机负载变化，
  表中数值只作量级参考。

在真实推理里这个算子会被前后别的 kernel 夹住、launch 可以流水起来，所以目标场景应当看核内耗时；
上面这张表只说明单测场景下一次调用的代价。

### 理论评估对比

**两个实测上界。** 要判断一个算子是偏算力还是偏带宽，需要一个「算力能到多高」和一个「带宽能到
多高」的参照。这里**不用平台配置里的 `DtypeMKN` 反推峰值**：按 `Ascend950PR_9589.ini` 的
`cube_freq = 1650 MHz`、32 个 Cube 核、`DT_FLOAT4_E2M1 = 16,64,16` 反推会得到 MXFP4
1730 TFLOPS / BF16 432.5 TFLOPS，而 10240³ 的 fp16 MatMul 实测已达 5 430.7 TFLOPS（下表第一
行），远超这两个反推值——说明 `DtypeMKN` 不是「每周期乘加次数」的换算来源，这条推法不采用。

改用**同一套采集协议**下测到的两个参照（也就是采集流程里那两个辅助 kernel）：

| 参照 | 算子 | 24 次采集中的最快 | 各次最小值的再取中位 | 用作 |
| :--- | :--- | --: | --: | :--- |
| 算力参照 | `CannBenchWarmup`：10240×10240×10240 fp16 MatMul（2.1475e12 FLOP） | 395.434 µs → **5 430.7 TFLOPS** | 396.712 µs → 5 413.2 TFLOPS | 算力上界参照 |
| 带宽参照 | `CannBenchCacheClean`：(96,1024,1024) fp16 ReduceMax（201.3 MB 纯读） | 103.908 µs → **1 937.5 GB/s** | 120.748 µs → 1 667.3 GB/s | 带宽上界参照 |

带宽参照是纯读归约，读数可靠。算力参照的那个 MatMul 自身也受它自己的访存压力牵制，所以
5 430.7 TFLOPS 只能当作**「同卡能做到的最高算力水平」的一条参照线，不是芯片峰值**——真实峰值
只会更高，这意味着下文的「占算力参照」是一个偏乐观（偏高）的估计，用它得出的结论只会更保守。
两者的比值给出这台机器的平衡点：`5430.7 TFLOPS / 1937.5 GB/s ≈ 2803 FLOP/Byte`。

**算量与 Bound 判定。** 每个用例的算量由用例定义直接推出：QK 矩阵乘的乘加次数

+ Q + 权重 + 全部输出，**不含**分页 padding、`block_table` 与 `plan`。这是一个解析模型，
不是显存计数器读数，用来判断量级与受限侧。

「roofline 上界」这一列的单位是 TFLOPS，含义是「按访存上界反推出的算力天花板」：
`算术强度 × 1 937.5 GB/s`。实测达成量与它的比值恒等于「占带宽参照」——因为
`(FLOPs / 时间) / (AI × 带宽) = (字节 / 时间) / 带宽`，两边是同一个式子，不是巧合。

读法（`MFU` 就是「实测达成算力 ÷ 算力参照」，Bound 指耗时被算力还是被带宽卡住）：

- **所有用例的算术强度（77–721 FLOP/Byte）都远低于机器平衡点 2803 FLOP/Byte**，也就是从 roofline
  上看它们都落在**访存侧**，算力天花板由「算术强度 × 1 937.5 GB/s」给出（表中最后一列）。
- **只有两个长上下文用例真正把 Cube 推起来了**：502.9 / 543.3 TFLOPS，相当于算力参照的
  9.26% / 10.00%，相当于带宽参照的 36.07% / 38.88%。这两个比例之所以不相等、而且比值恰好是
  `算术强度 ÷ 平衡点 = 719.6 / 2803 ≈ 0.257`（128K 档是 0.257），是一个恒等式：
  `占算力参照 ÷ 占带宽参照 = 算术强度 ÷ 平衡点`，与实现无关，只由用例的算术强度决定。
  换句话说，**在同一份算术强度下，带宽达成率天然就是算力达成率的 3.9 倍，这不能说明算子偏哪一侧**；
  能说明问题的是绝对值——它们**既没打满算力（10.0%），也没打满带宽（38.9%）**，卡在两者之间。
- **其余 10 个用例的达成率都在 1% 以下**（达成 0–4.8 TFLOPS），耗时由上文那条约 4 µs 的固定核
  开销决定。对它们算 MFU 只会得到一个好看但没有信息量的数字，所以表中留空。

**利用率。** 这里三种「利用率」的口径不同，先分清：

- **核占用率**（可由表内数据复算）：`aicore_time(us)` / `aiv_time(us)` 与 `Task Duration(us)` 之比，
  表示 Cube / Vector 核在算子这段时间里被占用的比例。
- **流水线占用率**（官方字段）：`aic_*_ratio` / `aiv_*_ratio`，含义是该流水线的占用时间除以
  `aicore_time` / `aiv_time`。
- **`cube_utilization(%)`**（官方字段）：msprof `op_summary` 给出的算子级综合利用率。

长上下文的 4 行是唯一对目标场景有解读价值的行，它们也正好解释了「既没打满算力也没打满带宽」：

- **最忙的两条流水不是 MAC**：`fixpipe`（L0C → UB 的折叠）0.69–0.736、`mte2`（显存 → L1 的搬运）

  `DESIGN.md` 里「query 常驻 L0A、一次搬运服务两次矩阵乘，是因为本算子的搬运次数比乘加次数更
  容易成为瓶颈」的设计判断一致。
- Vector 侧的 `aiv_vec` 是 0.494–0.506，也不是最忙的，说明向量算力不是瓶颈。
- 因此核内耗时的进一步下降取决于搬运与折叠链路，而不是 Cube 的算术效率。
- 短序列与空输入那些行呈现的是另一件事：`AIC scalar ≈ 0.47–0.89`、`AIV scalar ≈ 0.48–0.99`，
  而 `mac`、`mte2`、`fixpipe` 基本为 0。这印证了上面的判断——它们的耗时量级由**标量控制开销**
  决定，不是由算力或带宽决定。

`cube_utilization(%)` 是 msprof 给出的算子级综合利用率字段，本文只作为工具口径原样列出，不参与
上面的瓶颈判断，也不与核占用率混用。

**小结。**

- **精度**：12/12 通过（CPU 自检 12/12、性质检查 3/3、上板用例 12/12、逐用例分数证据 12/12），
  分数输出与 CPU 参考**逐元素完全一致**（`max_abs_error = 0`）；两类输出分别按集合语义与逐元素
  语义判定，阈值查表定死，接口不接受外部容差。
- **目标场景（长上下文）**：Cube 核占用 99.5–99.8%、Vector 核占用 97.4–98.6%，核没有空转；
  达成 502.9 / 543.3 TFLOPS，相当于算力参照的 9.26% / 10.00%、带宽参照的 36.07% / 38.88%，
  **两头都没打满**；最忙的流水是 fixpipe（69.1–73.6%）与 mte2（69.1–72.8%）而不是 MAC
  （44.6–47.2%），瓶颈明确落在搬运与折叠链路上。
- **64K 档与 128K 档的达成率**：两档都是 7 个分片、84 个工作项，单工作项覆盖的 key tile 数分别
  是 37 与 74；达成率 9.26% / 36.07%（64K）对 10.00% / 38.88%（128K）。工作项内部的固定开销
  （载入 query 块、建立 Cube↔Vector 握手、归并选择结果）在 64K 档摊到更少的 tile 上，与两档
  达成率的高低方向一致。
- **短序列用例**：耗时由约 4 µs 的固定核开销决定，只看量级即可；它们的流水线占用由标量控制主导。
- **调用代价（补充口径）**：核内 3.9–142.4 µs，而一次 wrapper 调用的墙钟最小观测是 1.28–1.77 ms，
  其中约 1.1–1.6 ms 落在框架的提交流程、0.15–0.23 ms 落在序列数组回读。这部分与算子实现无关，
  在真实推理里会被前后 kernel 的 launch 重叠掉。
