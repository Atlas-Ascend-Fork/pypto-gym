# mhc_pre_fuse 结果说明

本文给出 `mhc_pre_fuse` 的用例、精度标准与性能结果。文中标「实测」的数据是在设备上
直接测得的；带宽、算术强度、有效浮点吞吐由实测时间与已知数据量按文中算式导出，可逐项
复算。

测试环境：

| 项目 | 取值 |
| :--- | :--- |
| 设备 | Ascend 950PR（`Ascend950PR_9589`，`NpuArch=3510`），单卡 |
| 计算单元 | cube 32 核 / vector 64 核（`[SoCInfo] cube_core_cnt` / `vector_core_cnt`） |
| 片上缓存 | 每个向量核 253952 字节（248 KiB）；L2 134217728 字节（128 MiB） |
| 软件 | CANN 9.3.0、PyPTO-Pro DSL（pypto 0.2.1）、torch 2.8.0、torch_npu 2.8.0.post4 |

核数、UB 与 L2 容量取自 CANN 平台配置 `Ascend950PR_9589.ini`。

## 用例

**用例（5 个）**

5 个形状，既是正确性用例，也是「性能结果」一节里的计时用例：

| 用例 | T | H | 残差输入大小（4·T·H·2 字节） |
| :--- | ---: | ---: | --- |
| 512x4096 | 512 | 4096 | 16.8 MB，可整块留在 L2 |
| 512x7168 | 512 | 7168 | 29.4 MB，可整块留在 L2 |
| 8192x4096 | 8192 | 4096 | 268.4 MB，远超 L2 |
| 8192x5120 | 8192 | 5120 | 335.5 MB，远超 L2 |
| 8192x7168 | 8192 | 7168 | 469.8 MB，远超 L2 |

每个形状在 `tests/test_mhc_pre_fuse.py` 里对应一个 `test_<T>x<H>` 函数。三种跑法等价：
按 pytest 收集、`python test_mhc_pre_fuse.py` 跑全部、或直接调用某一个 test 函数。每个
test 函数都带 `@pytest.mark.soc("950")` 标注——仓库根的收集钩子对没有标注的用例默认只认
`910`，标注之后在 Ascend 950 上不会被剔除。

5 个形状的 `T` 都是 8 的倍数，因此都走 `tb = 8`；`H = 4096 / 5120 / 7168` 都能被 512
整除，因此都取最宽的 `h_blk = 512`，隐藏维刚好切成 8 / 10 / 14 块，都够 5 级流水展开。
`T` 不能被 8 整除时按 4 / 2 / 1 退化的词元分块、以及 `H` 只能取更窄 `h_blk` 的情形，属于
约束允许、但本套用例未覆盖的分支。

输入取值：`gemm_out_mul`、`mhc_scale`、`mhc_base`、`residual` 取 `N(0, 1)` 并 clamp 到
[−8, 8]，`gemm_out_sqrsum` 由 `residual` 现算，保证两者一致。

**验证资产**

- `tests/test_mhc_pre_fuse.py`：5 个正确性用例，每个用例一个 test 函数；
- `tests/assets/mhc_pre_fuse_golden_cpu.py`：独立 CPU 参考实现（纯 torch 的 FP32 计算，
  另有 FP64 oracle 交叉验证与性质检查），同时是自检入口；
- `tests/assets/mhc_pre_fuse_precision.py`：精度比较器，阈值表内置于文件，不接受外部参数。

## 精度标准

**判定标准**

比较器是 `tests/assets/mhc_pre_fuse_precision.py`（方案 A 混合容差）。参考值由
`tests/assets/mhc_pre_fuse_golden_cpu.py` 在 CPU 上独立算出。

逐元素判定：`|actual − golden| <= atol + rtol × |golden|`。

整体判定（下面四条必须**同时**满足）：

- `matched_ratio >= 0.99`：逐元素通过的比例；
- `max_abs_error <= max(fixed_limit, 32 × ULP)`；
- `mean_abs_error <= atol`；
- `mean_rel_error <= rtol`。

另有三条规则：NaN 的位置必须一致；Inf 必须同号（一方是 Inf、另一方是有限值时，把
Inf 换成该 dtype 的最大有限值再比）；整数类型按精确相等比。

阈值表写死在比较器里，不接受调用方传参：

| 输出 | dtype | rtol | atol | `max_abs_error` 上限 |
| :--- | :--- | :--- | :--- | :--- |
| `post_mix` / `comb_mix` | FP32 | 2⁻¹⁰ = 9.77e-04 | 2⁻¹⁶ = 1.53e-05 | 1.0e-02 |
| `layer_input` | BF16 | 2⁻⁶ = 1.56e-02 | 2⁻⁶ = 1.56e-02 | 1.0e+00 |

`max_abs_error` 上限取 `max(fixed_limit, 32 × ULP)`。ULP 取 1.0 附近的值，也就是相邻
两个可表示数之间的距离：FP32 是 2⁻²³ = 1.19e-07，BF16 是 2⁻⁷ = 7.81e-03。乘以 32 之后
分别是 3.8e-06 和 0.25，都还小于对应的 `fixed_limit`（1e-2 和 1.0），所以上限就是
`fixed_limit`。

**实测结果**

**5 / 5 通过，15 个输出张量（5 个用例 × 3 个输出）全部 PASS，`matched_ratio` 一律
1.0000（阈值 0.99）。**

下表是 5 个用例里**最坏**的一次取值，括号里是该值出现的用例，「余量」是阈值除以实测值：

| 输出 | 指标 | 最坏值（出现用例） | 阈值 | 余量 |
| :--- | :--- | :--- | :--- | ---: |
| `post_mix` | mean_abs_error | 9.661e-09（8192x7168） | 1.53e-05 | 1600 倍 |
| `post_mix` | mean_rel_error | 2.700e-08（8192x7168） | 9.77e-04 | 3.6e4 倍 |
| `post_mix` | max_abs_error | 1.788e-07（8192x7168） | 1.00e-02 | 5.6e4 倍 |
| `comb_mix` | mean_abs_error | 2.249e-08（512x7168） | 1.53e-05 | 680 倍 |
| `comb_mix` | mean_rel_error | 1.230e-07（8192x4096） | 9.77e-04 | 7900 倍 |
| `comb_mix` | max_abs_error | 2.384e-07（8192x4096） | 1.00e-02 | 4.2e4 倍 |
| `layer_input` | mean_abs_error | 4.669e-08（512x7168） | 1.56e-02 | 3.3e5 倍 |
| `layer_input` | mean_rel_error | 4.027e-07（512x4096） | 1.56e-02 | 3.9e4 倍 |
| `layer_input` | max_abs_error | **1.562e-02**（512x4096） | 1.00e+00 | 64 倍 |

从这两组数可以读出：

- `post_mix` 和 `comb_mix` 是 FP32 输出，三项指标离阈值都有两个数量级以上的余量；
- `layer_input` 是 BF16 输出，最坏的最大绝对误差 1.562e-02，阈值 1.0，余量 64 倍。
  这个偏差来自 BF16 输出本身的舍入（1.562e-02 正好等于数值量级 2~4 处的一个 BF16
  相邻值间隔，见下一条）。5 个用例的最大绝对误差都 ≥ 1.5e-02，说明这是 BF16 表示粒度
  的下限，而不是个别用例的异常。

**BF16 输出的误差下限**

把最坏误差换算成 BF16 的相邻值间隔（ULP）来看。对 `layer_input` 偏差最大的那个元素，
记下参考值在该处的幅值，再取这个幅值上 BF16 的两个相邻值之间的距离，两者一比：

| 用例 | 参考值在该处的 \|值\| | 该处 BF16 间隔 | 最坏偏差 | 比值 |
| :--- | ---: | ---: | ---: | ---: |
| 512x4096 | 3.1250 | 1.5625e-02 | 1.5625e-02 | 1.00 ULP |
| 512x7168 | 2.9062 | 1.5625e-02 | 1.5625e-02 | 1.00 ULP |
| 8192x4096 | 2.4062 | 1.5625e-02 | 1.5625e-02 | 1.00 ULP |
| 8192x5120 | 2.1875 | 1.5625e-02 | 1.5625e-02 | 1.00 ULP |
| 8192x7168 | 2.1094 | 1.5625e-02 | 1.5625e-02 | 1.00 ULP |

也就是**最坏偏差正好等于一个 BF16 间隔**，5 个用例都是如此。可见偏差来自**输出一次性
舍入到 BF16**，而不是迭代误差的累积。

## 性能结果

本节所有数字按下面的口径采集。

**时间**

- 每个用例独立进程，连续调用 21 次，丢弃第 1 次（含首次编译与冷启动），取其余 20 次
  的中位数。
- 为保证每次采样的前置条件一致，进程开头执行一次升频 + 清 L2，之后每次调用前再清一次
  L2：升频用 MatMul（10240×10240 fp16），清 L2 用 ReduceMax（96×1024×1024 fp16）。
- 耗时取 profiling 记录中被测 kernel（设备侧名字 `PYPTO_mhc_pre_fuse_kernel`）的
  `Task Duration(us)` 一列，`Block Num` 为 64，与向量核数一致。
- 每个用例重复采集 5 轮，表中「实测时间」取 5 轮中位数的中位数，「波动带」取这 5 轮的
  极值。独立重复采集时，各用例的中位数与该表的偏差不超过 3%。

**流水线利用率**

采用 AI Core 的采样剖析（`PipeUtilization`）。采样窗口内只有 1 次预热调用和 2 次被测
调用，两次被测调用前同样清一次 L2，使窗口内的访存状态与计时一致。结果按
`aiv_vec_ratio > 0.15` 区分被测 kernel 与冷启动 kernel（后者只有 0.04 和 0.00），
取被测 kernel 两次稳态采样的平均值。采纳条件：窗口内被测 kernel 的 `aiv_total_time`
与该用例的实测时间相差 10% 以内。

### 绝对性能结果

单位 µs。「实测时间」是 5 轮中位数的中位数，「波动带」是这 5 轮的极值。

| case | T | H | 实测时间 | 波动带 |
| :--- | ---: | ---: | ---: | :--- |
| 512x4096 | 512 | 4096 | 13.133 | 13.058 ~ 13.291 |
| 512x7168 | 512 | 7168 | 20.799 | 20.730 ~ 21.096 |
| 8192x4096 | 8192 | 4096 | 201.490 | 198.760 ~ 204.697 |
| 8192x5120 | 8192 | 5120 | 266.235 | 265.178 ~ 267.466 |
| 8192x7168 | 8192 | 7168 | 380.383 | 379.889 ~ 382.192 |

5 个 case 的 `Block Num` 都是 64，与设备上的向量核数一致。

流量按算子实际读写算，每个词元：

- 读 `4·H·2`（residual，BF16）+ `24·4`（gemm_out_mul，FP32）+ `4`（gemm_out_sqrsum，FP32）；
- 写 `H·2`（layer_input，BF16）+ `4·4`（post_mix，FP32）+ `16·4`（comb_mix，FP32）。

带宽 = 流量 ÷ 实测时间：

| case | 读 (MB) | 写 (MB) | 合计 (MB) | 读带宽 (GB/s) | 合计带宽 (GB/s) |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 512x4096 | 16.83 | 4.24 | 21.06 | 1281 | 1604 |
| 512x7168 | 29.41 | 7.38 | 36.79 | 1414 | 1769 |
| 8192x4096 | 269.25 | 67.76 | 337.02 | 1336 | 1673 |
| 8192x5120 | 336.36 | 84.54 | 420.90 | 1263 | 1581 |
| 8192x7168 | 470.58 | 118.10 | 588.68 | 1237 | 1548 |

**参考带宽**：在同一颗器件上做 1 GiB 连续 BF16 拷贝（读 1 GiB + 写 1 GiB），取 30 次
中的最小值，多次测量为 1401 ~ 1429 GB/s，取 1427.5 GB/s 作为对照。该值是一次**实测
代理**，不是器件规格书中的峰值带宽：平台配置 `Ascend950PR_9589.ini` 只有 `ddr_rate` /
`l2_rate` 这类相对速率，没有 HBM 峰值带宽字段。因此「读带宽」一列是相对该参考值的
指示值。

「合计带宽」一列（1548 ~ 1769 GB/s）高于参考值，原因是部分写回被 L2 吸收、在 kernel
结束前没有真正落到 HBM，按名义写流量算出来的带宽偏高。**读带宽才是有意义的口径**：
1237 ~ 1414 GB/s，相当于参考值的 87% ~ 99%。

### 理论评估对比（主要写 MFU/Bound 情况、利用率）

**Bound 判定：访存受限**

判定访存受限只需要两个可复算的量：要做多少次浮点运算、要搬多少字节。

**浮点运算**集中在最后一步 `layer_input[t,:] = Σ_m residual[t,m,:] × pre[t,m]`：
每个输出元素 4 次乘法 + 3 次加法 = **7 次浮点运算**，整算子 `7 × T × H` 次。

**字节数**在上面列过，换算成「每个输出元素摊到多少字节」（以 `H = 4096` 为例）：

| 口径 | 每个输出元素的字节数 |
| :--- | ---: |
| 只算读 | `4 × 2`（residual）+ `(24 + 4) × 4 ÷ 4096`（mul 与 sqrsum）= **8.02** |
| 读写都算 | 再加 `2`（layer_input）+ `(4 + 16) × 4 ÷ 4096` = **10.04** |

于是算术强度只有：

| 口径 | 算术强度 |
| :--- | ---: |
| 只算读流量 | 7 / 8.02 = **0.87 FLOP / Byte** |
| 算读写总流量 | 7 / 10.04 = **0.70 FLOP / Byte** |

0.7~0.9 FLOP/Byte 是很低的算术强度——搬 1 字节的数据，只做不到 1 次浮点运算。下面的
实测利用率和这个判断一致：大 shape 下搬运管道（MTE2）已经接近饱和，而向量管道还有
大段空余。

**MFU 口径**

MFU 是「实测浮点吞吐 ÷ 硬件峰值算力」的比值，衡量的是算力利用率。本算子的算术强度
只有 0.7~0.9 FLOP/Byte，性能由访存决定，这个比值不反映实现质量，因此不作为评价指标；
与之对应，本报告用有效带宽与搬运管道利用率来刻画实现水平。

与分母无关的一个量是按上面的口径算出的有效浮点吞吐 `7 × T × H ÷ 时间`，5 个用例落在
**1.08 ~ 1.24 TFLOP/s**。它不除以任何峰值，只表示每秒完成的有效浮点运算量。

**流水线利用率实测**

| case | aiv_vec_ratio | aiv_mte2_ratio | aiv_mte3_ratio | aiv_scalar_ratio | 采样到的 kernel 时间 (µs) |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 512x4096 | 0.367 | 0.849 | 0.233 | 0.099 | 13.36 |
| 512x7168 | 0.306 | 0.906 | 0.239 | 0.067 | 21.07 |
| 8192x4096 | 0.341 | 0.963 | 0.316 | 0.020 | 205.06 |
| 8192x5120 | 0.293 | 0.974 | 0.349 | 0.017 | 266.99 |
| 8192x7168 | 0.249 | 0.982 | 0.335 | 0.014 | 386.22 |

读出的结论：

1. **大 shape 的瓶颈是搬入**。8192 三档的 MTE2 已到 96% ~ 98%，基本打满，而向量管道
   只用了 25% ~ 34%。继续优化向量侧（比如再压指令条数）收益很小，能改的只有减少读流量
   或提高搬运效率。
2. **`T=512` 两档是另一种形态**。MTE2 降到 85% ~ 91%，向量管道升到 31% ~ 37%，两者的
   差距明显缩小（大 shape 是 98% 对 25%）。也就是说小规模下搬运不再是唯一的大头，
   启动与定长开销（算系数、算地址）占比上来了——标量占比从大 shape 的 1.4% ~ 2.0% 升到
   6.7% ~ 9.9%。这两档的实测时间不能只用读流量来解释。
3. **标量占比随规模单调下降**（0.099、0.067 → 0.020、0.017、0.014），说明每个词元块里的
   定长开销被摊薄了，核内切分是有效的。

**性能边界**

读 `4·T·H` 个 BF16 由 `layer_input` 的计算定义决定，是流量的下界；MTE2 已达 96% ~ 98%，
接近饱和。本算子的性能上限由残差读带宽决定。
