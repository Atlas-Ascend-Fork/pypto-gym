## 用例

`golden.all_cases()` 定义 **32 个设备场景**：12 个 decode、20 个 prefill，特征维度均为 `(H,R,N,D,Dr)=(5120,1280,64,512,64)`。共 21 个不同的 T，覆盖所列生产矩阵；不是对整数区间 `[1,262144]` 的每个 T 都做了设备测试。

| 阶段 | batch | seq | T | 当前 32 核组上的实际分配 |
| :--- | :--- | :--- | :--- | :--- |
| decode，12 个组合 | 1/4/8/12/16/32 | 1/6 | 1/4/6/8/12/16/24/32/48/72/96/192 | QB 均按 `(tile,head,列块)` 跨核分配；T≤128 时 A1 归约维二分，T=192 时 A1 按单输出块分配 |
| prefill，20 个组合 | 1/4/8/16/32 | 1024/2048/4096/8192 | 1024/2048/4096/8192/16384/32768/65536/131072/262144 | A1 均用两个输出块共享 X；QB 在 T=1024/2048 时跨核分配输出块，T≥4096 的所列场景中按 tile 分配 |

A1 分组条件为 `ceil(T/128)*7>=num_cores`，QB 按 tile 分配条件为 `ceil(T/128)>=32`，两者独立。通用输入的 QB 分界在 T=3969，表中因相邻测试值为 2048、4096，才表现为从 4096 起切换。JSON 字段 `expected_template` 固定将 decode 标作 `split_k`、prefill 标作 `split_t`，它是历史标签，不控制 kernel，也不能据此判断每例真实执行的分支。

输入与比较的构造逻辑如下：

- `SharedWeights` 固定 seed=2026，整轮复用权重；`DeviceWeights` 按设备缓存搬运和 NZ 转换结果，三份权重的准备不在算子内部。
- `make_case_inputs` 按 `seed + batch*100003 + seq` 生成每例输入，x 按块生成 E4M3FN 字节，scale 使用非单位的 2 的幂（默认指数 -2..2），gamma 位于 `[0.75,1.25)`。这样可以检查 scale、分组顺序和逐特征权重是否实际生效。
- RoPE 表按每 batch 的 seq 位置生成；decode 位置位于 `8192-seq .. 8191`，prefill 为 `0 .. seq-1`。位置由输入表表达，不由 cache 地址决定。
- cache 页大小为 128，slot 数为 `(ceil(T/128)+1)*128`；随机置换选择 T 个不同 slot，cache 初值填随机字节，至少一整页保持未命中，用于检查分页写入与越界污染。
- 同 T 的不同 batch/seq 组合采用相同的 kernel 分支和工作量划分，但 seed、位置表和 cache 索引可不同，因此不能把它们当作同一份数值输入。

直接运行 `tests/test_attn_prologue.py` 默认执行完整 32 场景；pytest 只收集 4 个 NPU 冒烟项（T=1/72/1024/2048）与 2 个 CPU 判据项。两个 CPU 入口内部各循环 6 个检查场景，共 12 个内部场景，并非 12 个独立 pytest 项。`--list` 在加载设备依赖之前列出所选场景 JSON；`--unique-t` 可保留每个 T 的首个场景。

CPU golden 自检另在小几何 T=4 和生产几何 T=1 上检查输出形状、dtype 和有限性。小几何只供参考与比较器自检，设备 kernel 的特征维度仍固定。

## 精度标准

**独立参考计算**：`tests/assets/attn_prologue_golden_cpu.py` 仅依赖 CPU torch，不导入 kernel。它用 `ldexp` 解码 E8M0（字节 0 为 `2^-127`），用 `frexp` 求正数的 `floor(log2)`，逐行完成 QA、RMSNorm、动态量化、基于量化 QR 的 QB、尾部 RoPE 和 KV 编码。`golden_chunks` 默认以 256 行分块，遍历完整 T；分块用于控制 CPU 内存，不表示抽样。参考实现按数学表达式计算，不复刻 Cube 的 K0 分块累加顺序。

**完整校验入口**：`tests/assets/attn_prologue_precision.py` 的 `validate_outputs`，最终通过条件由 `Comparison.passed` 定义，报告标识为 `criterion="fp64_value_domain"`。Q 的容差检查与 FP8 的值域复核是两套规则：

1. **Q**：设备 BF16 与 CPU 参考 BF16 都转 FP32 比较。逐元素误差大于 `0.02 + 0.02*abs(ref)` 记为 bad，非有限设备元素也记为 bad；要求 `q_elements>0`、`q_bad/q_elements<=0.001` 且 `q_nonfinite=0`。最大绝对/相对误差只作诊断，不另设最大误差通过门槛。
2. **QR payload、scale 与命中 KV**：先逐字节与 FP32 参考比较。任何 payload 字节差异都会提名所在完整行；QR 的 scale 字节差异也通过 `groups_needing_review` 提名整行，即使 payload 完全相同也不会漏检。`BOUNDARY_REL=1e-5` 用于首轮差异归因，不是最终 FP64 值域判定的浮点容差，也不作为是否提名差异行的必要条件。
3. **被提名行的 FP64 复核**：`FP64Shadow.recompute_full` 从原始输入和权重重算完整 QA 或 KV 行，以 FP64 完成反量化、投影、RMSNorm、量化或位置变换。`_adjudicate_rows` 检查该行所有元素，包含 payload 字节相同但 scale 发生变化的元素。未出现字节差异的行无需再次用 FP64 重算；因此“所有 T 都逐行经过 FP32 首轮检查”不等于“所有行都执行了 FP64 复核”。
4. **未命中 cache**：最后将未被 `cache_index` 选中的所有 slot 与随机初始值逐字节比较，必须 `untouched_bad=0`。

FP64 `adjudicate` 的三类可接受结果直接对应代码中的统计字段：

| 分类 | 判定含义 |
| :--- | :--- |
| `value_identical` | 设备与 FP64 参考的 payload 乘各自 scale 后数值精确相同且有限；包含正负零、不同 scale 下等值的编码 |
| `adjacent_bracket` | scale 相同、两个有限 E4M3 值之间没有其他可表示值，并且 FP64 真值落在二者闭区间内；不额外应用 `1e-5` 中点距离阈值 |
| `own_scale_consistent` | 未满足前两类，但设备 payload 恰等于 FP64 真值按设备所报 scale 重新饱和、舍入后的编码 |

其他元素记为 `hard`；要求 `qr_hard=0`、`kv_hard=0`。`scale_bad`、原始 payload mismatch 和各复核分类是诊断统计，不要求全部为 0。尤其 `own_scale_consistent` 不额外限制设备 scale 与参考 scale 相差多少，不能将当前规则描述为“scale 必须逐字节相同”或“只允许一位编码误差”。这是现有比较器的实际通过范围，不是本次文档新增的容差。

CPU 判据自检包括正负零、不同 scale 下等值编码、相邻值包围真值，以及非相邻错误、错误 scale、NaN 编码；完整校验器还分别注入 Q、QR、scale、命中 KV、未命中 cache 的损坏，并检查能否拒绝。比较器要求提供 FP64 shadow，缺失时直接报错。

## 性能结果

**历史测量口径**：原文环境为 DAV_3510（32 Cube / 64 AIV），CANN 9.3.0、PyTorch 2.12.0+cpu、torch_npu、Python 3.12、设备 1。记录指标为 msprof 导出的纯 NPU `task duration(us)`，排除 CPU 输入准备、编译、host 分配和启动调用耗时。原文说明每个正式样本前用 512 MiB FP16 `ArgMax` 读取冲刷 L2 并同步，3 次预热后采 7 次正式样本取中位数，msprof 每批最多 8 个 case。

### 理论评估对比（MFU / Bound / 利用率）

Bound 表示主要性能限制，MFU（Model FLOPs Utilization）是有效计算吞吐相对于选定理论峰值的比例，roofline 用计算量及数据量估计计算或带宽下界。pipe 占比表示某个执行流水的活跃时间比例，与 MFU、内存带宽利用率均不同。

**已有证据支持的判断**：5 个代表 T 的历史快照中，AIC MTE2 占比为 0.804–0.882，均为最大项，说明应优先关注 GM/L2→L1 的操作数加载；T=4096 的 MAC 占比也达到 0.846，计算与加载都值得关注。没有全部 T 的快照，不能把这 5 点直接写成“全场景都已证明带宽受限”，也不能仅凭占比给出全部等待原因。

逻辑计算量为每 token 102.23616 MFLOP，T=1 的有效吞吐约 2.58 TFLOP/s，T=4096 约 719.0 TFLOP/s。本文缺少对应 SKU、数据类型和运行频率下的 MXFP8 理论峰值依据，因此 **MFU 未计算**，不沿用原文“decode 不足 1%”作为已核实数字。小 T 还存在固定 128 行片上窗口，逻辑有效 FLOP 与实际执行槽位工作量不能混同。

#### 分析过程

**第 1 步：从源码核算算术工作量。** QA、KV、QB 的每 token 乘加数分别为 `H*R`、`H*D`、`R*N*D`，合计 51118080；按一次乘法和一次加法计 2 FLOP，为 102236160 FLOP/token。这个数字不包含 RMSNorm、量化、RoPE，也不把物理尾部槽位算作有效 token 工作。

**第 2 步：明确 MTE2 在读什么。** A1 从 GM 加载 X、scale 和 Wqa/Wkv，再经 L1→L0 做矩阵乘；B 加载量化 QR、scale 和 Wqb。权重物理为 NZ，payload 窗口通过同址 ZN 视图搬给 L0B。所有这些数据经过 AIC MTE2，但一次 GM 访问可能来自 L2，也可能需要 HBM，二者不能仅由 `aic_mte2_ratio` 区分。

**第 3 步：decode 的权重基准量。** 三份 E4M3 payload 为 51118080 B，三份 E8M0 scale 为 1597440 B，共 **52715520 B，约 52.72 MB**。以 T=1 的 39.58 µs 折算为 1.332 TB/s，这是“每调用一份权重”的有效吞吐指标，不是实测 HBM 带宽。A1 归约维二分会重复读取部分权重 scale，X、QR、中间工作区及输出也有额外流量，所以完整 MTE2 字节量略大于该权重基准量。

若采用原文 1.5 TB/s 参照，仅权重对应约 35.14 µs，`39.58/35.14≈1.13`；若再加入原文估计的 4 µs 固定开销，模型为约 39.14 µs，比值约 1.01。这只说明历史数值与该简化模型相近，不足以证明剩余开销无法优化，或把差值全部拆给 launch 与屏障。

**第 4 步：prefill 的权重复读与 QR 复用。** 逐 tile 的 B 分配让每核每 tile 只加载一次 QR，再完成 256 个输出块，但每 tile 仍读取全部三份投影权重。分布式 B 则让多个核组各持有同一 tile 的 QR 副本；32 核组下每组 8 个 QB 输出块，因此 QR 在一个 tile 上可被回读 32 次。T=1024 有 8 tile，但 B 仍由 32 核组共同分配输出块，不是只有 8 个核在执行。

对 T=4096 的完整 32 tile、A1 分组和 B 逐 tile 路径，源码层面的 AIC MTE2 有效字节可计算为：

```text
权重 payload + scale：32 * 52715520                 = 1686896640 B
A1 的 X + scale：     7 * 4096 * (5120 + 160)       =  151388160 B
B 的 QR + scale：     4096 * (1280 + 40)            =    5406720 B
合计                                               = 1843691520 B
```

即约 1.844 GB，未含硬件对齐及缓存事务放大。除以总时长 582.44 µs，为约 3.17 TB/s 的有效加载吞吐。若再用旧快照 0.882 折算 MTE2 活跃时间约 513.71 µs，可得到活跃时段估算约 3.59 TB/s；这种折算依赖统计汇总口径，不是独立测得的总线峰值或每核硬件上限。原文约 1.87 GB 为粗略模型，现按实际 scale 字节数与加载次数校正。

Q 输出在该 T 下为 268435456 B（256 MiB），由 AIV 经 MTE3 写 GM，不能直接计入 AIC MTE2 输入流量。权重重复读取是否全部由 L2 吸收，需 L2 命中率和 HBM 计数器验证；即使总权重小于缓存，也不能从容量关系保证只读一次 HBM。

**第 5 步：结合 pipe 与同步看重叠。** 历史快照 AIV vec 最大 0.183、MTE3 最大 0.194、AIC FIXPIPE 最大 0.096，低于 AIC MTE2；支持在这些代表点优先研究加载。A2 却位于两道全局同步之间，不能与依赖其 QR 的 B 矩阵乘并行，只能与 AIC 对纯权重的预取形成部分重叠。B 与 B-epi 才有逐输出块的双槽握手。

AIC scalar 为 0.207–0.339，低于各点最大 pipe 的一半，支持当时未明显受标量活跃时间主导；不能由此证明不存在发射间隙或等待。四槽权重轮转、两列块共享 X、tile 变化时才加载 QR/位置表，都从源码上减少重复读取或复用依赖；实际收益仍应由同环境对照和时间线确认。

#### 各场景 Bound 归类

| 场景 | 现有证据支持的重点 | 源码与测量依据 |
| :--- | :--- | :--- |
| decode，T≤128 | 权重加载和阶段固定开销 | A1 归约维二分，B 跨核列块分配；T=1/72 的 MTE2 为 0.863/0.862，权重基准量与 T 无关 |
| decode，T=192 | 权重与 QR 的多 tile 复读、同步间的 A2 工作 | A1 按单列块分配，A2 用独立 QR/KV 任务及位置表预载；MTE2=0.830 |
| prefill，T=1024/2048 | AIC 加载与分布式 QR 复读 | A1 分组，B 仍由各核组分配输出块；仅 T=1024 有快照（MTE2=0.804，MAC=0.696），不能给 T=2048 编造具体占比 |
| 所列 T≥4096 的 prefill | 逐 tile 权重读取与 MX 计算均需关注 | T=4096 快照 MTE2/MAC 为 0.882/0.846，结构上 QR 每 tile 驻留一次；更大 T 耗时近线性，但其具体 pipe 与缓存瓶颈需独立采集 |

**测量口径的已知局限**：历史原始附件与采样脚本未随当前目录提供；pipe 只覆盖 5 个 T，没有分核时间线、L2 命中率或 HBM 实际流量，原文“权重 HBM 只读一次”“无发射串行残留”等不能由现有证据确定。后续复测应保存 kernel/test SHA、平台与工具链版本、原始 task 明细，并补采缓存与各核等待；峰值来源齐全后再计算 MFU 和完整 roofline。性能对照应在相近时间窗采集，保持冲刷、预热及统计口径一致。
