# EngramGateBwd 结果说明（RESULTS）

> 实现：`op_kernel/engram_gate_bwd.py`；用例：`tests/test_engram_gate_bwd.py`；
> 精度基准（golden）：`tests/assets/engram_gate_bwd_golden_cpu.py`；精度对比脚本：`tests/assets/engram_gate_bwd_precision.py`。
> 环境：Ascend 950PR（32 AIC / 64 AIV）、CANN 9.2.0、torch_npu 2.8.0。

## 精度标准

用官方 Scheme A（`tests/assets/engram_gate_bwd_precision.py`）。它对每个输出算四条指标，各自比阈值：

| 指标 | 含义 | 通过条件 |
| :--- | :--- | :--- |
| `atol` | 平均绝对误差 | `<= atol` |
| `rtol` | 平均相对误差 | `<= rtol` |
| `matched_ratio` | 满足 `|actual - golden| <= atol + rtol·|golden|` 的元素占比 | `>= 0.99` |
| `max_abs_error` | 最大绝对误差 | `<= max(fixed_limit, 32 ULP)` |

阈值按**实际输出的 dtype** 查表定死，不由调用方传入：BF16 是 `rtol = atol = 2^-6 = 1.5625e-2`、
`max_abs <= 1.0`；FP32 是 `rtol = 2^-10 = 9.766e-4`、`atol = 2^-16 = 1.526e-5`、`max_abs <= 1e-2`。
本算子里 `grad_x` / `grad_key` / `grad_value` 是 BF16，`grad_weight` 是 FP32。

**结果：12/12 PASS。** 下表的每个数都是「实测 / 阈值」，且取该用例四个输出里**最紧**的那条：

| 用例 | `atol` 占比 | `rtol` 占比 | `max_abs` 占比 | `matched_ratio` |
| :--- | ---: | ---: | ---: | ---: |
| `t512_h2048` | 0.076 | 0.001 | 0.031 | 1.0000 |
| `t512_h2560` | 0.076 | 0.001 | 0.016 | 1.0000 |
| `t512_h3072` | 0.084 | 0.002 | 0.016 | 1.0000 |
| `t512_h4096` | 0.068 | 0.001 | 0.016 | 1.0000 |
| `t512_h6144` | 0.082 | 0.003 | 0.016 | 1.0000 |
| `t512_h7168` | 0.070 | 0.003 | 0.016 | 1.0000 |
| `t8001_h2048` | **0.949** | 0.003 | 0.052 | **0.9999** |
| `t8001_h2560` | 0.776 | 0.002 | 0.063 | **0.9999** |
| `t8001_h3072` | 0.643 | 0.003 | 0.031 | 1.0000 |
| `t8001_h4096` | 0.757 | 0.002 | 0.125 | 1.0000 |
| `t8001_h6144` | 0.767 | 0.003 | 0.125 | 1.0000 |
| `t8001_h7168` | 0.651 | 0.002 | 0.063 | 1.0000 |

最紧的一条是 `t8001_h2048` 的 `grad_weight`（FP32）的 `atol`（平均绝对误差）占 **0.949**，
`matched_ratio` 最低 0.9999（阈值 0.99）。仅次于它的是 `grad_key` 的最大绝对误差占 0.125，
其余各项占比都在 0.78 以下（最高的 `t8001_h2560` 的 `atol` 为 0.776），
其中 `rtol` 一项全部在 0.004 以下。
token 数越大越紧，是因为 `grad_weight` 要跨全部 token 累加，误差随 token 数增长。

golden（`tests/assets/engram_gate_bwd_golden_cpu.py`）自身还有一层独立校验，用来保证它不是
「照着 kernel 写的」：它用 `torch.backward` 对正向公式做 **FP64 自动微分**，逐算例比对解析反向；
并检查三条性质：

- `grad_out == 0` → 四个梯度全为 0；
- `value == 0` → `dgate == 0`，于是 `grad_x == grad_out`、`grad_key` 与 `grad_weight` 为 0；
- `image_mask` 全 True → `grad_x == grad_out`，其余为 0。

## 性能结果

**采集口径。** 采用 CANN 官方的 kernel 明细采集方式（`kernel_details`），在单张 Ascend 950PR 上完成：

1. 预热：先以一次大尺寸矩阵乘把频率带到稳态，随后清空 L2 缓存；
2. 测量：以固定的预热步数与测量步数划分窗口，**每个测量步之前清空 L2 缓存**，再调用被测算子，
   使每一次测量都处于冷启动状态；
3. 统计：以清缓存的那一行作为步的分隔符（其自身不计入耗时），先求每个 kernel 在测量步上的中位数，
   再把同一用例各 kernel 的中位数相加；
4. 重复：同一用例独立测量 3 次，取最小值。

下表是本算子 **kernel 本身**的 device 时间（裸 launch，不含 host 侧准备）：

| 用例 | kernel (µs) |
| :--- | ---: |
| `t512_h2048` | 27.91 |
| `t512_h2560` | 31.28 |
| `t512_h3072` | 34.91 |
| `t512_h4096` | 42.82 |
| `t512_h6144` | 65.04 |
| `t512_h7168` | 75.96 |
| `t8001_h2048` | 532.12 |
| `t8001_h2560` | 629.20 |
| `t8001_h3072` | 720.99 |
| `t8001_h4096` | 963.75 |
| `t8001_h6144` | 1446.79 |
| `t8001_h7168` | 1688.72 |

分两档看：512-token 六例 **27.9–76.0 µs**，8001-token 六例 **532.1–1688.7 µs**。
每档内耗时随 `dim` 近似线性（同一个核处理的数据量正比于 `dim`）；跨档则随 token 数增长，
因为每个核要串行处理的 token 数从约 32 涨到约 500。

**测量波动。** 同一用例重复测量的相对偏差约 5%，512-token 档更明显（单次耗时短，固定开销占比更高），
8001-token 档在 1% 以内。因此表中的绝对值用于量级与趋势判断；比较实现之间的差异，应在同一轮测量内进行。

### 绝对性能结果

调用方实际拿到的是公开 wrapper：除裸 kernel 外，它还包含两个 host 侧准备 kernel，
在 kernel 明细中可以分别观察到：

- `aclnnCat_ConcatD`：把正向保存的四行（`raw_dot`/`gate`/`rstd_x`/`rstd_k`）打包成 `[t, 4*hc]`，约 3.5–4.5 µs；

### 理论评估对比

**访存量与计算量（解析）。**

算术强度 = 每从显存搬 1 字节数据、做多少次浮点运算。它决定了算子受限于搬数据还是受限于算：
强度低说明搬进来的数据还没来得及算几回就要换下一批，瓶颈在搬运。

按 `hc = 4` 逐 token 计（每个 `(token, head)` 行读 1 行 `x`、1 行 `key`、1 行 `grad_out`
（另三个 head 的 `grad_out` 只在 v 片上被读到，属于同一批行的重复读，按"唯一"口径只算一次）、
`value` 行按 token 共享；写 1 行 `grad_x`、1 行 `grad_key`、`value` 行按 head 切分）：

```text
唯一读  = 13 行 × dim × 2 B（bf16）
唯一写  =  9 行 × dim × 2 B
等效运算 = 59 × dim FLOPs   （每个 (token, head)：S1 归约 2·dim、S3 grad_value 1.75·dim、S4 主扫 11·dim；
                              每 token 有 4 个 head。只数向量乘/加，不数类型转换。）
```

| 用例 | 唯一读 (MB) | 唯一写 (MB) | 合计 (MB) | 等效运算 (GFLOP) | 算术强度 (FLOP/B) |
| :--- | ---: | ---: | ---: | ---: | ---: |
| `t512_h2048` | 27.3 | 18.9 | 46.1 | 0.06 | 1.34 |
| `t512_h2560` | 34.1 | 23.6 | 57.7 | 0.08 | 1.34 |
| `t512_h3072` | 40.9 | 28.3 | 69.2 | 0.09 | 1.34 |
| `t512_h4096` | 54.5 | 37.7 | 92.3 | 0.12 | 1.34 |
| `t512_h6144` | 81.8 | 56.6 | 138.4 | 0.19 | 1.34 |
| `t512_h7168` | 95.4 | 66.1 | 161.5 | 0.22 | 1.34 |
| `t8001_h2048` | 426.0 | 294.9 | 721.0 | 0.97 | 1.34 |
| `t8001_h2560` | 532.5 | 368.7 | 901.2 | 1.21 | 1.34 |
| `t8001_h3072` | 639.1 | 442.4 | 1081.5 | 1.45 | 1.34 |
| `t8001_h4096` | 852.1 | 589.9 | 1442.0 | 1.93 | 1.34 |
| `t8001_h6144` | 1278.1 | 884.8 | 2163.0 | 2.90 | 1.34 |
| `t8001_h7168` | 1491.1 | 1032.3 | 2523.5 | 3.38 | 1.34 |

算术强度与形状无关，恒为 **1.34 FLOP/B**，也就是每搬 1 字节只做约 1.3 次浮点运算。

**Bound 判定（来自官方 profiler 的 pipe 利用率）。**

判据来自官方 profiler 的 `kernel_details.csv`：每个 kernel 都会给出
`aiv_vec_ratio` / `aiv_mte2_ratio` / `aiv_mte3_ratio` / `aiv_scalar_ratio`
（各 pipe 忙碌时间 ÷ kernel 时间；MTE2 = GM→UB 搬入，MTE3 = UB→GM 搬出，V = 向量计算）。
下表是 12 例全量的实测值，每个用例 5 个测量 step 各出一行、取中位。
其中「kernel」列是**单次测量的步中位数**，与「性能结果」的「3 次测量取最小值」口径不同，
所以同一用例在两处的 kernel 时间会有几个百分点的差别；pipe 占比是比值，不受这个口径影响：

| 用例 | kernel (µs) | V 向量 | MTE2 搬入 | MTE3 搬出 | Scalar |
| :--- | ---: | ---: | ---: | ---: | ---: |
| `t512_h2048` | 27.9 | 37.0% | **56.6%** | 36.0% | 19.6% |
| `t512_h2560` | 31.4 | 39.7% | **54.3%** | 33.7% | 17.8% |
| `t512_h3072` | 34.9 | 42.1% | **54.7%** | 31.5% | 15.7% |
| `t512_h4096` | 44.9 | 41.9% | **58.9%** | 26.7% | 12.2% |
| `t512_h6144` | 63.7 | 43.3% | **61.6%** | 21.9% | 8.3% |
| `t512_h7168` | 74.8 | 42.2% | **65.0%** | 20.0% | 7.5% |
| `t8001_h2048` | 525.1 | 29.1% | **71.9%** | 27.7% | 10.5% |
| `t8001_h2560` | 626.4 | 29.6% | **71.7%** | 24.2% | 8.8% |
| `t8001_h3072` | 726.4 | 30.4% | **72.6%** | 23.8% | 7.7% |
| `t8001_h4096` | 963.2 | 29.6% | **74.5%** | 33.8% | 5.8% |
| `t8001_h6144` | 1450.6 | 28.6% | **75.3%** | 42.3% | 3.9% |
| `t8001_h7168` | 1689.7 | 28.1% | **75.8%** | 44.0% | 3.3% |

**结论：kernel 由 MTE2（搬入）主导** —— 12 例里 MTE2 占比 54.3%–75.8%，是唯一始终最大的 pipe；
向量计算只占 28.1%–43.3% 的时间，`cube_utilization = 0%`
（本算子不含矩阵指令）。这是本设计的预期形态——算子本身几乎没有计算，代价全在把
`grad_out`/`x`/`key`/`value` 搬进来、把三个梯度搬出去。

**算力上限、访存上限与 roofline。**

- **向量算力上限**：AIV 主频由官方计数器推出——`aiv_total_cycles ÷ aiv_time ÷ 64 核` ≈ **1.64 GHz**；
  fp32 寄存器 64 通道，一次 FMA 2 FLOP，故单核 64×1.64e9×2 ≈ 210 GFLOP/s，
  64 核合计 **≈ 13.4 TFLOP/s**。
- **访存上限**（同口径实测，3 次测量取最快值）：

  | 参照 | 实测 | 带宽 |
  | :--- | ---: | ---: |
  | `fill_` 1 GiB（纯写） | 584.8 µs | 1.836 TB/s（写） |
  | `copy_` 1 GiB（读+写） | 1404.3 µs | 1.529 TB/s（读+写合计） |
  | `cann_bench_cache_clean` 192 MiB（纯读） | 119.6 µs | 1.684 TB/s（读） |

  纯读参照取自大样本中的最快值，作为读侧上限的量级参照；实际可达带宽随系统负载变化。

- **Ridge point** = 13.4 TFLOP/s ÷ 1.53 TB/s ≈ **8.8 FLOP/B**（拐点：强度低于它就该受限于访存）。
  本算子算术强度 **1.34 FLOP/B**，只有拐点的 **15%** → **落在明显的访存受限区**：
  向量单元只需发挥约 15% 的峰值算力就能跟上访存，与「Bound 判定」的 pipe 数据（V 28%–43%、MTE2 54%–76%）一致。

| t512_h3072 | 1.171 | 69.6% | 0.811 | 44.2% |
| t512_h4096 | 1.273 | 75.6% | 0.882 | 48.0% |

读利用率上限 **75.6%**、写上限 **48.0%**（相对上表的最快值参照）。若按读侧参照的常见区间
（约 1.0–1.7 TB/s）衡量同一组数据：512-token 档的 1.26–1.27 TB/s 已接近读侧上限，
8001-token 档的 0.88 TB/s 仍有余量；写侧利用率 30%–48%，余地大于读侧。

8001-token 档的等效带宽明显低于 512-token 档，说明 token 数变大后
**单位数据可分摊到的并行与流水深度不足**（每个核需串行处理约 500 个工作项）。

**小结。**

- **形态**：访存受限（算术强度 1.34 FLOP/B，远低于拐点 8.8 FLOP/B），官方 pipe 数据亦显示
  MTE2 搬入占 54%–76%。
- **512-token 档**：等效读带宽 1.26–1.27 TB/s，接近读侧实际上限，余量有限；
- **8001-token 档**：0.88 TB/s，约为 512-token 档的七成；原因是每个核需串行处理约 500 个工作项，
  单位数据可分摊到的并行与流水深度不足。
