# engram_gate 设计说明

> 算子本体：`op_kernel/engram_gate.py`；参考实现与精度比较器：`tests/assets/`。
> 运行平台：Ascend 950PR（平台信息里 `soc_version = 'DAV_3510'`），cube（矩阵计算单元）
> 32 核 / vector（向量计算单元）64 核，UB（片上统一缓冲）容量 256 KiB。

## 1 计算阶段划分

算子的全部工作由**一个** kernel 完成，跑在 AI 向量核（AIV）上，最多可铺开到 64 个核；
每个核负责若干 `(token, head)` 行，**一次只处理一整行**：先把这一行的 `x`、`key` 搬进片上，
在这一行内算出两路 RMS 统计量和加权点积，得到这个行的 `gate`，再用同一个 `x` 行和
`value` 行算出 `y = x + gate·value`，写回全局内存。实际起核数随形状变化，见第 2 节。

之所以把四步合成一趟：分开做时，RMS 这一步要读一遍 `x` 与 `key`，残差更新这一步还要
再读一遍 `x`、再读一遍 `value`，中间的统计量也要往返全局内存。融合后每个 `(token, head)`
行的 `x`、`key`、`value` 各只搬进片上一次、`y` 只写一次，中间的统计量也不再往返全局内存
——从 HBM 取的唯一字节数已经压到公式本身需要的最小流量。`value` 由同一 token 的 `hc` 个
head 各搬一次、`weight` 由每个核搬自己绑定那一行，这两处重复下发就是 `RESULTS.md` 流量表
里「发出的读写」比「HBM 流量」多出来的部分。

代价是**行内串行**：`pass1` 与 `pass2` 读的是同一块 UB 行（这正是整行驻留的意义），
所以同一行的两趟不能重叠。行与行之间则可以重叠，见第 5 节。

```text
[一次性，每个核一次]  载入 weight 的 wcore = core % hc 这一行到 UB

[每个 (token, head) 行]
  ┌ 直通分支（image_mask[token] == True）
  │   搬入 x 行 → 原样搬出到 y 行，不做任何数值计算
  └ 计算分支（image_mask[token] == False）
      阶段 A  pass1：沿 dim 逐段（每段 64 个元素）累加 Σx²、Σkey²、Σ(x·w·key)
      阶段 B  标量链：rstd → dot → gate（sigmoid）
      阶段 C  pass2：读回同一块 UB 行的 x 与 value，算 y = x + gate·value，打包成 BF16 写回
```

阶段 A、C 是唯一有数据量的部分（各读 `dim` 列），阶段 B 只涉及几个标量。

**与数据相关的分支不进入向量函数**：`image_mask` 的判断在 kernel 主体里用标量完成
（`pl.getval(image_mask, token)`），两条分支各是一段直线代码。向量函数 `engram_gate_vf`
内部只有两趟满段循环加 `tail != 0` 引出的尾段补丁（`pass1`、`pass2` 各一处），这个判断按
整行统一生效（要么整行按尾段处理，要么整行跳过），不产生逐个元素的条件选择。

阶段 B 的标量链按功能说明里的公式逐步展开：

```text
xrms = sqrt(Σx²/dim + eps)          krms = sqrt(Σkey²/dim + eps)
nd   = (Σ(x·w·key) · (1/√dim)) / (xrms · krms)
mag  = sqrt(max(|nd|, clamp_value))     符号取自 nd     →  signed_root
gate = 1 / (1 + exp(-signed_root))
```

这套中间量就是 `README.md` 功能说明那四行公式的逐步展开：`nd` 对应那里的 `dot`
（`rstd = 1 / (xrms · krms)`），`signed_root` 对应 `copysign(√max(|dot|, clamp_value), dot)`，
`gate` 则写成 `1 / (1 + exp(-x))` 的形式。

`eps` 与 `clamp_value` 是编译期立即数，因此 wrapper 只接受默认值 `1e-6`。

## 2 核间切分策略

- 起核数 `block_dim = min(向量核数, t · hc)`，再向下取整到 `hc` 的倍数。取整是必须的：
  token 维按 `hc` 个一组分配，核数不是 `hc` 的整数倍就会有 token 没人处理。
  这个式子要求 `hc ≤ 向量核数`（本平台 64），否则取整后 `block_dim` 为 0；超出时运行时会报错。
- **head 维固定绑定**：核 `c` 永远处理 head `c % hc`。这样每个核只需要常驻**一行**
  `weight`（`hc × dim` 里的一行），不必按 token 反复换 weight。
- **token 维按网格步长分配**：令 `nc = block_dim`、`dtok = nc / hc`，核 `c` 处理
  token 序列 `c / hc, c / hc + dtok, c / hc + 2·dtok, …`（`/` 是整数除法）。
  相邻的 `hc` 个核共享同一个 token 起点，分别负责不同的 head；跨组之间按固定步长跳。
- 分配是均匀的：行数 `t · hc` 被切成 `nc` 份，各核拿到的行数最多相差 1。

各用例的实际起核数：

| 用例 | t | hc | `t·hc` | 起核数 | `dtok` | 每核行数 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| `partial_image_mask` | 5 | 4 | 20 | 20 | 5 | 1 |
| `model_token_count_nomask` | 72 | 4 | 288 | 64 | 16 | 4 ~ 5 |
| `chunked_one_chunk_tail_one` | 3 | 4 | 12 | 12 | 3 | 1 |
| `model_dim_plus_one_partial_mask` | 5 | 4 | 20 | 20 | 5 | 1 |
| `compile_default_shape` | 2 | 4 | 8 | 8 | 2 | 1 |

只有 `model_token_count_nomask` 能把 64 个向量核喂满；其余四个用例的规模本身就小于
核数，属于「一个核一行」的形态（这也解释了 `RESULTS.md` 里它们的时间量级相近）。

## 3 核内切分策略

### 3.1 基本块的选择

| 维度 | 取值 | 选择依据 |
| :--- | :--- | :--- |
| 基本块 | 一个 `(token, head)` 行 | 行的所有中间量（`x`、`key`、`value`、`y`、统计量）都在片上，两趟计算复用同一块数据 |
| UB 行宽 `CHUNK` | 8512（编译期常量） | 取用例里最大的 `dim`（8449）向上取整到 64 的倍数：`ceil(8449/64)·64 = 133·64 = 8512`，留出余量并与行内分段（64）对齐；`CHUNK` 同时就是 `dim` 的上限 |
| 行内分段 | 64 个元素一段 | 一段正好装进一个 FP32 向量寄存器，段内每步运算对应一条向量指令 |
| 满段数 `n_full` | `dim / 64`（截断） | 满段走无掩码的快循环 |
| 尾段 `tail` | `dim % 64` | 不足 64 个元素的尾巴用掩码单独处理，避免越界 |

`n_full` 与 `tail` 都由运行时的 `dim` 推出：`dim` 是 64 的倍数时尾段为空，
`dim = 8449`、`5121` 这类非 64 倍数时尾段为 1。

### 3.2 核内 Buffer 划分

全部 tile 都在 UB 里（tile 指片上的一块数据缓冲），地址是**静态字节偏移**（编译期算好，
运行时不改）：

| 缓冲 | 形状 / 类型 | 起始字节 | 槽数 | 用途 |
| :--- | :--- | ---: | ---: | :--- |
| `ux` | `[1, 8512]` BF16 | 0 | 3 | `x` 行，`pass1`/`pass2` 共用 |
| `uk` | `[1, 8512]` BF16 | 51072 | 3 | `key` 行 |
| `uv` | `[1, 8512]` BF16 | 102144 | 3 | `value` 行 |
| `uw` | `[1, 8512]` FP32 | 153216 | 1 | `weight` 行（本核绑定的 head），常驻 |
| `uo` | `[1, 8512]` BF16 | 187264 | 3 | `y` 输出行 |

一行 BF16 是 `8512 × 2 = 17024` 字节（代码里的 `S_BF`），一行 FP32 是
`8512 × 4 = 34048` 字节。三槽布局的总占用：

```text
4 组 × 3 槽 × 17024 + 34048 = 238336 字节 ≈ 232.75 KiB
```

UB 有 256 KiB，占用约 91%。**槽数取 3 是容量允许的最大值**：改成 4 槽需要
`4 × 4 × 17024 + 34048 = 306432` 字节 ≈ 299 KiB，编译时就会被拦下——编译器报的是
`Tile addr ... + size ... exceeds Vec capacity 0x40000 (262144 bytes)`，
`0x40000` 就是这台机器 UB 的实际容量。

`uw` 只留一槽且 `depth = 1`：它在 token 循环开始前载入一次，之后只读不写。

### 3.3 寄存器布局

一个 FP32 向量寄存器是 64 lane 宽（lane 指一个向量寄存器里并列的通道，本平台一个 FP32
向量寄存器有 64 个，也就是能同时算 64 个元素），正好覆盖行内的一段：

| 寄存器 | 用途 |
| :--- | :--- |
| `x` / `k` / `w` | 本段的 `x`、`key`、`weight`（BF16 搬入时展开成 FP32） |
| `tmp` | `x·w` 的中间积，随后与 `k` 做融合乘加累加进 `a_dot` |
| `a_x2` / `a_k2` / `a_dot` | 三路统计量的累加器，段与段之间保持存活 |
| `mt` | 尾段掩码（前 `tail` 个元素有效，其余置零） |
| 标量链寄存器 | `xrms`、`krms`、`nd`、`mag`、`gate` 等，都只用一个寄存器行 |

满段用 `mul_add_dst` 直接累加（`a_x2 += x·x`、`a_k2 += k·k`、`a_dot += (x·w)·k`），
不需要额外掩码；尾段改用「掩码乘积 + 一次全掩码加法」两步完成。

三路统计量各自只有一个累加器：同一行内 `a_x2` 的相邻两次更新存在写后读依赖。不过满段循环
每段有 9 条指令（3 条取数、2 条 BF16→FP32 展开、4 条乘加），三条累加只占其中 3 条；
`model_token_count_nomask` 已达到同机参考带宽的 95.6%（见 `RESULTS.md` 第 3 节），说明它
受 HBM（片外显存）带宽限制，而不是受这条依赖链限制。

## 4 接口选择

| 环节 | 用法 | 理由 |
| :--- | :--- | :--- |
| 全局内存 ↔ 片上 | `pl.load` / `pl.store` + `pl.set_validshape` | 有效形状夹到真实列数 `dim`，只搬需要的列，不搬 `CHUNK` 的余量 |
| 片上 ↔ 寄存器 | `vf.load_align` / `vf.store_align` | 行内按 64 个元素对齐寻址，一段一条指令 |
| BF16 展开 | `LoadDist.UNPK_B16` | 搬入时顺带把 BF16 展开成 FP32，省掉一趟独立转换 |
| BF16 打包 | `StoreDist.PACK` | 先在寄存器里取整成 BF16、`bit_cast` 成 `uint32`，再由 `store_align` 打包写回，省掉一趟独立转换 |
| 取整口径 | `vf.astype` + `CAST_RINT` | 就近取整到偶数，与 CPU 参考实现的舍入口径一致 |
| 融合乘加 | `vf.mul_add_dst` | `dst += a·b` 一条指令完成，`pass1` 的三路统计量都用它累加 |
| 行内归约 | `vf.reduce_sum` | 把 64 个元素的累加器归约成一个标量 |
| 尾段掩码 | `vf.update_mask` | 只让前 `tail` 个元素有效，其余置零 |
| 符号处理 | `vf.lt` + `vf.select` + `vf.muls` | 实现 `copysign`：按 `nd` 的正负在 `±mag` 之间二选一 |
| 门控标量链 | `vf.exp` / `vf.add` / `vf.div` / `vf.sqrt` / `vf.adds` / `vf.maxs` | sigmoid 与 RMS，逐条对应功能说明里的公式 |
| 标量广播 | `vf.full` | 把一个值灌满整个寄存器行：累加器清零、广播常数 `1.0` 与运行时的 `dim`，以及在 `pass2` 之前把标量 `gate` 扩成整行供逐元素相乘 |
| tile 与同步 | `pl.make_tile_group` + `auto_mutex` | 槽位轮转的互斥由互斥信号量 ID 自动管理，代码里不写显式同步 |
| 平台信息 | `get_platform_info().vector_core_num` | 起核数从平台问，不写死 64 |

## 5 流水设计

### 5.1 weight 只搬一次

`uw` 在 token 循环**外面**载入：每个核只需要自己绑定 head 的那一行 `weight`，
整个循环期间常驻 UB、只读不写。若把它放进循环里，每个核每处理一个 token 都要重新搬一次
这一行；放到循环外后每个核只搬一次。

### 5.2 三槽轮转，让行与行重叠

`ux` / `uk` / `uv` / `uo` 各有 3 个槽，按 `slot % 3` 依次轮转，每个槽带自己的互斥
信号量 ID。连续 3 次循环迭代落在 3 个不同的槽上，每行都有自己的缓冲，不必等上一行算完
才能开始下一行的搬运。多行并发的收益体现在带宽受限的那个用例上：它的有效带宽达到同机
参考带宽的 95.6%（见 `RESULTS.md` 第 3 节）。

同一个 token 内部是不能重叠的：`pass2` 要读 `pass1` 搬进来的那一行 `x`，
所以行内顺序固定为「搬入 → 向量计算 → 搬出」。

### 5.3 满段快循环 + 尾段补丁

`pass1` 与 `pass2` 的主体都是无掩码的满段循环：`pass1` 每段是一串乘加累加，三路累加都用
`mul_add_dst`；`pass2` 每段是「乘 + 加 + 取整打包」。只有 `dim` 不是 64 的倍数时才多跑一段
带掩码的同款逻辑，这样绝大多数段上没有掩码开销。

### 5.4 分支的代价被隔离

直通 token（`image_mask == True`）只做「搬入 `x` → 搬出 `y`」，不进入向量函数，
`key` 与 `value` 也不搬（`weight` 在 token 循环外只载入一次，与走哪条分支无关）。
分支判断用的是标量 `pl.getval`，向量函数保持直线代码。

最后一步是编译期与运行时的分工。`CHUNK`、`eps`、`clamp_value` 是编译期常量，它们决定
UB 的字节布局、掩码宽度和标量链里的立即数；而 `t`、`hc`、`dim` 全部是运行时动态轴——
本算子**只有一个** `@pl.jit` kernel 定义，形状不进编译期签名，换形状不需要重新编译。
`n_full`、`tail`、`dtok` 这些由形状推出的量都在运行时求得，上面几个小节的循环边界与
尾段分支按运行时值走。

代价是满段循环的次数是运行时值，尾段掩码的宽度也随 `tail` 在运行时变化；收益是任意形状
共用一个已编译的 kernel，省掉了形状种类多时的一次性编译开销。
