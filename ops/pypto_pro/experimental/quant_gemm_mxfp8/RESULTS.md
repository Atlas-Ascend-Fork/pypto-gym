## 用例

用例覆盖支持域内的边界组合，并覆盖 `InputFormat`（E5M2 / E4M3FN）、`HasBias`（有 / 无）与 `WeightNz`（ND / WeightNZ）三个 tiling 维度的全部取值。

**功能与精度用例（16 个 shape）**，按所验证的边界分组：

| 组                       | shape `(M,N,K)`                                   | 覆盖的边界                                                                |
| :----------------------- | :-------------------------------------------------- | :------------------------------------------------------------------------ |
| 基线                     | `(96,256,256)` ×2                                | 单个完整输出块；带 / 不带 bias                                            |
| 单步 K                   | `(16,32,128)`、`(96,256,128)`                   | `K == G_BK`，整个归约只有一步；前者 M、N 各为一个 16 宽 fractal         |
| M 与 N 同时尾块 + K 尾窗 | `(50,100,384)` ×2、`(97,257,1152)`             | `vm = 50 / 1`、`vn = 100 / 1`；`K = 1.5 / 4.5 × G_KL1`；两种 dtype |
| M 跨多块                 | `(200,300,640)`、`(192,512,512)`                | `200 = 2×96 + 8` 有尾块、`192 = 2×96` 无尾块                        |
| K 跨 scale 窗口          | `(96,1024,5120)`、`(96,256,4224)`               | 两个 scale 窗口（`4096 + 1024`、`4096 + 128`）                        |
| 多轮 grid-stride         | `(1536,1024,128)`                                 | 64 个输出块 / 32 核 = 2 轮                                                |
| WeightNZ                 | `(96,288,256)`、`(96,256,256)`、`(96,32,256)` | N 尾块（`288 = 256 + 32`，仍 32 对齐）、满块带 bias、32 列 fractal 下界 |
| Profile 选择校验 | `(96,1792,5120)` | 该 shape 必须仍选 Profile 0（split-K），见 [DESIGN.md](DESIGN.md) 的 Profile 选择警告 |

| 1       | `(96,32768,1280)` | A 常驻 + 4 轮                      | `AI_CORE` / 32 块            |
| 2       | `(96,5120,8192)`  | 滑动窗口                           | `AI_CORE` / 20 块            |

## 精度标准

golden 是**独立的 CPU FP64 参考**：按 `y = (x1 × 2^(sa−127)) @ (x2 × 2^(sb−127))^T + bias` 逐元素计算，再按 round-to-nearest-even 舍入到 BF16。它与设备实现不共享任何代码路径。

判定门限（`tests/assets/` 下的 `compare`，返回 `count == 0`）：

| 判据         | 要求                                                                             |
| :----------- | :------------------------------------------------------------------------------- |
| 逐元素误差   | `\|Pro − golden\| ≤ atol + rtol × \|golden\|`，`atol = 1e-3`、`rtol = 8e-3` |
| 超门限元素数 | **必须为 0**（不允许任何单个元素超门限）                                   |
| 有限性       | 输出与 golden 均无非有限值；NaN/Inf 一律计为超门限                               |
| 形状         | 与 golden 完全一致                                                               |

`max_abs`、`max_rel`、`RMSE` 由测试打印，但**只是诊断量、不参与判定**。其中 `max_rel` 按 `|Pro − golden| / |golden|` 计算，当 `|golden|` 很小而绝对误差仍落在 `atol` 内时，它可以远大于 `rtol`——实测最大到 0.52，而同一用例的超门限元素数为 0。因此不能把 `max_rel ≤ rtol` 当作判据。

**实测结果**：34 个用例（16 个功能 shape + 18 个性能 shape）、合计 **25,046,225** 个输出元素，**超门限元素 0 个**，无非有限值。

| 用例集                 | 例数 |   元素合计 |      超门限 | `max_abs` 最大 | `RMSE` 最大 |
| :--------------------- | ---: | ---------: | ----------: | ---------------: | ------------: |
| 功能与精度（16 shape） |   16 |  2,190,545 | **0** |                4 |        0.0166 |
| 性能（18 shape）       |   18 | 22,855,680 | **0** |               16 |        0.0335 |

按 shape 拆分，三个 profile 的性能用例元素数分别为 `96x1792x5120` 1,032,192、`96x32768x1280` 18,874,368、`96x5120x8192` 2,949,120，超门限均为 0。`max_abs = 16` 出现在输出量级本身较大的用例上（该处 `|golden|` 同量级，故仍满足 `atol + rtol×|golden|`）。

Profile 0 的 split-K 路径把 K 切成 4 段分别累加、再由 56 个 AIV 按 `((p0+p1)+p2)+p3` 归并，其 FP32 累加分组与单 worker 端到端归约不同，因此末位 BF16 舍入可能不同。这不影响上述门限判定（该 shape 的 1,032,192 个元素全部通过），但意味着**累加顺序是数值契约的一部分**，改动 profile 选择会改变位级结果（见 [DESIGN.md](DESIGN.md) 的 Profile 选择警告）。

**绝对耗时的不确定度**：四次独立采集之间，同一用例的绝对耗时相对极差中位 **2.13%**、最大 **5.18%**（36 组）。这是本节的测量不确定度，上表的中位数应在此幅度内理解。

### 理论评估对比（MFU / Bound / 利用率）

#### 分析过程

访存下界 `t_est = 实际流量 ÷ 带宽参照`：

| Profile |  实际流量 | `t_est` |   实测中位 |     `t/t_est` | 带宽利用率 |
| :------ | --------: | --------: | ---------: | --------------: | ---------: |
| 0       | 15.825 MB | 11.06 µs | 12.960 µs | **1.171** |      85.4% |
| 1       | 49.803 MB | 34.82 µs | 38.187 µs | **1.097** |      91.2% |
| 2       | 45.068 MB | 31.51 µs | 35.537 µs | **1.128** |      88.7% |

**Profile 1 与 2 已贴近访存 roofline**：`t/t_est` 分别为 1.097 与 1.128，`mte2_ratio` 均为 0.9530，`η_tail = 1`、`A = 1.0`，即没有流量放大也没有核间浪费，剩余 10%–13% 的超出量属于流水填充与首尾非重叠段落。两者的 `mac_ratio` 只有 0.2890 / 0.4800，远低于 1，说明 Cube 阵列大部分时间在等数据，算力不构成约束。

Profile 2 与 Profile 1 的 FLOP 完全相同（8.0531 GFLOP）耗时却更短（35.537 对 38.187 µs），差值来自少读约 4.7 MB 权重（45.068 对 49.803 MB）——这直接印证瓶颈在带宽而非算力。Profile 2 的 `mac_ratio` 最高（0.4800）而 `cube_utilization` 最低（61.10%），因为它的 `K = 8192` 最长、单块工作量最大，但只启动 20 块（`N/BN = 20 < 32`），有 12 个 AIC 无工作可做。

**Profile 0 属固定开销受限，不属访存受限**。它的规模太小（1.7616 GFLOP、10.320 MB 逻辑流量），实测 12.960 µs 中无法用带宽解释的部分取决于 2.75 MB workspace 有多少命中 L2：

| 假设                  |   GM 流量 | `t_est` | 无法用带宽解释的部分 | 占实测 |
| :-------------------- | --------: | --------: | -------------------: | -----: |
| workspace 全部落 HBM  | 15.825 MB | 11.06 µs |             1.90 µs |    15% |
| workspace 全部命中 L2 | 10.320 MB |  7.22 µs |             5.74 µs |    44% |

2.75 MB 远小于 128 MiB 的 L2，具备较好的缓存复用条件，但**实际命中率未测**（无计数器），故本文只给区间不给单值。无论取哪一端，`t/t_est` 都在 1.171–1.795 之间，且 `mte2_ratio` 只有 0.5885、`η_tail = 0.875`、`A = 1.53`，三项都指向同一结论：该 shape 的耗时由 split-K 的结构性开销（workspace 往返、全 AIC FIX 屏障、56 个 AIV 的归并段、4 个空闲块）主导，而不是由 GM 带宽主导。split-K 换来的是 Cube 占用从 7/32 提到 28/32——若不分片，7 个输出块只能占用 7 个 AIC。

#### MFU

MFU（Model FLOPs Utilization）= 有效计算吞吐 ÷ 硬件理论算力峰值。它与本文另外两个利用率是**不同的量**：「带宽利用率」以实测可达带宽为分母，profiler 的 `mac_ratio` 是 MAC pipe 的活跃时间占比，三者不可互相代替。

**峰值来源**。平台常量取本机安装态 `framework/src/platform/parser/simulation_platform/platform_config/Ascend950PR_9589.ini`，逐项核对：

| 常量                  | 值             | ini 位置                                        |
| :-------------------- | :------------- | :---------------------------------------------- |
| Cube 分形 `M×N×K` | `16×32×16` | `[DtypeMKN]` 的 `DT_FLOAT8_E4M3FN=16,32,16` |
| `cube_core_cnt`     | 32             | `[AICoreSpec]`                                |
| `cube_freq`         | 1650 MHz       | `[AICoreSpec]`                                |

`峰值 = M·N·K × 2 × cube_core_cnt × cube_freq = 16×32×16 × 2 × 32 × 1.65×10^9` = **865.08 TFLOP/s**（FP8 dense，一次乘加计 2 FLOP）。

MXFP8 用的是同一个 Cube 单元：`[AICoreintrinsicDtypeMap]` 中只有 `Intrinsic_mmad`（其 dtype 组合含 `e4m3e4m3`、`e4m3e5m2`、`e5m2e4m3`、`e5m2e5m2`）与 `Intrinsic_mmad_sp`（仅 s8），**没有 MX 专用 intrinsic**；`[AICoreSpec]` 的 `l0_a_mx_size = l0_b_mx_size = 4096` 与 `bt_size = 4096`，正是本实现 MX scale plane（每槽 2048 字节 × 2 槽）与 BiasTable 所用的那两个独立平面。E8M0 分组反量化由 `matmul_mx` 在 Cube 内联完成，不额外占用 MMAD 周期。

**MFU 的带宽上限**。本机 roofline 拐点 = `865.08 TFLOP/s ÷ 1.4305 TB/s = 604.7 FLOP/B`。三个 profile 的算术强度（111.3 / 161.7 / 178.7 FLOP/B）**全部远低于拐点**，因此 MFU 被算术强度而非实现质量封顶：

| Profile |     算术强度 | 占拐点 | 带宽上限（绝对） | 带宽上限 MFU | 实测 MFU | 达上限 |
| :------ | -----------: | -----: | ---------------: | -----------: | -------: | -----: |
| 0       | 111.3 FLOP/B |    18% |    159.2 TFLOP/s |       18.41% |   15.71% |  85.4% |
| 1       | 161.7 FLOP/B |    27% |    231.3 TFLOP/s |       26.74% |   24.38% |  91.2% |
| 2       | 178.7 FLOP/B |    30% |    255.6 TFLOP/s |       29.55% |   26.20% |  88.7% |

「达上限」一列与「绝对性能结果」里的带宽利用率数值相同，这是恒等式而非巧合：`MFU ÷ 上限 = (FLOP/t) ÷ (AI × BW) = bytes ÷ (t × BW) = t_est ÷ t`，可用作内部一致性校验。

由此，**提高 MFU 的唯一途径是提高算术强度**——增大 tile 以复用操作数、或让同一份权重被更多输出块共享（Profile 1 的 A 常驻已把 A 的读取量降到 1/4，这正是它 `t/t_est` 最低的原因）。在算术强度不变的前提下，继续优化搬运与流水最多把耗时压到各自的 `t_est`，即**提速 17.2%（P0）/ 9.7%（P1）/ 12.8%（P2）**，MFU 相应升到 18.41% / 26.74% / 29.55% 的上限。注意这里的提速幅度与「达上限」比例互为倒数关系（如 P1 的 `1/0.912 = 1.097`），不是同一个数。

**Profile 0 的上限有一个未测区间**。它的算术强度取决于 2.75 MB workspace 往返有多少真正落到 GM：全部落 HBM 时实际流量 15.825 MB、算术强度 111.3、上限 MFU 18.41%（实测达 85.4%）；全部命中 L2 时 GM 流量只有逻辑的 10.320 MB、算术强度 170.7、上限 MFU 28.23%（实测达 55.7%），但此时绑定资源已变成 L2 带宽，而 **L2 带宽未测**，用 GM 带宽做的 roofline 不再适用。本文按前者（较保守、且与 `A = 1.53` 的流量口径一致）列表，并把 L2 命中率记为 `unknown`。这也解释了为何 Profile 0 的 MFU（15.71%）显著低于另两个 profile：它规模最小（1.7616 GFLOP），固定开销与 workspace 往返占比最大。
