## 精度标准

golden 是**独立的 CPU FP64 参考**：按 `y = (x1 × 2^(sa−127)) @ (x2 × 2^(sb−127))^T + bias` 逐元素计算，再按 round-to-nearest-even 舍入到 BF16。它与设备实现不共享任何代码路径。

判定门限（`tests/assets/quant_batch_matmul_mxfp8_precision.py` 的 `compare`，返回 `count == 0`）：

| 判据         | 要求                                                                             |
| :----------- | :------------------------------------------------------------------------------- |
| 逐元素误差   | `\|Pro − golden\| ≤ atol + rtol × \|golden\|`，`atol = 1e-3`、`rtol = 8e-3` |
| 超门限元素数 | **必须为 0**（不允许任何单个元素超门限）                                   |
| 有限性       | 输出与 golden 均无非有限值；NaN/Inf 一律计为超门限                               |
| 形状         | 与 golden 完全一致                                                               |

`max_abs`、`max_rel`、`RMSE` 由测试打印，但**只是诊断量、不参与判定**。其中 `max_rel` 按 `|Pro − golden| / |golden|` 计算，当 `|golden|` 很小而绝对误差仍落在 `atol` 内时，它可以远大于 `rtol`——实测最大到 0.633，而同一用例的超门限元素数为 0。因此不能把 `max_rel ≤ rtol` 当作判据。

**实测结果**：28 个用例（19 个功能 shape + 9 个性能 shape）、合计 **11,049,317** 个输出元素，**超门限元素 0 个**，无非有限值。

| 用例集                 | 例数 |  元素合计 |      超门限 | `max_abs` 最大 | `RMSE` 最大 |
| :--------------------- | ---: | --------: | ----------: | ---------------: | ------------: |
| 功能与精度（19 shape） |   19 | 3,971,429 | **0** |                8 |        0.0177 |
| 性能（9 shape）        |    9 | 7,077,888 | **0** |                8 |        0.0217 |

`max_abs = 8` 出现在输出量级本身较大的用例上（该处 `|golden|` 同量级，故仍满足 `atol + rtol×|golden|`）。

**静态量**（由 shape 直接计算，不含任何实测）：FLOP `= 2×8×96×1024×4096 = 6.4425 GFLOP`；逻辑流量 `= 39,452,672 B = 39.45 MB`（x1 3.15 + x2 33.55 + scaleA 0.10 + scaleB 1.05 + out 1.57 + bias 0.03），其中权重占 85%；算术强度 163.3 FLOP/B；尾块效率 `η_tail = 1`（M、N 均整除 tile）；流量放大 1.0（无 workspace、无部分和）。

**任务形态**：`Task Type = AI_CORE`、`Block Num = 32`，一次公开调用对应一个设备任务。

**采集窗口洁净度**：本算子四次采集的冲刷任务中位分别为 748.61 / 750.03 / 749.89 / 750.63 µs；同一窗口全部八次采集（含 GEMM）的合并中位为 **750.62 µs**，由此反推的带宽参照为 **1.430 TB/s**（1073.74 MB 往返 ÷ 750.62 µs），本文所有 `t_est` 与占比都用这一参照。把每次采集的 27 个样本按时间五等分，各段中位漂移 ≤0.12%；task 数全部精确（90/90/180），`flush,A,flush,B` 交替序列校验通过。

### 理论评估对比（MFU / Bound / 利用率）

#### 分析过程

访存下界 `t_est = 逻辑流量 ÷ 带宽参照 = 39.45 MB ÷ 1.430 TB/s = 27.58 µs`。实测中位 30.732 µs，故 `t/t_est = 1.114`，带宽利用率 `t_est/t = 89.7%`。

计算下界不构成约束：`6.4425 GFLOP ÷ 实测 209.6 TFLOP/s` 与访存下界同量级，而 `cube_utilization` 已达 95.58%、`mac_ratio` 仅 0.2840，说明瓶颈在搬运侧而非阵列侧——若为算力受限，`mac_ratio` 应接近 1。

`mte2_ratio = 0.9440` 与 `t/t_est = 1.114` 互相印证：搬运部件几乎全程忙碌，剩余 11.4% 的超出量来自首尾不重叠的段落（scale 窗口载入、BiasTable 搬运、末次 fixpipe 写出）与流水填充/排空。

#### 量化依据

| 量                   |            值 | 来源                                 |
| :------------------- | ------------: | :----------------------------------- |
| 逻辑流量             |      39.45 MB | 由 shape 与 dtype 直接计算           |
| 带宽参照             |    1.430 TB/s | 同窗口 512 MiB D2D 冲刷任务反推      |
| 访存下界 `t_est`   |     27.58 µs | 上两行相除                           |

#### MFU

MFU（Model FLOPs Utilization）= 有效计算吞吐 ÷ 硬件理论算力峰值。它与本文另外两个利用率是**不同的量**：「带宽利用率」以实测可达带宽为分母，profiler 的 `mac_ratio` 是 MAC pipe 的活跃时间占比，三者不可互相代替。

**峰值来源**。平台常量取本机安装态 `framework/src/platform/parser/simulation_platform/platform_config/Ascend950PR_9589.ini`，逐项核对：

| 常量                  | 值             | ini 位置                                        |
| :-------------------- | :------------- | :---------------------------------------------- |
| Cube 分形 `M×N×K` | `16×32×16` | `[DtypeMKN]` 的 `DT_FLOAT8_E4M3FN=16,32,16` |
| `cube_core_cnt`     | 32             | `[AICoreSpec]`                                |
| `cube_freq`         | 1650 MHz       | `[AICoreSpec]`                                |

`峰值 = M·N·K × 2 × cube_core_cnt × cube_freq = 16×32×16 × 2 × 32 × 1.65×10^9` = **865.08 TFLOP/s**（FP8 dense，一次乘加计 2 FLOP）。

MXFP8 用的是同一个 Cube 单元：`[AICoreintrinsicDtypeMap]` 中只有 `Intrinsic_mmad`（其 dtype 组合含 `e4m3e4m3`、`e4m3e5m2`、`e5m2e4m3`、`e5m2e5m2`）与 `Intrinsic_mmad_sp`（仅 s8），**没有 MX 专用 intrinsic**；`[AICoreSpec]` 的 `l0_a_mx_size = l0_b_mx_size = 4096` 与 `bt_size = 4096`，正是本实现 MX scale plane（每槽 2048 字节 × 2 槽）与 BiasTable 所用的那两个独立平面。E8M0 分组反量化由 `matmul_mx` 在 Cube 内联完成，不额外占用 MMAD 周期。

**逐例 MFU**（有效吞吐 = `6.4425 GFLOP ÷ 实测耗时`，MFU = 有效吞吐 ÷ 865.08 TFLOP/s）：

| 用例                      |         耗时 µs | 有效吞吐 TFLOP/s |    **MFU** |
| :------------------------ | ---------------: | ---------------: | ---------------: |
| `e5m2_vector_bias`      |           30.081 |            214.2 |           24.76% |
| `e5m2_batch_bias`       |           30.881 |            208.6 |           24.12% |
| `e5m2_no_bias`          |           30.849 |            208.8 |           24.14% |
| `e4m3fn_vector_bias`    |           30.865 |            208.7 |           24.13% |
| `e4m3fn_batch_bias`     |           30.918 |            208.4 |           24.09% |
| `e4m3fn_no_bias`        |           30.732 |            209.6 |           24.23% |
| `e4m3fn_vector_bias_nz` |           30.554 |            210.9 |           24.37% |
| `e4m3fn_batch_bias_nz`  |           30.576 |            210.7 |           24.36% |
| `e4m3fn_no_bias_nz`     |           30.369 |            212.1 |           24.52% |
| **九例中位**        | **30.732** |  **209.6** | **24.23%** |

九例 MFU 区间 24.09%–24.76%，极差 0.67 个百分点。

**MFU 的带宽上限**。本机 roofline 拐点 = `865.08 TFLOP/s ÷ 1.4305 TB/s = 604.7 FLOP/B`。本算子的算术强度只有 **163.3 FLOP/B**（权重占逻辑流量 85%），仅为拐点的 27%，因此**即使搬运完全打满、计算完全免费，MFU 也不可能超过 `163.3 ÷ 604.7 = 27.00%`**（等价的绝对上限是 `163.3 FLOP/B × 1.4305 TB/s = 233.6 TFLOP/s`）。实测 209.6 TFLOP/s 已达该上限的 **89.7%**。

这个 89.7% 与「绝对性能结果」里的带宽利用率数值相同，是恒等式而非巧合：`MFU ÷ 上限 = (FLOP/t) ÷ (AI × BW) = bytes ÷ (t × BW) = t_est ÷ t`。它同时构成一处内部一致性校验。

因此 **24% 的 MFU 不是实现质量的度量，而是该 shape 算术强度的直接后果**。要提高 MFU 只能提高算术强度——增大 tile 以复用操作数，或让同一份权重被更多输出块共享。在算术强度不变的前提下，继续优化搬运与流水最多把耗时压到 `t_est = 27.58 µs`，即**提速 11.4%**、MFU 从 24.23% 升到上限 27.00%；注意这里的 11.4% 是可达提速，而 89.7% 是已达上限的比例，两者互为倒数关系（`1/0.897 = 1.114`），不是同一个数。

#### 各场景 Bound 归类

| 场景                                          | 归类                               | 依据                                                                                                 |
| :-------------------------------------------- | :--------------------------------- | :--------------------------------------------------------------------------------------------------- |
| `B/M/N/K = 8/96/1024/4096`（全部 9 个用例） | **访存受限（memory-bound）** | `mte2_ratio = 0.9440` 主导；`mac_ratio = 0.2840` 远低于 1；`t/t_est = 1.114`、带宽利用率 89.7% |

九个用例的 `InputFormat`、`HasBias`、`WeightNz` 取值不同，但耗时极差仅 2.72%、pipe 占比形态一致，因此归为同一类。权重占逻辑流量 85%，是访存受限的直接原因；这也解释了为何 x2 载入被设为不在 L2 分配（见 [DESIGN.md](DESIGN.md)「接口选择」）：权重每块只流过一次，参与 L2 分配只会挤掉被跨块复用的张量。

**未覆盖的性能场景**：支持域内其余 shape（含所有尾块 shape、`K` 非 `KL1`/`SCALE_KL1` 整数倍的 shape、输出块数多于核数需多轮 grid-stride 的 shape）**尚未按上述协议采集**。尾块工作量小于满块、且输出块数不是核数整数倍时末轮有 worker 空转，负载均衡不由构造保证，因此不能把本节的 Bound 归类外推到这些 shape。
