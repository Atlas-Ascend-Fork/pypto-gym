# quant_mla_prolog 结果记录（PyPTO-Pro）

设备为 Ascend 950PR_9589 满配 32 Cube / 64 Vector。性能数据采集于并入本仓前的
实现版本，其后仅有四笔不涉及设备侧算术的清理（主机侧校验拆分、`assert` 改
`raise`、纯 `pl.*` 内层体抽取、删除恒真参数），每笔均重跑全部用例通过。

## 用例

`23` 个用例函数全部通过，`0` 失败。

| 维度 | 覆盖 |
| --- | --- |
| `T` 档界与尾块 | `1, 7, 8, 9, 17, 31, 32, 33, 63, 64, 65, 127, 128, 129, 255, 256` 共 16 档，含每个档界两侧与非整除尾块 |
| `quant_mode_c=0` | 单独一轮 `1, 8, 32, 64, 128, 256` 共 6 档 |
| 散写 | `slot < 0` 跳过、跨页乱序散写、多 m 块下的跳过 |
| 行独立性 | 单行改动不影响其他行；窗口外的 L1 旧字节不外泄（`T=255` 与 `T=256` 的前 255 行逐 bit 相同） |
| 重复调用 | 同输入重复调用结果一致 |
| workspace | 前次调用的残留不影响本次结果 |
| 公开契约 | 返回 dict 的键序；`quant_mode_c=0` 下 `descale_q` 键缺席；`kv_cache_out` 是入参对象本身；物理 PA_NZ 形状的 `kv_cache` 被拒；scale 的多一维 / 行数不等 / 群数不等三类违例被拒；`quant_mode_aw=0` 被拒 |
| `norm_eps` | 多个取值的变体与非法值拒绝 |
| 量化 scale | 除法语义的 `qscale` 回归 |

泛化检查按 `authoring.md#generalization-and-specialization` 的三项：

| 检查 | 结果 |
| --- | --- |
| 未列尺寸可用 | `T = 3, 13, 45, 77, 100, 200, 333`（配 1~5 个 block）全部通过，反量化相对 L2 在 `1.20e-3 ~ 1.58e-3`、余弦 ≥ `0.9999988` |
| 同类内复用产物 | 同一 capacity 档内改 `T`、`cache_index`、`norm_eps`，新增编译特化 `0` 份 |
| 跨类切换 | `quant_mode_c` 1→0 新编一份、0→1 命中已有产物（新增 `0` 份）；同一 capacity 下两种模式各一份产物 |

`norm_eps` 是运行期标量参数而不是编译期变体键，所以改 `eps` 不产生新产物 ——
这是第二项为 `0` 份的原因。

静态规则门禁（`pypto-pro-kernel` 的 `check.py rules`）：`179` 处 VF 调用全部对照框架
源码核对完成，`0` 处违规、`0` 处需核查，`0` 处禁用的 tile Vector 计算。

## 精度标准

判据在 `tests/assets/quant_mla_prolog_precision.py`，三个终输出各自判定：

| 输出 | 判据 |
| --- | --- |
| `q`（E4M3）| 乘回 `descale_q` 反量化后，相对 L2 < `3.0e-2` 且余弦 > `0.999` |
| `descale_q`（FP32）| 相对 L2 < `3.0e-2`，且取值全正 |
| `kv_cache_out` | 写入行按 `cache_index` 取出、乘回 `qscale_kv` 反量化后比相对 L2 < `3.0e-2`；未写入行逐 bit 完全不变 |

`quant_mode_c=0` 下 `q` 与 `kv_cache_out` 都是 BF16 终值，直接比；`descale_q` 整条
不存在，两侧都应缺席。

编码态 FP8 的逐字节差异只作诊断打印，不参与判定。原因是它对 `kv_cache` 的写入行
固有不可达：源头是 `kv_raw` 的 7168 项 FP32 累加次序，相邻 FP8 码的差异不代表模型
精度。

CPU 真值在 `tests/assets/quant_mla_prolog_golden_cpu.py`，只依赖 torch，可脱离 NPU
运行；它与 kernel 的逐条对应关系见 README 的功能说明。

四条实现路径与等价参照路径**逐 bit 相同**：权重逐 fractal 装载、merged-row 权重装载、
动态 `valid_shape` 收窄的装载（有效行逐 bit 正确、窗口外行保持预置哨兵的乘积，证明
GM 读只发生在窗口内）、γ 的片上 `astype(BF16, CAST_RINT)` 绕行。

公开接口在上板前做主机侧校验（全部只读元数据，无张量数据操作），错误调用全部在发射
kernel 之前被拒：

| 错法 | 异常 |
| --- | --- |
| 权重 NZ 排布反了（元素数相同）| `ValueError` |
| `wkb` 不是 BF16 | `ValueError` |
| `norm_weight_qa` 不是 FP32 | `ValueError` |
| `cache_index` 不是 INT64 / 短于 `T` | `ValueError` |
| `descale_x` 群数不等 / 行数不等 / 多一维 / 不是 E8M0 | `ValueError` |
| `qscale_kv` 形状不是 `[1]` | `ValueError` |
| `x` 非连续 | `ValueError` |
| `kv_cache` 容量装不下 `T` 行 / 不是逻辑 `[blocks, 128, 1, 576]` | `ValueError` |
| `quant_mode_aw != 1` | `ValueError` |
| 张量不在设备上 | `RuntimeError` |
| `quant_mode_c=1` 缺 `qscale_kv` / `quant_mode_c=0` 多传 `qscale_kv` | `ValueError` |

这些错法的共同点是**不报错就是静默错值**：排布错的权重元素数是对的；非连续的 `x`
会按行距读到错字节；越容量的 cache 让散写算出界外地址。`norm_eps` 的非法值（非正、
非有限）由另一组用例覆盖。

入参校验里「与 `x` 不在同一设备」这一条需要两张可用设备才能走到，取证环境只有一张，
该分支未被触发。
## 性能结果

### 采集环境

| 项 | 值 |
| --- | --- |
| 芯片 | Ascend 950PR_9589，32 Cube / 64 Vector |
| CANN | `compiler/version.info` 报 9.2.0（安装目录 cann-9.3.0） |
| Python / torch / torch_npu | 3.12（conda）/ 2.12.0+cpu / 2.12.0 |

### 采集协议

| 项 | 取值 |
| --- | --- |
| 指标 | msprof application 模式采集的 `op_summary*.csv` → `Task Duration`，即 native 设备任务时延 |
| 采集参数 | `--task-time=l0 --aicore-shape=on`；需要流水占比时另加 `--aic-metrics=PipeUtilization` |
| 统计 | 每档预热 11 次后计量 30 次取中位数；采集行数与该口径不符即整档作废 |
| kernel 选取 | 按 kernel 名唯一命中，host 侧搬运不计入 |
| 干净度 | **本卡独占**（采集前后各探一次本卡占用）**加量级自检**（median 落在历史值的 ±20% 之外即丢弃该档重采） |
| 噪声底 | 同协议 `n = 30` 下窗口间重复性约 ±3%，低于该量级的差异不应解读为性能变化 |

干净度判据是**本卡独占**而不是整机无外来进程：实测在整机有 5~13 个外来用卡进程、
但都落在另一张卡上时，本卡四个档位的散布仍只有 ±3%、标准差不到 1 us。卡间是隔离
的，另一张卡上的负载不污染本卡的 `Task Duration`。


### 绝对性能结果

`quant_mode_c=1`，`n = 30`，紧凑输入（`kv_cache` 单页、顺序索引）：

| `T` | 本包 median（us） | 标准差（us） | 散布 |
| ---: | ---: | ---: | ---: |
| 8 | 31.66 | 0.56 | ±2.8% |
| 32 | 35.69 | 0.54 | ±2.2% |
| 64 | 44.48 | 0.58 | ±3.1% |
| 128 | 63.13 | 0.90 | ±1.4% |

`T = 8` 按同协议独立进程重复采集三轮：31.75 / 31.67 / 31.91 us，与上表 31.66 us
一致（跨进程差异 ±0.8%）。`T = 8` 的时延对 `kv_cache` 物理页布局敏感：多页碎片化
`kv_cache`（72 页、乱序跨页索引）使时延跨进程在 32.2 ~ 37.3 us 间波动（同实现同
输入），紧凑 `kv_cache` 稳定在 31.7 ~ 31.9 us。其中确定性的部分是最小合法行数：
本实现的 NZ tile 行数须为 16 的倍数（见 `DESIGN.md` 的基本块选择），`T = 8` 的中间
量按 16 行计算，是有效行的两倍、占该档总流量 7.4%。

单 kernel 全融合架构存在与数据量无关的固定成本，经逐相位消融定位：3 道跨相位真依赖
屏障、section 机制与启动合计约 10.4 us，在 30 us 级 kernel 上占比约三分之一。`T`
增大后固定开销占比随之下降，与上表档位间时延增幅的走势一致。

每档实际选中的特化（由 host 侧的选档表达式算出，不据注释或变体名）：

| `T` | `MRows` | capacity | m 分块数 | front 段宽 |
| ---: | ---: | ---: | ---: | ---: |
| 8 | 16 | 16 | 1 | 512 |
| 32 | 32 | 32 | 1 | 512 |
| 64 | 64 | 64 | 1 | 512 |
| 128 | 128 | 128 | 1 | 256 |

`T = 128` 起 front 段宽由 512 降为 256（`a_l0a` 双槽在 512 宽需 131072 B 而 L0A 只有
65536 B），K 段数随之翻倍。这解释了下一节中该档等效吞吐偏低：按 `T = 64` 档的
1.80 TB/s 折算应为 57.4 us，实测 63.13 us，差 5.7 us 落在这次特化切换上。

### 理论评估对比（MFU / Bound / 利用率）

本算子是**访存主导**（memory-bound）。按契约算出的每次调用 GM 流量，与上表 median
对照得到等效吞吐：

| `T` | 权重+scale | 中间量往返 | 激活+输出 | 合计 | 等效吞吐 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 8 | 57.4 MB | 4.65 MB | 0.51 MB | 62.5 MB | 1.97 TB/s |
| 32 | 57.4 MB | 9.29 MB | 2.04 MB | 68.7 MB | 1.92 TB/s |
| 64 | 57.4 MB | 18.59 MB | 4.07 MB | 80.1 MB | 1.80 TB/s |
| 128 | 57.4 MB | 37.17 MB | 8.15 MB | 102.7 MB | 1.63 TB/s |

权重主导的档位吞吐更高（`T = 8` 时权重占该档流量 92%）；随 `T` 增大、中间量往返占比
上升（`T = 128` 时占 36%），等效吞吐降至 1.59 TB/s（其中 7.2 us 落在 front 段宽
512 → 256 的特化切换上，见上节）。这与 AIC 侧 PIPE 占比一致：MTE2 是最忙的一条、
占 56.1%，Cube 占 31.8%（`msprof op --aic-metrics=PipeUtilization`，`T = 512` 的
独立采集）。因此 MFU 不是本算子的有效指标 —— Cube 的 mac 利用率低是访存受限的结果，
不是调度缺陷。

同一次 pipe 采集里 MTE1 占 35.3%、scalar 30.3%、fixpipe 26.0%，**没有任何一条流水
接近饱和**，各占比之和 179% —— 余量在跨流水串行化，不在单条流水的字节数上。

权重与其 scale 固定 57.4 MB 且与 `T` 无关，`T <= 128` 时占总流量 56% 以上；中间量
往返里最大的一项是 M6 → M7 的 `q_latent`，`T = 128` 下 25.2 MB、占总量 24.5%。权重
scale 本身只占全部权重字节的 2.4%。`T > 128` 时 front 拍序（`(n, m_idx, k1)`、
`k1` 最内）使权重窗口按 m 分块重读，该区间不在本表采集范围。

该吞吐是**按契约字节数除以设备任务时延得到的等效值**，不是物理主存流量：其中的重复
搬运与 L2 命中都没有单独计量。本文**没有**测量硬件带宽上限，因此不据此声明「已接近
带宽墙」或推断剩余空间 —— 那需要物理内存流量计数器或一条匹配的持续带宽基准。

### 复现命令

命令从仓库根目录执行。

```bash
D=ops/pypto_pro/kimi_k3/quant_mla_prolog

# 数值：CPU 真值自检（不需要 NPU）与全量用例
python3 $D/tests/assets/quant_mla_prolog_golden_cpu.py
TILE_FWK_DEVICE_ID=0 pytest $D/tests -q

# 静态规则门禁（pypto-pro-kernel skill 的检查器）
python3 <skill>/scripts/check.py --pypto-root <pypto> rules $D

# 性能：按「采集协议」节的口径自建采集入口（预热 11 + 计量 30 取中位）
msprof --output=<out> --application="<bench>" --task-time=l0 --aicore-shape=on
```

性能采集的 runner 与解析器不随交付包提供：它们绑定具体机器的环境变量与产物路径。
按「采集协议」节的口径自行搭建即可复现。
