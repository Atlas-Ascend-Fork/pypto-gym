# mega_recurrent_kda 结果说明

本文给出 `mega_recurrent_kda` 的精度与性能结果：用哪些用例检验、按什么标准判定、实测数据是
多少、以及这些数据说明什么。精度数据由 `tests/test_mega_recurrent_kda.py` 在 Ascend 950DT
上实测；性能数据由 `tests/test_mega_recurrent_kda.py --bench` 按 device 口径采集。由实测值再算一步
得到的量（段占比等）都在出现的地方写明算法。

## 1 用例

**测试环境**

| 项目     | 取值                                                                                                            |
| :------- | :-------------------------------------------------------------------------------------------------------------- |
| 硬件平台 | Ascend 950DT（`soc_version = 'DAV_3510'`），cube 32 核 / vector 64 核                                         |
| 软件环境 | CANN 9.2.0-beta.2、PyPTO-Pro                                                                                    |
| 默认配额 | 支持 8 / 16 / 24 / 28 / 32 AIC；默认取设备可用最大值（950DT 为 32 AIC / 64 AIV，AIV = 2 × AIC）           |
| 输入构造 | `tests/assets/mega_recurrent_kda_golden_cpu.py` 的 `make_cpu_arguments`，每用例固定 seed（`731 + batch`） |

支持的 AIC 配额固定为 8 / 16 / 24 / 28 / 32；默认取设备上可用的最大配额（由
`pypto_pro.runtime.platform.get_platform_info().core_num` 读取：950DT 为 32，28 核 SKU 为 28，
更多核的设备仍默认 32）。`MEGA_KDA_CUBE_CORES` 只能取上述集合且不超过设备规格，其它值在
host 侧报 `ValueError`。本文表格是 950DT（32 核）上的实测值。

**用例清单**

`tests/test_mega_recurrent_kda.py` 里的一个精度用例对应一个 `test_precision[...]` 参数，共 9 个；
另有 3 个契约用例（非法 `S`、AIC 配额、公开签名）。`rows = B·S`，`MTile` 是编译期 M tile，`Mpad` 是对齐
到 `MTile` 后的行数：

| case             |  B |  N | `rows` | `MTile` | `Mpad` | `m_tiles` | 说明                                  |
| :--------------- | -: | -: | -------: | --------: | -------: | ----------: | :------------------------------------ |
| `tp16_b16`     | 16 |  6 |      128 |       128 |      128 |           1 | TP16、小 batch                        |
| `tp16_b32`     | 32 |  6 |      256 |       128 |      256 |           2 | TP16、中 batch                        |
| `tp16_b48`     | 48 |  6 |      384 |       128 |      384 |           3 | TP16、大 batch（`m_tiles` 最多）    |
| `tp4_short_b4` |  4 | 24 |       32 |        32 |       32 |           1 | 最小 batch，单 M-tile，`MTile = 32` |
| `tp4_tail_b12` | 12 | 24 |       96 |       128 |      128 |           1 | 行数非 tile 倍数（96 → 128）         |
| `tp4_main_b32` | 32 | 24 |      256 |       128 |      256 |           2 | Vector 工作项最多（768）              |
| `tp8_short_b8` |  8 | 12 |       64 |        64 |       64 |           1 | `MTile = 64`                        |
| `tp8_tail_b24` | 24 | 12 |      192 |       128 |      256 |           2 | 行数非 tile 倍数（192 → 256）        |
| `tp8_main_b64` | 64 | 12 |      512 |       128 |      512 |           4 | 最大用例，`m_tiles = 4`             |

九个用例覆盖了三种 `MTile`（32 / 64 / 128）、三种 head 数（6 / 12 / 24）、单 M-tile 与多
M-tile、以及行数是否对齐到 tile。`S` 恒为 8，`H` 恒为 7168。

**运行方式**

```bash
pytest ops/pro/kimi_k3/mega_recurrent_kda/tests/test_mega_recurrent_kda.py -q
```

精度判定与参考值都在 `tests/assets/` 下，随算子一起维护。

## 2 精度标准

每个用例把 `output`、`conv_state`、`recurrent_state` 三者分别与独立 CPU golden 比较，逐元素
判据为 `torch.testing.assert_close(atol=5e-3, rtol=5e-3)`，即

```text
|actual − golden| <= 5e-3 + 5e-3 · |golden|
```

这个阈值来自 SPEC，比 `tests/assets/mega_recurrent_kda_precision.py`（方案 A 混合容差）对
BF16 的默认阈值（`rtol = atol = 2⁻⁶ ≈ 1.56e-2`）更严。除了逐元素容差，还要求两个状态池的
槽 0 **逐位不变**（`torch.equal`）。

| 参数           |                                                                    取值 |
| :------------- | ----------------------------------------------------------------------: |
| `atol`       |                                                                    5e-3 |
| `rtol`       |                                                                    5e-3 |
| 参与比较的张量 | `output`（BF16）、`conv_state`（BF16）、`recurrent_state`（FP32） |
| 额外要求       |                    `conv_state` / `recurrent_state` 的槽 0 逐位不变 |

### 2.1 结果

**9 / 9 通过。** 下表是每个用例三个张量的实测**绝对最大差**：

| 用例             | (B, N)   |  output | conv_state | recurrent_state |
| :--------------- | :------- | ------: | ---------: | --------------: |
| `tp16_b16`     | (16, 6)  | 8.11e-4 |    2.44e-4 |         7.76e-4 |
| `tp16_b32`     | (32, 6)  | 9.71e-4 |    2.44e-4 |         8.59e-4 |
| `tp16_b48`     | (48, 6)  | 9.84e-4 |    4.88e-4 |         8.81e-4 |
| `tp4_short_b4` | (4, 24)  | 1.49e-3 |    4.88e-4 |         9.08e-4 |
| `tp4_tail_b12` | (12, 24) | 1.65e-3 |    4.88e-4 |         9.47e-4 |
| `tp4_main_b32` | (32, 24) | 1.71e-3 |    4.88e-4 |         1.02e-3 |
| `tp8_short_b8` | (8, 12)  | 1.01e-3 |    2.44e-4 |         8.63e-4 |
| `tp8_tail_b24` | (24, 12) | 1.08e-3 |    4.88e-4 |         8.66e-4 |
| `tp8_main_b64` | (64, 12) | 1.62e-3 |    4.88e-4 |         9.19e-4 |

两点说明：

- 最大的 `output` 差是 `tp4_main_b32` 的 1.71e-3，为 `atol` 的 34%；最大的
  `recurrent_state` 差是 1.02e-3，为 `atol` 的 20%。九个用例的三个张量都在容差内，且余量
  都在 2.9 倍以上。
- `conv_state` 的差只取 4.88e-4 与 2.44e-4 两个值（分别是 BF16 在 `[0.125, 0.25)` 与
  `[0.0625, 0.125)` 上的一个 ULP），说明它只差在 BF16 最后一位的舍入上，不是算法偏差。

由于 cube2 的 K 段累加走 `AtomicAdd`（见 `README.md` 约束说明），同一用例重复测量的
`max_abs_error` 可在 1–2 个 BF16 ULP 内浮动；表中给出其中一次实测值。

除 9 个参数化用例外，还有两类补充验证：

- **全规格抽查**（同一 CPU golden、同容差）：`B=128/N=24` → output 1.82e-3、conv 4.88e-4、
  rec 1.15e-3；`B=256/N=12` → 1.44e-3 / 4.88e-4 / 1.08e-3；`B=512/N=6` →
  1.22e-3 / 4.88e-4 / 1.13e-3。全部通过，槽 0 逐位不变。
- **新分配输入探针**：每次调用都用新分配的张量（不复用工作区），`B = 4/16/32/64` 各 12–20 次，
  0 失败、无 NaN。

### 2.2 形状与边界行为

声明范围之内的形状都能正常输出，声明之外的输入在 host 侧报错、不静默给出结果。逐条实测的
行为如下：

| 情形                                                      | 实测行为                                                 |
| :-------------------------------------------------------- | :------------------------------------------------------- |
| `B = 128/N = 24`、`B = 256/N = 12`、`B = 512/N = 6` | 正常输出，三项精度均在`5e-3` 内                        |
| `S != 8`（`hidden_states` 行数与 `B·8` 不符）      | `ValueError`：要求 `[Mpad, 7168]` 的 padded A 操作数 |
| `H != 7168`                                             | `ValueError`：`hidden_states must be the padded A operand [Mpad, 7168]`（H 固定为 7168） |
| 奇数 head 数                                              | `ValueError`：`mega_recurrent_kda requires an even head count`          |
| `output_gate_projection_weight` 列数非 128 的倍数        | `ValueError`：`output_gate_projection_weight columns must be a multiple of 128`        |
| head 数超过 128（beta 补齐宽度）                          | `ValueError`：`head count {n} exceeds the padded beta width 128`        |
| 六个投影权重以 ND 传入                                    | `ValueError`：要求 BF16 FRACTAL_NZ allocation-root     |
| `conv_state_indices[b] == 0`                            | 该行不改动`conv_state`，卷积输出全 0                   |
| 8 / 16 / 24 / 28 / 32 AIC 配额                            | 9/9 精度用例通过，槽 0 逐位不变                          |
| 每次调用都用新分配输入                                    | 0 失败、无 NaN                                           |

## 3 性能结果

本算子一次调用只下发一个 mixed kernel（`PYPTO_mega_recurrent_kda_kernel`），因此本算子的性能
即该 kernel 的 device 耗时。下表给出任务级耗时。

**性能测试方法**

验证环境为 Ascend 950DT（`DAV_3510`）、CANN 9.2.0-beta.2、PyPTO-Pro，固定单卡单进程。
覆盖 TP4/8/16 × 模型 batch 1/8/16/32 × 8/16/24/32 AIC，共 48 个代表点，精度 9/9 通过。

每点采集 20 个样本取均值，每次采样前恢复初始状态并驱逐 224 MiB L2；恢复、清 L2 和导出
不计入耗时。计时用 `torch_npu.profiler`，只统计 `PYPTO_mega_recurrent_kda_kernel` 的 device
`Duration(us)`。

### 3.1 绝对性能结果

**12 用例 × 4 配额（device 时间，单位 µs）**

两点读法：

1. **绝对时延随配额单调下降**（12 用例一致）：8→16 为 −33%…−50%、16→24 为 −20%…−28%、
   24→32 为 −9%…−18%（(128,24) 的实测链：3577.8 → 1827.3 → 1361.5 → 1188.8 µs）。
2. **32 AIC 绝对时延最低**：12 用例中 32 AIC 均不高于 24/16/8 AIC；小 batch 下 24/32 AIC 差距较小。

### 3.2 理论评估对比

**Bound 判定**

本算子是两种计算单元各管一段的混合形态，两段各有自己的Roofline：

| 段                               | 主要资源                         |                实测利用率 | 判定                                     |
| :------------------------------- | :------------------------------- | ------------------------: | :--------------------------------------- |
| cube1（qkv / proj2 / raw_decay） | MAC（矩阵乘）与 MTE2（权重搬运） |                 92% / 92% | 双屋顶同时饱和                           |
| 递归阶段（激活 + KDA 递归 + 门控） | VEC（向量指令）                  |                    ≈ 60% | 受逐 token 依赖与状态 DMA 限制           |
| 递归阶段的每 token 状态写回      | L2 写带宽                        | 深度 2 快照 + 延迟一拍后与计算部分重叠 | 硬成本（每 token 物化`128×128` 状态） |
| cube2（输出投影）                | MAC / MTE2                       | 72 µs，已与递归阶段重叠 | 不构成瓶颈                               |

三点结论直接由表得出：

1. **前端 Cube 已在硬件屋顶**。cube1 的 MAC 与 MTE2 同时到 92%，再压缩字节或加宽 N-tile
   都不会有稳定收益（M2N2、L1 双缓冲、N384 强制等方向均已实测否决）。
2. **递归段被逐 token 的固定代价钉住**，而不是被某类可移除的指令钉住。(128,24) 共 24 576 个
   token 迭代，逐 token 成本约 1.46 µs（≈2620 cycle），而 ksum / delta / update 的指令级精简（融合乘加、去掉标量 store、
   去掉 `o` 整块、2 行 ILP 展开）全部落在 ±1.3% 以内。
3. **状态写回是硬契约，但已与计算部分重叠**。每个 token 都要把 `128×128` FP32 状态写回
   `recurrent_state`，`(128,24)` 下 8×64 KiB/项、合计约 1.5 GB。把 `c_snap` 改成深度 2
   快照、并让 token t 存 token t−1 的快照（延迟一拍），可让写回的 DMA 与当前 token 的向量计算
   并发，大 batch 在 8/16/24/32 AIC 分别回收约 15% / 14% / 7% / 2%。剩余写回代价仍受
   UB→GM 字节带宽与「快照槽数不足以完全隐藏 DMA」限制。
