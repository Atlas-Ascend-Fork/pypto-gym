# block_attn_res_update_rms_norm 结果说明

本文给出 `block_attn_res_update_rms_norm` 的精度与性能结果：用哪些用例检验、按什么标准判定、
实测数据是多少、以及这些数据说明什么。所有数值均由同一台机器、同一套工具链实测得到；
由实测值再算一步得到的量（有效吞吐等）都在出现的地方写明算法。设计与取舍见
[DESIGN.md](DESIGN.md)。

## 2 精度标准

判定标准（`tests/assets/block_attn_res_update_rms_norm_precision.py`，与上游 AscendC 参考算子一致）：

- `np.isclose(candidate, reference, rtol=1e-3, atol=0)` 的不满足元素比例 ≤ `1e-3`；
- 任一元素非有限（NaN/Inf）直接判失败；
- `y` 与 CPU 参考比较，`p` 与 `partial + fp32(delta)` 比较；
- 除 `partial_block` 外的 6 个输入在调用后必须与调用前逐位相等（只读性检查）；
- 输出 shape 必须为 `[T, 7168]`、dtype 为 BF16、device 与输入一致。

cancellation 用例单独用「2 倍参考」规则：对称构造的 `p` 使 `dot ≈ 0`，任何 FP32 归约顺序
（包括 golden 自身）相对 float64 预言机都会超过 `1e-3` 的比例门限，因此要求
`kernel_bad ≤ 2 × max(golden_bad, 1)`，非有限值仍判失败。这条规则没有放宽被测实现的
标准，只是把「参考自身也做不到的顺序敏感性」从判据里排除。

### 2.1 结果

`TILE_FWK_DEVICE_ID=5 pytest ops/pro/kimi_k3/block_attn_res_update_rms_norm/tests --mode jit -q`
→ **21 passed**，且 `y` / `p` 与 CPU golden **逐位一致**（T = 1、8、64、254、512 抽样 `max|diff| = 0.0`）：

| 组 | 结果 |
| :--- | :--- |
| shapes（10 个 `T`） | 全部 PASS（`y`、原地 `p`、shape、只读性） |
| numeric regressions | cancellation `T = 8`：kernel_bad 24 ≤ limit 118、83 ≤ limit 166；`ftz` / `recip_ftz` 全部 PASS |
| routing / transitions | PASS，`select_path` 在 `T = 0/1/2` 返回 0，`T = 3/4/1024` 返回 1 |
| empty / validation | `T = 0` 返回空 `[0, 7168]` BF16；5 类非法入参全部报 `ValueError` |

跨类别切换后的二进制复用性**未验证**：当前安装的运行时没有提供「编译事件 / cache 条目」
查询接口，因此不根据「key 相同」推断复用，只记录为未验证项。

### 2.2 形状与边界行为

- `T = 0`：不启核，直接返回空张量；`T ≥ 1` 时起核数为 `min(56, T)`。
- `T = 1/2` 走 `Path = 0`（整行单体），`T ≥ 3` 走 `Path = 1`（分行段）；`T = 3` 是
  阈值本身，两个方向的相邻取值（`3` 与 `5`）都在用例里。
- `T = 254` 时 56 核分到 5/4 行不等（`254 = 56×4 + 30`），无尾块、无空转核，精度 PASS。
- `D != 7168`、非连续张量、跨 device、非正 epsilon 均在 host 侧报错。

## 3 性能结果

**测量方法**：每个（实现，用例）组合单独跑一次 msprof application，进程内 50 次预热 +
200 次受测启动，指标取内核 `Task Duration` 的 p50（单位 μs，设备端内核时间，不含预热、
输入恢复和 host 调用开销）。本实现数据在 CANN 9.3.0 / device 5 上测得；AscendC 参考
数据在不同环境测得，仅作量级参考。

### 3.1 绝对性能结果

| 用例 | 形状 | 起核数 | p10（μs） | p50（μs） | p90（μs） |
| :--- | :--- | ---: | ---: | ---: | ---: |
| T1 | `[1, 7168]` | 1 | 2.919 | 3.025 | 3.095 |
| T2 | `[2, 7168]` | 2 | 3.087 | 3.129 | 3.185 |
| T4 | `[4, 7168]` | 4 | 3.564 | 3.634 | 3.715 |
| T8 | `[8, 7168]` | 8 | 3.629 | 3.727 | 3.829 |
| T32 | `[32, 7168]` | 32 | 3.849 | 4.148 | 4.405 |
| T64 | `[64, 7168]` | 56 | 5.257 | 5.704 | 6.283 |
| T254 | `[254, 7168]` | 56 | 10.134 | 10.626 | 11.153 |
| T512 | `[512, 7168]` | 56 | 16.668 | 17.332 | 17.823 |

与 AscendC 实现的性能倍数（同功能 = `update` + `RmsNorm` 两算子合计）：`T1/8/64/512` 分别为
1.58 / 1.63 / 1.52 / 1.15 倍，几何平均 **1.45 倍**；若只与其半程算子 `update` 相比则为 0.80 倍
（我们多做了整段 RMSNorm）。

注意：AscendC 参考数据在不同环境测得，仅作量级参考；同一实现在不同环境实测的抖动约 ±2%
（CANN 9.2.0 + device 0：3.00/3.07/3.61/3.65/4.04/5.53/10.32/16.71 μs）。

### 3.2 理论评估对比（流量与有效吞吐）

每行固定流量：`partial` 读+写各 4·D、`delta` 读 2·D、`numerator` 读 4·D、`y` 写 2·D；
`query`（4·D）与 `gamma`（2·D）每核只搬一次。有效吞吐 = 上表总流量 ÷ p50。

| 用例 | GM 流量（MB） | p50（μs） | 有效吞吐（TB/s） |
| :--- | ---: | ---: | ---: |
| T1 | 0.158 | 3.025 | 0.05 |
| T8 | 1.262 | 3.727 | 0.34 |
| T32 | 5.046 | 4.148 | 1.22 |
| T64 | 9.748 | 5.704 | 1.71 |
| T254 | 31.539 | 10.626 | 2.97 |
| T512 | 61.129 | 17.332 | 3.53 |

小 `T` 时吞吐极低（`T1` 只有 0.05 TB/s），说明这些用例完全由**串行的三阶段依赖 +
两次全行归约**决定，与搬运能力无关：`T1` 的 0.158 MB 在 2.94 μs 内搬完，等价带宽远低于
硬件能力，时间花在「搬入 → 两路归约 → 取整 → 再归约 → 写回」的链条上。`T ≥ 254` 时吞吐
升到 3 TB/s 量级，行的重叠已经吃满。注意 `T512` 的工作集约 51 MB，小于本平台 128 MiB 的
L2，稳态读多来自 L2，因此这里的有效吞吐**不能**直接当作 HBM 带宽上限。

### 3.3 优化轮次（试过未采用的改动）

| 方案 | 做法 | 结果 | 结论 |
| :--- | :--- | :--- | :--- |
| 按 `D` 切分多核（`T ≤ 4`） | 8 个核各持 896 列；`dot`/`ssq`/`ssq_h` 经 GM scratch 交换，两次 `INTER_BLOCK` 屏障 | 精度完全正确，但性能只有整行方案的 0.64 / 0.72 / 0.74 倍（`T1/T2/T4`） | 两次 GM 往返 + 屏障约 1.2 μs，超过多核省下的向量时间，已移除 |
| 屏障本身的开销探针 | 同一 kernel 里 0 / 1 / 2 次 `set_cross_core` + `wait_cross_core` | 2.052 / 2.041 / 2.040 μs | 屏障原语本身几乎免费，代价在 GM 往返，因此调屏障参数无意义 |
| `enable_slice=False` 等编译期开关 | 逐一开关试 | 差异在 ±1~2% 抖动内 | 无稳定收益，未采用 |
| 去掉 VF 内 `mem_bar` | 删掉 4 处 `VST_VLD` 后跑 `T = 1/8/64` | 精度仍通过；`T1` 2.939、`T512` 16.794 μs（保留时 2.936 / 16.621） | 无性能收益，且同址写后读的顺序保证丢失（竞争偶发，通过测试不能证明安全），保留 |
| **`Path` 阈值重标定（已采用）** | 在当前环境强制 `Path = 0` / `Path = 1` 各测一遍 `T = 1/2/3/4/8` | `T1` 3.020/3.131、`T2` 3.115/3.245、`T3` 3.87/3.54、`T4` 3.94/3.64、`T8` 4.02/3.75（单体/分行段，μs）；`T3` 加速 1.09 倍 | 阈值由 `4` 改为 `3`：`T = 3` 从 3.87 降到 **3.54 μs（−8.5%）**，其余用例不受影响 |

`T < 3` 与 `T ≥ 3` 分两条调度（`Path`）的阈值也是实测定的：单体方案在 `T = 1~2` 最快
（少一次 VF 边界），从 `T = 3` 起分行段因为 `p` 写回与计算重叠而占优（复核数据见 §3.3）。

## 4 已知限制

- 在 Ascend 950PR（28C/56V）+ CANN 9.1.0 / 9.2.0 / 9.3.0 上验证通过；UB 预算
  （200960 / 253952 B）与 tiling-key 接口依赖平台，换芯片需重新确认。
- 不同 pypto_pro 版本会改变向量 codegen：实测 9 月版在 `h` 上有 ~16% 元素差 1 个 BF16 ULP
  （`y` 37% 超 1e-3 门限），11 月版与本文件全部数据逐位一致。验收请固定工具链版本。
- `D` 固定 7168，不支持其他隐藏维；`T` 是唯一动态轴。
- `T ≤ 8` 的剩余空间在流水重叠而非核数：把向量计算整段去掉后的地板约 1.97 μs，当前
  `T1` 约 3.0 μs，两者之差是三段计算的串行暴露量。
