# QuantSparseLightningIndexer 结果记录（PyPTO-Pro）

对应实现：`op_kernel/quant_sparse_lightning_indexer.py`。接口与约束见 `README.md`，结构与流水见 `DESIGN.md`。本文给出用例、精度标准、绝对性能与理论评估。

本文的**用例通过记录与绝对性能表均为本目录当前实现的实测数据**：功能回归在 CANN 9.3.0 / `Ascend950PR_9589`（32 Cube / 64 Vector）上重跑，`--mode jit` 62 passed、`--mode aclnn` 54 passed；性能为 22 个测量点的 msprof 冷 L2 采集，环境与口径见「绝对性能结果」。

「理论评估对比」里的 pipe 占比与 MFU 均取自与性能表同一次采集；逐 pipe 的**绝对**折算时间需要能产出 `aicore_time(us)` / `aiv_time(us)` 的更高等级采集，本次未做，相关结论在下文按证据范围说明。

## 精度标准

**独立参考实现**：`tests/assets/quant_sparse_lightning_indexer_golden_cpu.py` 在 CPU 上独立解码 MXFP4 并按与 kernel 相同的舍入链计算——每字节低 4 位先于高 4 位、E2M1 幅值 `{0,0.5,1,1.5,2,3,4,6}` 配符号位、E8M0 指数 `字节值-127`、每 32 个连续逻辑元素共享一个 scale；QK 交接为 BF16，权重转 BF16，逐 head 融合乘加的每一步结果都舍入为 BF16。参考实现不读取设备输出，也不与 kernel 共享中间量。

**比较器**：`tests/assets/quant_sparse_lightning_indexer_precision.py`，固定阈值 `rtol = 1/128`、`atol = 2.5e-5`（`1/128` 对应 BF16 在 1 附近的相邻数间隔），由比较器模块常量固定，调用接口不接收自定义阈值。逐项检查：

1. 无效项：`indices == -1` 且（输出分数时）`values == -inf`；
2. 有效数量 == `min(topk, 允许集合大小)`；
3. 选中索引互不重复；
4. 选中索引先减去该行 `output_idx_offset`，再检查全部落在 `[0, 分数长度)` 且全部属于允许集合（候选块归属 + 可见性双重约束）；
5. 分数与参考实现在选中位置上一致（`rtol/atol`）；
6. TopK 边界：`min(选中分数) >= boundary - atol - rtol*|boundary|`，其中 `boundary` 为允许集合上第 `选中数量` 大的分数；`boundary` 为 `+inf` 时要求选中分数全为 `+inf`。

**输入连续性**：aclnn/nnopbase 会在 launch 前把非连续输入 `aclnnContiguous` 拷成连续（实测 tiling 申报 5,767,168 B 而 `aclnnXxxGetWorkspaceSize` 返回 22,545,408 B，差值即 16 MiB 系统预留 + 连续化拷贝缓冲），所以 kernel 永远只看到紧凑 axis-0 stride，`TndStrideMode` 在 built-in 路径下恒为 3。因此 `test_strides_scale_dtype_and_guards` 与 `test_independent_tnd_strides` 在 aclnn 模式下验证的是「框架归一化后端到端结果仍正确」；「kernel 自己按 padded stride 取址」这一路径只在 `--mode jit` 下被覆盖（`op_kernel` 宿主入口直接把调用方张量交给 kernel，不经过这次拷贝，会选到 `TndStrideMode` 的 0/1/2）。host tiling 相应地按紧凑 stride 申报，详见 `op_host/quant_sparse_lightning_indexer_tiling.cpp` 的注释。

由于输出顺序不保证，比较器不逐位置对齐 CPU `topk` 的索引，而是检查输出集合、数量、对应分数和选择边界。若边界处有同分项，允许选择其中任意合法项。即使不返回分数，比较器仍会根据选中的索引查询 CPU 分数并检查 TopK 边界。`test_comparator_rejects_corruption` 对比较器自身提供负例验证。

**结果记录**：本目录当前实现实测 **`--mode jit` 62 passed（1001.98 s）**、**`--mode aclnn` 54 passed**（另 8 项标 `jit_only`，见「用例」一节）。性能校验覆盖最后一次预热及计时窗口内首末输出；`--benchmark` 路径的中间采样输出没有逐一校验，故不能表述为「每个性能样本都独立通过精度检查」。

**口径**：冷 L2 —— 每个样本前对 **512 MiB** FP32 缓冲区做 `ReduceSum` 驱逐 L2
（= 上报 L2 容量的 **4.0 倍**；L2 驱逐 task 自身中位 335.2 µs，不计入结果），
与被测算子同 stream 串行。**3 轮预热丢弃 + 7 轮正式样本取中位数**；
- **同进程内交替发射**：每轮按「L2 驱逐 → 采样 → L2 驱逐 → 采样」的顺序成对发射，两个采样点
  相邻、共享同一份输入与同一张卡，使批次间漂移对两者的影响一致。
消除批次间漂移；每个场景一次独立 msprof 采集，共 11 次。
指标口径是**一次公开调用发射的全部 native task 耗时之和**；本实现每次调用恒定 1 个 task，
故逐 task 与整次调用的设备耗时相同。LI/LD 调度表在计时窗口之外生成一次，窗口内不含 AICPU task；
host 侧校验、分配与启动开销均不计入。

**采集自检**（解析侧强制，违反即报错退出）：① 每个计入的 task 必须紧邻**同 stream** 的 flush 前导；
② 每场景恰好 20 个 L2 驱逐前导 task（2 个计时前的一致性校验没有驱逐前导，按构造排除）；
③ 核配额必须恒为 `32/64`（22 个点全部满足）；④ 计时前先校验输出与 CPU 参考**逐位一致**
（`indices` 与 `values` 的 int16 位模式全等），**22 个测量点全部通过**。

  图捕获不会改变被测口径。

### 理论评估对比（MFU / Bound / 利用率）

本节所有由耗时推导的量已按本表 built-in `typical` 中位数 **76.709 µs** 重算；pipe 占比快照仍为结构改动之前的历史采样，未按当前结构重采。

Bound 表示性能受哪个阶段或哪类资源限制；MFU（Model FLOPs Utilization）表示有效计算吞吐与所选硬件理论峰值之比；roofline 分析用计算量、数据流量及相应峰值估算耗时下界。三者含义不同，特别是 profiler 的 MAC pipe 时间占比不能直接代替 MFU；本文的 MFU 以平台配置 `[DtypeMKN]` 的 FP4 fractal 推导峰值，口径与算式见下。

**主要判断**：原有 profiler 快照与单记录/成对 DMA 对照共同支持：`typical` 的主要优化方向是 AIV 读取离散 PA K 记录的阶段，包括访问效率和 DMA 发射。源码也显示每 tile 每 AIV 要处理 32 条独立记录。该判断适用于记录中的场景；当前结构改动后的 pipe 快照尚未刷新，不能把旧版本占比直接当作当前性能分解。

按原输入 K/scale 的读取量计算，算术强度约为 `9.664 GFLOP / 80.22 MB = 120.5 FLOP/B`，这里还没有计入 GM 中转、键工作区、部分结果及输出流量。`aic_mac_ratio=0.128` 应称为 MAC pipe 活跃时间占比，不是 MFU；MFU 的分子分母口径见上。**MXFP4 理论峰值与 MFU**：峰值按平台配置 `Ascend950PR_9589.ini` 的权威参数推导——`[AICoreSpec] cube_freq=1650`（MHz）、`cube_core_cnt=32`，`[DtypeMKN] DT_FLOAT4_E2M1=16,64,16`（即每核每周期一个 M16×K64×N16 的 fractal，对比 `Default=16,16,16` 的 BF16，FP4 的 K 维深 4 倍）。按一次乘加计 2 FLOP：

```text
MXFP4 峰值 = 2 × 16 × 64 × 16 × 32 核 × 1.65 GHz = 1730.2 TFLOP/s ≈ 1.73 PFLOP/s
BF16  峰值 = 2 × 16 × 16 × 16 × 32 核 × 1.65 GHz =  432.5 TFLOP/s   (仅供对照)
有效 QK 吞吐 = 9.664 GFLOP / 76.709 µs        =  126.0 TFLOP/s
MFU = 126.0 / 1730.2                          =    7.28%
```

**`typical` 场景的 MXFP4 MFU 约 7.3%**（若误用 BF16 峰值作分母会得到 29.1%，那是错的——硬件执行的是 `matmul_mx` 的 FP4×FP4 通路）。这个 MFU 只统计 QK 点积的 FLOP，不含 head 归约、键编码、radix 选择与位置映射等向量运算量，因此应读作「Cube 侧 MXFP4 峰值的利用率」，不是整算子的算力利用率。

7.3% 与实测的 `aic_mac_ratio=0.128`（MAC pipe 活跃时间占比 12.8%）并不矛盾，两者相除得 **MAC 活跃期内的峰值利用率约 57%**（`7.28% / 0.128`）：即 Cube 一旦在算，效率并不算差，MFU 低主要来自 MAC 有约 87% 的时间不活跃——与「主要瓶颈在 AIV 离散 K 记录搬运及 DMA 发射」（AIV `mte2` 占比 0.742 为各 pipe 最大）的判断一致。

#### 分析过程

以下结合源码解释上表数据，区分可直接计算的量与仍需验证的推断。

**第 1 步：核算点积工作量。** `typical` 为 72 行，每行 32 tile，共 2304 次 `matmul_mx`。每次完成 `32*512*128` 个乘加，按一次乘法和一次加法计 2 FLOP，总计约 9.664 GFLOP。除以 76.709 µs 得到 126.0 TFLOP/s，这是全芯片有效 QK 吞吐，不包含 head 归约和 TopK 的向量运算量。再除以 MXFP4 理论峰值 1730.2 TFLOP/s 得 **MFU ≈ 7.28%**；与本次重采的 `aic_mac_ratio=0.128` 相除可知 MAC 活跃期内的峰值利用率约 57%，即 MFU 低主要来自 MAC 约 88% 的时间不活跃，而非算的时候效率差。

**第 2 步：检查 AIC 累加结果是否限制流水。** 当前 `acc` 只有一个槽，MAC 与该槽的 FIXPIPE 搬出存在复用依赖。把 L0C 改为两槽的评估结果是：生成代码确认第二槽地址为 `0x10000`，典型耗时由 81.35 变为 81.51 µs，没有收益，因此保持单槽。这说明 MAC/FIXPIPE 的这项依赖不是主要瓶颈；该结论来自一次对照评估，不能推广到所有输入形状。详见 [DESIGN.md](DESIGN.md)「已知取舍与已否方案」。

**第 3 步：检查 Vector 和 MTE3。** 实测 `aiv_vec_ratio=0.221`，包括 head 归约、顺序恢复、键编码、radix 及位置映射；`aiv_mte3_ratio=0.322`，包括 GM 环发布与键写回。它们都低于 AIV MTE2。原有 UB→L1 对照中，省去 GM 中转约节约 0.121 µs/tile，UB 内布局重排却约需 0.624 µs/tile，因此该替代方案没有采用。多个 pipe 占比相加大于 1，说明快照统计范围内存在时间重叠，但不能单靠比例之和确定每对 pipe 的具体重叠关系。

**第 4 步：理解标量开销。** 实测 AIV `scalar` 为 0.348、AIV `mte2` 为 0.742，比值约 **0.47**，落在自查约定的 0.5 以内。源码中的地址准备、标量读取、循环和 DMA 描述符发射都会贡献标量工作；它与搬运效率密切相关。把成对 DMA 的数据依赖分支改成无条件地址钳位后，典型耗时曾从 80.64 降到 79.23 µs，说明发射路径值得优化，但不能据此把全部标量时间都归给这一项。

**第 5 步：核算候选数据读取量。** 每 Query 读取 2048 条记录，每条 544 B，共 `72*2048*544 = 80216064 B`，约 80.22 MB。除以 76.709 µs 得到 1.046 TB/s；相比**本次同环境实测**的 `ReduceSum` 顺序读参照 1.533 TB/s，为约 68%。这里统计的是算法请求的原输入字节数，未包含 cache line 放大，也没有 HBM 计数器数据，故应称为“有效候选读取吞吐”，不能直接写成实际 HBM 带宽利用率。

**第 6 步：将访问形态与 DMA 条数分开讨论。** 实测 AIV `mte2` 占比最大，为 **0.742**。由于 `aiv_time(us)` 在当前采集路径下恒为 0.0，无法折算成绝对 µs；其余约 25.8% 表示在该指标口径下 MTE2 不活跃，但其他 pipe 可能仍在执行，不能称为「没有任何 DMA 在执行」，也不能直接把不活跃比例当作可回收时间。

- **DMA 条数对照**：把每 tile 每 AIV 的 16 条成对 DMA 拆成 32 条单记录 DMA 后，典型场景由 81.5 µs 增至 101.9 µs，约上升 25%；按每核 72 tile 折算，新增一条 DMA 对应约 `20.4 µs/(72*16)=17.7 ns` 的平均时间增量。它包含发射、依赖和重叠变化后的整体结果，不能视为脱离场景的单条指令固定延迟。该方案因此被否决，详见 [DESIGN.md](DESIGN.md)「已知取舍与已否方案」。
- **访问形态分析**：每行从 16384 个逻辑块中随机选 2048 个，K 的逻辑页容量为 1024 页，页表又随机映射物理页；544 B 记录起点以 32 B 为粒度变化，不保证 512 B 对齐。这样的离散小块读取与顺序 `ReduceSum` 的访问方式不同，可能影响缓存及内存访问效率。不过现有 65–70% 比值还混合了发射、计算、同步等成本，没有独立随机访问带宽实验，不能把它宣称为输入格式决定且无法改进的带宽上限。

**第 7 步：估计带宽参照耗时。** `t_est = 80.22 MB / 1.533 TB/s ≈ 52.3 µs`。分母是**本次同环境实测**的顺序读带宽——同一次采集里那个 512 MiB `ReduceSum` L2 驱逐 task 的中位耗时 350.3 µs（`536870912 B / 350.3 µs = 1.533 TB/s`），不再沿用原文的 1.46–1.57 TB/s 区间取高值，本表 `t_meas/t_est = 76.709 / 52.3 ≈ 1.47`。它是只计原输入有效读取、采用乐观顺序带宽的参照，不是精确的完整 kernel 下界。随机访问、DMA 发射、GM 中转、行边界和分片归并都可能影响差距；这些因素会相互重叠，不能直接把各段 pipe 时间相加。若改用更低的随机读取带宽，估计时间会增加、比值会减小，因此当前 1.54 会放大相对于该估计的差距。

**第 8 步：结合调度解释其他阶段的影响。** 典型场景按 tile 数每 worker 都是 72，但不同 worker 的整行 TopK 次数及分片归并职责可能不同。AIC 要等待 `EV_K_READY`，AIV 要等待 `EV_QK_READY`，行尾还要执行子块握手和可能的 MIX 同步。实测 AIC pipe 占比之和约 **1.091**（`mac 0.128 + mte2 0.456 + mte1 0.140 + fixpipe 0.232 + scalar 0.135 + mte3 0.0`）、AIV 侧约 **1.633**、`cube_utilization=96.237%`，并不足以唯一还原上述等待关系。结合 DMA 条数对照可判断 gather 值得优先优化；要量化各段等待及当前瓶颈，仍需刷新 profiler 并查看分核时间线。

**测量口径的已知局限与后续优化方向**：

1. 当前目录没有上述历史性能批次、对照实验和 profiler 快照的原始附件，本次保留数字并解释其适用范围，没有新增实测结论。复测应保存 kernel/test SHA256、设备与工具链版本、每轮原始样本和 profiler 文件。
2. 成对 DMA 分支、手动同步与条件化全局屏障都影响 pipe 占比的解读。若要据此排定优化优先级，应先补采典型场景的**分核时间线**（各 worker 的 AIC/AIV 起止与事件等待）；单核汇总占比不足以精确还原等待关系。
3. 若继续优化，可验证 `kscratch` 已有自动 mutex 时每 tile 的显式 MTE3→V 同步是否仍必要；评估 K/scale L1 槽能否加深而保持 L0B 两槽；缩短空行输出路径。任何同步删除都需重新验证别名读写和跨核事件依赖。L1 深度改变还需解耦当前统一的 `buf=t&1` 索引、重新核算布局；GM 环加深需先处理事件 0–15 的编号预算。
4. 补采 L2 命中、HBM 实际流量和随机 544 B 读取参照，才能区分逻辑流量、缓存流量与内存流量；MXFP4 理论峰值已按 `Ascend950PR_9589.ini` 的 `[DtypeMKN] DT_FLOAT4_E2M1=16,64,16` + `cube_freq=1650` + `cube_core_cnt=32` 推导为 1730.2 TFLOP/s，MFU 已给出（约 7.28%，QK 口径）；但分子只含 QK 点积的 FLOP，若要把 head 归约、键编码与 radix 的向量运算量一并计入，还需另行核算 Vector 侧的等效 FLOP 与 VF 峰值，本文未做。
